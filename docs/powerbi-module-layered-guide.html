Quick overview

Harvest (inventory → definitions → parse) pulls TMDL/PBIR into Aurora and raw store. Link binds tables to Unity Catalog. Recreation (translate → oracle → parity → publish) produces kb_verified_queries for Inspector. Operators use Estate → Power BI and Jobs; agents never see raw TMDL.

Pilot result: Vessel Internal Audit — 63/73 measures published with parity (see recreation doc).

1. What we built (one paragraph)

ALOFT’s Power BI bridge harvests workspaces, semantic models, and reports from Microsoft Fabric/Power BI, stores structured metadata in Aurora (pbi_* tables) and encrypted raw TMDL/PBIR in object storage, binds model tables to Unity Catalog, compiles DAX measures to Databricks SQL, compares results to Power BI (“oracle”), and publishes parity-approved rows into kb_verified_queries so Inspector can answer questions with report-aligned SQL. Operators browse and debug everything on Estate → Power BI (/agent-lab/estate/powerbi). Harvest and recreation run as context jobs in the Node harvester (scripts/context/orchestrator.ts), not as ad-hoc Python in production.

Layer D — Harvest jobs (orchestrator)

Job kinds are implemented in scripts/context/orchestrator.ts (harvester container). Stages and chaining rules are defined in src/lib/powerbi/pipeline-stages.ts.

pbi_oraclePower BI reference valuesdax-query.ts, client.executeDatasetQueries

Recommended order (full recreation on one model):

pbi_inventory → pbi_definitions → pbi_parse → pbi_catalog_link → pbi_domains
  → pbi_translate → pbi_oracle → pbi_parity → pbi_publish

Example — launch translate for one model from Jobs UI / API:

POST /api/agent-lab/context/jobs/launch
Content-Type: application/json

{
  "kind": "pbi_translate",
  "sourceId": "<context-source-uuid>",
  "props": {
    "model_ids": ["b7d7e779-15df-4c75-9c8a-27764fd889d2"],
    "chain": ["pbi_oracle", "pbi_parity", "pbi_publish"],
    "ui_surface": "estate.powerbi.model"
  }
}

The Run pipeline control expands chain using PBI_STAGES so parse always pulls catalog_link + translate when definitions changed, etc.

Why TypeScript in the harvester (not Python): One Node image already runs catalog harvest; Fabric TMDL and REST are JSON/text; avoids a second runtime (build plan D7).

Why separate inventory from definitions: Inventory is cheap and safe to run often; getDefinition is heavy and rate-limited — skip when content hash unchanged.

Example — find published verified query for a measure:

SELECT id, natural_language_question, sql_text, status
FROM kb_verified_queries
WHERE org_id = :org
  AND pbi_measure_id = :measure_uuid
  AND status = 'verified'
  AND origin = 'powerbi';

Why raw TMDL is not in Postgres: Size, PII in embedded tables, and agent safety — stewards use Estate; agents get curated SQL only.

6. Worked examples

6.1 First-time estate onboarding (operator)

  1. Create context source (tenant + workspace GUIDs).
  2. Jobs → PBI Inventory.
  3. Jobs → PBI Definitions (scoped models or whole workspace).
  4. Jobs → PBI Parse.
  5. Jobs → PBI Catalog Link (requires catalog harvest for UC paths).
  6. Open Estate → Power BI → confirm models show tables/measures.
  7. For a pilot model → Run pipeline → Publish.
  8. Inspector → ask a question that matches a published verified query.

6.2 Debugging one failing measure

  1. Estate → model → measure shows parity_verdict: fail, root_cause JSON.
  2. Open graph: GET …/graph?measure=Attained_CII.
  3. Check fidelity: replica drift on a column? → fix UC or column override.
  4. GET …/measures/:id → compare full DAX vs SQL.
  5. Re-run chain: pbi_translate → pbi_oracle → pbi_parity for that model_ids only.
  6. CLI (dev): npx tsx scripts/powerbi/investigate.ts --model "<name>".

6.3 Catalog link fixing “No SQL”

Symptom: Measures stuck at no_uc / skipped_no_binding.

Cause: Partition used Databricks.Catalogs navigation without native SQL text.

Fix (2026-11-16): catalog-link.ts resolves {[Name=cat,Kind="Database"],…} paths. Re-run pbi_catalog_link then pbi_translate.

6.4 Compiler rule synthesis (missing DAX function)

Symptom: Compile error dax_fn for e.g. uncommon scalar.

Flow: translate.ts → rule-gap-fill.ts → LLM template → rule-difftest against Power BI → insert pbi_translation_rules → recompile measure.

Why: Avoid one-off hand SQL; estate-wide reuse after proof.

3. Definitions (pbi_definitions) — TMDL & PBIR files

How: Fabric POST …/getDefinition (async 202 → poll operation → definition.parts[]). Each part: { path, payload } where payload is base64 file bytes. Written by raw-store.ts under PBI_RAW_STORE_ROOT (default powerbi-estate/).

3.1 Semantic model → TMDL tree

API:

POST https://api.fabric.microsoft.com/v1/workspaces/{workspaceId}/semanticModels/{modelId}/getDefinition?format=TMDL

On disk (example layout):

powerbi-estate/definitions/{pbi_model_id}/
  database.tmdl
  model.tmdl
  relationships.tmdl
  expressions.tmdl          # shared M expressions
  cultures/en-US.tmdl       # Q&A synonyms
  roles/Owner & TSI RLS.tmdl
  tables/Fact_Sales/
    Fact_Sales.tmdl           # table, columns, measures, partition source = M
  tables/Date/
    Date.tmdl

TMDL is text (Tabular Model Definition Language): indentation-based blocks like table, column, measure, partition, relationship.

*Example — measure block inside tables/…/.tmdl:**

measure 'Revenue' = SUM(Fact[Amount])
    formatString: #,0.00
    displayFolder: KPIs
    lineageTag: a1b2c3d4-…

Example — partition source (Power Query M) in same file:

partition 'Fact_Sales' = m
    mode: import
    source =
        let
            Source = Databricks.Catalogs("adb-…", "catalog.schema.table")[Data],
            …
        in
            Source

Metadata stored on pbi_models.props after fetch (not the full files):

props.definition fieldMeaning
storage_kinddefinitions
storage_pathRelative path under raw root
part_countNumber of Fabric parts
content_hashHash of all part payloads
inventory_hashLinks to inventory content_hash when fetched
fetched_at, fetch_run_idAudit

Use: Input to pbi_parse; stewards can open raw TMDL on disk; graph API reads same folder for report consumers when present.

3.2 Report → PBIR or PBIR-Legacy tree

API:

POST https://api.fabric.microsoft.com/v1/workspaces/{ws}/reports/{reportId}/getDefinition
POST …/getDefinition?format=PBIR-Legacy   # when report_format is legacy

On disk:

powerbi-estate/report-definitions/{pbi_report_id}/     # modern PBIR
  definition/pages/…/visuals/…/visual.json
  report.json                                          # sometimes root summary

powerbi-estate/report-definitions-legacy/{id}/         # legacy
  report.json                                          # large JSON; config string inside

PBIR visual.json: JSON describing visual type, field wells (Measure.Property, columns, hierarchies), filters.

Legacy report.json: Outer JSON; inner config string contains escaped JSON — we scan for "Measure": { "Property": "Measure Name" }.

8. Example: one measure end-to-end

1. Inventory: dataset id + name → pbi_models
2. Definitions: Fabric TMDL → powerbi-estate/definitions/{id}/tables/X/X.tmdl
3. Parse: measure 'Opex YTD' = … → pbi_measures.dax + lineage_tag
4. Catalog link: partition M → pbi_source_bindings.uc_full_path = catalog.schema.fact_opex
5. Translate: DAX + graph → pbi_translations.sql_text
6. Oracle: EVALUATE { [Opex YTD] } → pbi_oracle_results
7. Parity: run SQL on Databricks → parity_verdict on translation
8. Publish: pass → kb_verified_queries (embedding + SQL)
9. Inspector: user question → run_verified_query

9. Security note

TMDL and legacy reports may contain embedded tables (emails for RLS, vessel lists). Raw store is not in git and is not exposed to agent tools; only steward UI and jobs read it.
