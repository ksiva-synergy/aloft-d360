Context Harvesting — Architecture & Step-by-Step Guide

How the harvester discovers Databricks objects, enriches them, embeds them for search, and powers Inspector harvested mode. Also covers scope, T3 usage, Mapper, and Silo Scan (manual vs scheduled). Includes worked examples.

Purpose

Raw warehouse tables are hard for an LLM to use. Harvesting copies and enriches metadata into Aurora (platform_context_*) so the app can search, describe, and profile objects without ad-hoc SHOW TABLES discovery on every chat.

OutcomeWhat harvest provides
DiscoverabilityVector + keyword catalog search (describe.ts → searchObjects)
TrustT1 profiles: null rates, cardinality, top values
SemanticsT2 LLM summaries, column roles, PII hints
FreshnessDaily change_detect → re-T0 only what changed
Inspector qualityHarvested mode: describe_schema first, then SQL on known paths
Usage intelligence (T3)Query history + lineage → key columns, co-tables, usage narrative
Cross-schema linksMapper (column mappings) + Silo Scan (table-level silo candidates)
Critical: If coverage or freshness is poor, contextMode=harvested can be worse than warehouse_only. Treat harvest health as a first-class SLO (Estate Overview, Jobs).

How often to run

Production schedules (EventBridge)

Defined in infra/context/eventbridge-rule.json. ECS runs scripts/context/orchestrator.ts.

Schedule (UTC)Command / kindWhat it does
Daily 04:00--sweepEnqueue change_detect for every active context source
Sunday 03:00--kind t1_profileFull column profiling sweep
Sunday 05:00--kind t3_usageUsage / query-history style harvest
Sunday 08:00--kind t4_scanT4 bootstrap (stubbed in this repo — fails until inspector port)
Monday 06:00--kind estate_inventoryFull estate re-inventory sync

When to run manually

  • New source: Sequential chain T0 → T1 → T2 → embed via POST /api/agent-lab/context/jobs/launch with sequential: true.
  • Urgent schema change: Per-source POST .../context/sources/[id]/harvest (queues T0) + launch orchestrator on ECS.
  • Single object: Re-harvest from Estate Object Detail / reharvest-all APIs.
  • Refresh LLM text: T2 + embed on demand (costly).
  • Cross-schema alignment: Mapper when two schemas must join (steward confirms proposals).
  • Silo discovery: Silo Scan per anchor table (not on cron).

You do not need the full T0→embed chain daily; daily change detect + weekly T1 is the usual balance. Mapping and silo jobs are not on EventBridge — see Mapper and Silo Scan.

Before harvest — worked example setup

Throughout this guide we use one table and one connection:

  • Connection display name: synergy_dwh (platform_databricks_connections)
  • Context source: src-001 → connection_ref, status=active, scope_include=['*.*.*']
  • Table: curated_db.maritime.crew_certificates

Before the first harvest: last_sweep_at is null, platform_context_objects has no rows for that path. Inspector harvested search returns nothing until T0+ (ideally through embed) completes.

Source scope — scope_include / scope_exclude

Your Databricks workspace may have thousands of tables. ALOFT does not treat all of them as “your estate” unless you say so. Scope is the permanent fence on each context source (platform_context_sources).

Simple rule for every table path catalog.schema.table:
  1. Must match at least one include pattern (default: *.*.* = as wide as permissions allow).
  2. Must not match any exclude pattern.
  3. Only then can estate inventory, T0–T2, Inspector catalog search, and (later) T4 bootstrap see that table.

What the fields mean

FieldStored onPurpose
scope_includeContext source (JSON array of globs)Allow list — which catalog.schema.table paths belong to this source.
scope_excludeSame sourceDeny list — paths to skip even if they matched include.

Patterns use three parts and * wildcards, e.g. curated_db.addressable_market.*. Matching logic: src/lib/context/scope-match.ts (matchesScope).

Worked example — curated_db.addressable_market

curated_db.addressable_market is a catalog + schema (all tables live under curated_db.addressable_market.<table_name>).

Only this schema

scope_include: ["curated_db.addressable_market.*"]
scope_exclude:  []

Harvest and catalog only tables in addressable_market. Other catalogs/schemas (even in the same workspace) are ignored for this source.

PathIn scope?
curated_db.addressable_market.fact_salesYes
curated_db.other_schema.any_tableNo
other_catalog.addressable_market.xNo (wrong catalog)

Whole curated_db catalog, but skip scratch schemas

scope_include: ["curated_db.*.*"]
scope_exclude:  ["curated_db.staging.*", "curated_db._scratch.*"]

addressable_market is included unless you add it to scope_exclude.

15k tables in Databricks vs hundreds of semantic entities

Scope is only the first filter. A table also needs T0 → T1 → T2 (last_t2_at) before T4 can propose an entity. So a wide *.*.* include does not mean 15k Auto-Bootstrap entities — only tables that were harvested, enriched, and processed by T4.

Where to set this in the product

1. Permanent scope_include / scope_exclude (source)

  • At source creation (API): POST /api/agent-lab/context/sources with JSON body fields scope_include and scope_exclude (arrays of strings). See src/app/api/agent-lab/context/sources/route.ts.
  • Estate overview: /agent-lab/estate — source cards show a catalog hint derived from the first include pattern (read-only today).
  • Note: There is no dedicated “edit scope” screen in the UI yet; changing an existing source’s permanent scope is typically done via API/DB until a settings page is added.

Example API body for your schema:

POST /api/agent-lab/context/sources

  "display_name": "Synergy curated",
  "scope_include": ["curated_db.addressable_market.*"],
  "scope_exclude": []

2. Per-job focus — includePatterns and excludeSchemas (UI)

Use this when you want one harvest run to target a slice without changing the source forever.

  1. Open Agent Lab → Data Estate → Jobs (/agent-lab/estate/jobs).
  2. Choose a job type (e.g. T0 Structural, T2 Semantic, or a sequential T0→T1→T2 chain) and start a run.
  3. In the launch confirmation modal:
    • Scope — click schemas to exclude: tree of catalogs/schemas → toggles excludeSchemas (stored as catalog.schema).
    • Focus — limit to specific tables (optional): textarea for includePatterns (e.g. curated_db.addressable_market.*, one per line).
  4. Confirm launch — scope is saved on the job; see it on the job detail page under excluded schemas / include patterns.

Implementation: src/app/(agent)/agent-lab/estate/jobs/page.tsx (launch modal), POST /api/agent-lab/context/jobs/launch.

Example runs (source allows all of curated_db)

Run A — only addressable_market:

excludeSchemas:  (none)

Run B — all curated_db except staging:

On launch (T0 / estate inventory): If includePatterns is empty, the Jobs modal may auto-exclude schemas in catalogs with more than 5,000 estate objects (e.g. huge landing_zone) so the first inventory does not sweep everything. You can un-check schemas in the tree before confirming. Scheduled EventBridge jobs do not use this modal — only the source’s permanent scope.
Semantic layer link: T4 Auto-Bootstrap only proposes entities for tables already in platform_context_objects with last_t2_at set. Tightening scope_include to curated_db.addressable_market.* is how you tell ALOFT “bootstrap semantics for this business area first.” See semantic-layer-guide → Context pipeline T0–T4.

How a run actually starts

A Daily schedule

  1. Fargate starts with orchestrator.ts --sweep.
  2. failStale(30) marks stuck running jobs failed.
  3. For each active source: enqueue('change_detect', sourceId, …).
  4. Loop: claimNext(orgId) → handler → until empty.
platform_context_jobs example:
  job_kind=change_detect  status=succeeded  stats={"changed_refs":1}

B Per-source harvest API

POST /api/agent-lab/context/sources/{id}/harvest → enqueues t0_structural only. Something must run the orchestrator (ECS launch route) to drain the queue.

C Full pipeline launch

POST /api/agent-lab/context/jobs/launch
{
  "kinds": ["t0_structural", "t1_profile", "t2_semantic", "embed"],
  "sequential": true
}

First job gets scope.chain = ["t1_profile","t2_semantic","embed"]. ECS runs --kind t0_structural; chain advances after each success.

Step: change_detect

Purpose: Find tables altered since last sweep; queue T0 only for those paths.

  1. Load source and Databricks connection; since = last_sweep_at.
  2. SQL (simplified): SELECT … FROM system.information_schema.tables WHERE last_altered > since
  3. Filter to source scope; example hit: curated_db.maritime.crew_certificates.
  4. For each ref: enqueue('t0_structural', sourceId, { path }, 'scheduled').

If system.information_schema is unavailable, adapter falls back to full resolveScope (treat as full change set).

Note: Daily change detect enqueues T0; it does not automatically run T1/T2/embed unless those jobs are queued or you launched a chain.

Step: t0_structural

Purpose: Copy schema from Databricks into Aurora (table/view inventory, column names, types, comments). T0 does not profile data (T1), run LLMs (T2), write embeddings, or create platform_sem_* rows (T4 + stewards).

ConditionBehavior
last_sweep_at IS NULLFirst run → resolveScope (all in-scope tables)
Later runsdetectChanges since last_sweep_at, or per-table jobs from change_detect
forceFullScanAlways resolveScope
includePatterns on jobForce resolveScope for that subset; does not advance last_sweep_at (preserves delta baseline)
excludeSchemas on jobMerged into source scope_exclude as catalog.schema.* globs for this run

harvestStructure (src/lib/context/databricks-adapter.ts) batches metadata SQL per catalog/schema. Results upsert into:

platform_context_objects:
  full_path: curated_db.maritime.crew_certificates
  object_kind: TABLE
  last_t0_at: (timestamp)
  lifecycle: active

platform_context_columns:
  crew_id, certificate_type, expiry_date (+ types, ordinals)

On a full sweep, objects missing from the run can be marked lifecycle: dropped (scoped drops when includePatterns was used). Updates last_sweep_at on platform_context_sources except includePatterns-only runs. Calls syncEstateFromHarvest → platform_estate_objects. On success with scope.chain, orchestrator.ts advanceChain enqueues T1.

Full walkthrough (UI → tables → pipeline): semantic-layer-guide → T0 deep dive.

T0 deep dive — what happens inside

This section documents the full T0 structural harvest path so you can reason about Data Estate, Inspector contextMode=harvested, and downstream T1–T4.

One-sentence summary

T0 answers: “What tables and columns exist in Databricks under this source’s scope?” and mirrors that into Aurora. Everything else in the harvest pipeline builds on those rows.

Inside runT0Harvest

Implementation: src/lib/context/harvest.ts → runT0Harvest. Called from scripts/context/orchestrator.ts when a claimed job has job_kind = t0_structural.

  1. Load source — platform_context_sources (scope_include, scope_exclude, last_sweep_at, connection_ref).
  2. Choose full vs delta — first run, forceFullScan, or job includePatterns → DatabricksAdapter.resolveScope; otherwise detectChanges(source, last_sweep_at).
  3. Connection — load platform_databricks_connections; build adapter with warehouse id + workspace host.
  4. Harvest structure — harvestStructure(refs) (SHOW CATALOGS, information_schema.tables, column metadata per ref; see adapter).
  5. Upsert catalog — for each table: upsert platform_context_objects (set last_t0_at, lifecycle: active); upsert platform_context_columns per column.
  6. Drop pass — on full sweep only: mark missing in-scope objects dropped (narrowed to harvested schemas when includePatterns used).
  7. Estate sync — syncEstateFromHarvest updates platform_estate_objects for Discovery UI.
  8. Source stamp — set last_sweep_at unless this was an includePatterns-only subset run.
  9. Job stats — inner run creates/updates a platform_context_jobs row with objects_swept, columns_upserted, queries_issued, etc.; orchestrator also finalizes the queued job it claimed.

Step: t1_profile

Purpose: Run profiling SQL on Databricks; store stats and drift in Postgres.

For crew_certificates: row counts, per-column null rates, distinct estimates, top-K values. Writes platform_context_profiles, updates row_count_est, last_t1_at, column profile JSON.

Example:
  row_count_est = 48291
  expiry_date.profile → null_rate, top_k, min/max
  last_t1_at = (timestamp)

Purpose: Bedrock (Claude Sonnet) produces object card + per-column semantics from T0/T1 data — no warehouse calls in enrich.ts.

Step: t3_usage (T3 — usage & connections)

Purpose: Learn how tables are actually used in Databricks — from query history and lineage — not just what columns exist (T0/T1) or what AI says they mean (T2).

Job kinds: Real implementation is t3_usage (src/lib/context/usage.ts, orchestrator case in orchestrator.ts). The Jobs UI also lists t3_connected, but there is no orchestrator handler for it today — use t3_usage.

What each tier answers

TierQuestion
T0What tables and columns exist?
T1What do values look like (nulls, stats)?
T2What does this data mean (summaries, PII hints)?
T3How is it used (queries, joins, busy columns, lineage neighbors)?
T4What business entities/measures to model? (stubbed in this repo)

Pipeline inside runT3Usage

  1. Window — Default ~7 days since last last_t3_at on the source, or explicit since/until for continuation jobs.
  2. Query history — Pull via DatabricksAdapter.pullQueryHistoryWindow (capped, e.g. 50k rows; may set nextCursor and enqueue a follow-up t3_usage job).
  3. Lineage — Table + column lineage for the same window (capped).
  4. Per object — Match queries whose text mentions the table name; derive:
    • access_stats — query count, executors, jobs vs ad-hoc vs dashboard vs Genie, first/last seen, weekly trend
    • key_columns — columns in SELECT/JOIN/WHERE (scored; lineage boosts importance)
    • filter_patterns — common WHERE shapes (literals masked — no secrets in stored patterns)
    • co_objects — other tables in the same queries or via lineage (“often used with”)
    • drift — vs previous usage snapshot version when applicable
  5. Persist — Versioned row in platform_context_usage; set last_t3_at and usage_evidence_at on the object.
  6. Narrative (top N) — Bedrock writes a short usage story + key columns into platform_context_semantics (status: observed) for the busiest tables.

Plain English example

Table curated_db.crew.active_roster after T3 might show: “240 queries this week, mostly jobs”; key columns crew_id, vessel_imo; co-objects curated_db.payroll.payslips and curated_db.fleet.vessels; narrative describing vessel filters and payroll joins. That comes from real query text + lineage, not schema guessing alone.

Mapper — mapping jobs (cross-schema column alignment)

Purpose: Propose column-to-column links across two schemas (e.g. HR vs payroll) so joins, lineage, and Inspector relations reflect business reality. Stored in platform_context_mappings (not platform_entity_mapping — that name appears in older architecture docs only).

Plain English

Same real-world field, different names: crew_id in one table and employee_ref in another. Mapper finds candidates with signals + LLM; stewards confirm or reject — nothing is auto-confirmed by the job.

Left scope:  curated_db.hr.*
Right scope: curated_db.payroll.*
→ proposals: crew_id ↔ employee_ref, vessel_imo ↔ ship_imo, …

What the job does (automated once started)

  1. Resolve left/right pathGlob → object IDs (mapping.ts → runMappingJob).
  2. Score column pairs: embeddings, name similarity, types, profiles (and value overlap where safe).
  3. Bedrock adjudicates: mapped / not_mapped / uncertain + mapping_kind (same_attribute, same_entity_key, derivable, …).
  4. Insert/update rows with status: proposed only.
  5. computeEntityTags — group objects into entity_tags on platform_context_objects from strong proposed key/attribute links.

Invariant: No Databricks access in mapping.ts — reads platform_context_* only.

Silo Scan — silo_scan jobs (table-level silos)

Purpose: For one anchor table, find other tables that may be the same business concept in a different catalog/schema (a data silo), not byte-for-byte duplicates. Complements Mapper (columns across two chosen schemas) and T3 (query co-usage).

Plain English

“We have crew roster here — is the same concept hiding under a different name elsewhere?” Silo Scan proposes table-to-table links for human review.

What one run does

  1. Embedding search — nearest neighbor objects in platform_context_embeddings (requires embed).
  2. Signals — column overlap, types, profiles, shared entity tags → composite score (default keep ≥ 0.60).
  3. LLM verdict — per pair: silo, duplicate, related, unrelated.
  4. Persist — platform_context_object_links (link_kind: silo_candidate, status: proposed).

Invariant: No warehouse access in silo.ts.

Inspector — full user example

User: “How many crew certificates expire this month?” — contextMode: harvested, connection synergy_dwh.

1. Chat setup

/api/inspector/chat loads governed semantic context if present. System prompt requires catalog search first. Tools include describe_schema and execute_tool.

2. Tool: describe_schema search

{ "action": "search", "connection": "synergy_dwh",
  "query": "crew certificates expiry", "k": 8 }

  "score": 0.87, "match_type": "blended" }] }

3. Tool: describe + profile + relations + usage

{ "action": "describe", "path": "curated_db.maritime.crew_certificates", "detail": "full" }
{ "action": "profile", "path": "curated_db.maritime.crew_certificates" }

All reads from platform_context_*. relations includes T2 FK hints, Mapper column proposals, and entity_tags peers. usage needs T3 (last_t3_at).

4. Tool: execute_tool

SELECT COUNT(*) AS expiring_count
FROM curated_db.maritime.crew_certificates
WHERE expiry_date >= date_trunc('month', current_date())
  AND expiry_date < date_trunc('month', current_date()) + INTERVAL 1 MONTH
LIMIT 100

Runs on Databricks via executeDatabricksSQL.

Splitting & concurrency

Large estates exceed a 15-minute budget per task (queue.ts TIME_BUDGET_MINUTES). planSplit creates parent + child jobs per catalog.schema partition; up to 5 concurrent child Fargate tasks. Children run orchestrator.ts --child-job <id>. When all children succeed, parent finalizes and chain continues to the next tier.

Mental model

Databricks     = source of truth for DATA and live SCHEMA changes
Aurora context_* = source of truth for CATALOG TOOLS (describe_schema)
ECS orchestrator = moves knowledge Databricks → Aurora in staged jobs
Inspector harvested = search/describe/profile from Aurora, then SQL for answers
