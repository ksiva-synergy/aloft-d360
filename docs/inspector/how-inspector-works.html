ALOFT · Inspector · how it works

How Inspector finds your data

When you ask Inspector a question, a model works in small steps: look up tables, read their columns, write SQL, then answer. This page shows how that loop runs, what the describe_schema tool does, and how embeddings let it search tables by meaning.

1 · The big picture

Two paths: prepare ahead, answer live

Before anyone asks a question, the Estate harvest copies Databricks metadata into ALOFT's own Postgres database. When a question arrives, the model reads that copy (fast and free) and only goes to Databricks to run the final SQL.

The model can only see tables the harvest has copied. A table missing from the catalog is invisible to Inspector, even though it exists in Databricks.

2 · The ReAct loop

Think, act, look, repeat

ReAct stands for Reason + Act. The model does not plan the whole answer up front. It takes one step, sees the result, and decides the next step. It stops when it replies with text and no tool call, or after 15 steps.

Step through a real-shaped example below. Watch the right-hand side: every step re-sends the whole conversation to the model, so each step is a full model call that gets bigger.

Example question: “How many crew certificates expire next month, by vessel?”
What model call #1 reads

Within one turn, about 80% of the input is served from the gateway's prompt cache, which makes repeated context cheaper. The model still has to work through all of it on every step, and nothing is cached across turns.

Measured from agent_turn_log and tool_invocation_log on dev (30 completed turns). The time goes into model calls, not database lookups. Fewer steps means faster answers.

Why ReAct fits Inspector

The model can't plan SQL before it knows which tables exist and what their columns are. Each step depends on the last result. ReAct also lets it recover in the same turn: if SQL fails, it sees the error and tries again.

What it costs

Every small step is a full model call that re-reads everything. Ten tiny lookups means ten big calls. The design works best when each step does more.

Code: the loop is runFoundryAgentLoop in src/lib/inspector/providers/foundry-chat.ts. Tools requested in the same step run in parallel. The 15-step limit is set in src/app/api/inspector/chat/route.ts.

3 · The describe_schema tool

One tool, seven actions

describe_schema reads the harvested catalog in Postgres. It never touches Databricks, which is why the prompt calls it “free”. The model picks an action each time it calls it.

ActionYou give itIt returnsAnswersStatus
searchA short phraseThe k best-matching tables: path, summary, score. No columns.“Which table holds this?”available
describeOne table pathColumns, types, comments, freshness, summary, related tables. compact or full.“What columns does it have?”available
profileOne table pathPer column: null rate, distinct count, top values“Which status values exist?”available
relationsOne table pathLikely join keys and related tables“How do I join to vessels?”available
listConnectionEvery tableRarely usefulavailable
researchA phraseSearch plus describe and relations for the top 5, in one callAll of the above at oncebuilt, not exposed
usageOne table pathHow people actually query it: common filters, key columns, tables it's usually joined with“How is this table normally used?”built, not exposed

research and usage are handled in src/lib/context/dispatch.ts but are missing from the tool's allowed actions in src/lib/inspector/prompts.ts, so Inspector's model can't call them. The Agent Lab builder already uses research. The server also runs no more than 2 describe_schema calls at once, so a burst of describes queues up.

4 · The prompt's rules

The order the model is told to follow

The system prompt sets this workflow. It's the reason a typical turn goes search → describe → profile → SQL, with one model call each.

Step 0
Check memory. If the injected operating memory already names the table, skip searching.
Step 0b
Check session knowledge. Table paths already confirmed in this chat shouldn't be searched again. Columns aren't carried over, so the model often describes them again.
Step 1
Search the catalog first, e.g. search “crew certificates” k:8.
Step 2A
Found: describe the tables, then profile them, and only then run SQL with execute_tool.
Step 2B
Not found: don't explore Databricks with SQL. Tell the user the domain isn't harvested yet.
Rules
“describe_schema is free… use it liberally.” “If SQL fails, fall back to describe_schema.” Both rules push the model toward more lookups.
5 · How embeddings work

Turning a table's meaning into numbers

search has to find “crew certificates” even when the table is called crw_cert_dtl. Matching words isn't enough, so it compares meaning. An embedding model reads a sentence and turns it into a list of 1,024 numbers. Sentences that mean similar things get similar lists.

Step 1 · From a table to a vector (done once, during harvest)

A · the text we build
curated_db.crew.crew_certificates (table): Certificates held by each seafarer, with issue and expiry dates and issuing authority. Grain: one row per certificate per crew member. Key columns: crew_id, cert_type, expiry_date, vessel_id.

Step 2 · Search is “find the nearest points”

Think of every table as a point on a map, placed by meaning. Your question becomes a point too. Search returns the closest points. Pick a question:

Has a Titan embedding: search can find it No usable embedding: invisible to meaning search Your question

Illustration, not real positions. Real vectors have 1,024 dimensions, which can't be drawn. Table names are examples. The idea holds: the question lands near tables with similar meaning, and tables without an embedding can only be found by name or keyword.

Step 3 · “Close” is measured as cosine similarity

Each vector is an arrow. Similarity is how closely two arrows point the same way: 1 means identical direction, 0 means unrelated.

The numbers below are measured on our catalog. Real tables are well spread out, so the vectors work. But for a typical question, the best match and the fifth match score almost the same, so search isn't confident about which table is right.

6 · How search ranks

Meaning first, then two word checks

Meaning alone can miss exact names, so the final score blends three signals. Results scoring under 0.15 on meaning are dropped. Tables in the same entity group as a strong hit get a small +0.05 boost.

Worked example with made-up inputs: score = 0.7 × meaning + 0.15 × keyword + 0.15 × name. Weights from src/lib/context/search-ranking.ts. A table with a cryptic name and no embedding scores zero on all three, so it never appears.

9 · Glossary

Terms on this page

ReAct
Reason + Act. The model takes one step at a time, reads each result, and decides the next step.
Loop / step
One model call. It returns tool calls (keep going) or a final answer (stop).
Tool
A function the model can ask ALOFT to run, such as describe_schema or execute_tool.
Harvest
Estate jobs that copy Databricks metadata into Postgres and enrich it with stats, summaries and relations.
Semantic card
The AI-written summary of a table: what it holds, its grain, key columns.
Embedding / vector
1,024 numbers that represent the meaning of a sentence. Similar meanings give similar numbers.
Titan v2
Amazon's embedding model on Bedrock, used for every searchable vector.
pgvector
The Postgres extension that stores vectors and finds the nearest ones quickly.
Cosine similarity
How closely two vectors point the same way. 1 means the same direction, 0 means unrelated.
Prompt cache
The gateway reuses the unchanged start of a request, which makes repeated context cheaper within a turn.
