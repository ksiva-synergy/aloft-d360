Self-Improving Memory — Architecture & Step-by-Step Flow

How ALOFT D360 learns from Inspector sessions without retraining models: traces are captured during the day, rules are injected into prompts, and overnight jobs distill new bullets for tomorrow.

What “self-improving” means

Self-improving is not fine-tuning Claude or Bedrock weights. It is a closed feedback loop:

  1. Analysts use Inspector; every tool call is recorded as a trace graph.
  2. Relevant memory bullets are retrieved and injected into the next prompt.
  3. Run success or failure updates bullet quality (helpful_count / harmful_count).
  4. Overnight synthesis reads traces and extracts new rules via an LLM (“Captain Track Sparrow”).
  5. New rules appear in Postgres immediately and affect the next chat via injection.
Design principle: Learning happens at prompt time — auditable, reversible (SUPERSEDED status), and scoped by task_signature so crew rules do not bleed into vessel tasks.

Memory bullets

Each rule is a row in platform_agent_memory.

Field / conceptMeaning
rule_typeHARD_RULE, SCHEMA_MAP, HEURISTIC, SOURCE_PREF, FAILURE_MODE

embeddingBedrock Titan vector for Phase 1b cosine search

Daytime — Inspector chat entry

POST /api/inspector/chat — approximate order of operations:

  1. Auth, semantic context, base system prompt
  2. Memory injection if MEMORY_INJECT_ENABLED=true and class allowed
  3. Trace writer — openSession(sessionId, 'inspector')
  4. Agent loop (Bedrock stream + executeInspectorTool)
  5. After stream: cost log, bandit, optional Marcus, attributeRunOutcome

Trace graph (synthesis input)

src/lib/memory/trace/capture.ts writes nodes fire-and-forget to Postgres.

Node typeMeaning
ACTIONTool invoked (name + params in payload)
OUTCOMETool succeeded; linked via LED_TO
CORRECTIONUser or agent fixed a path; CORRECTED_BY edge
DEAD_ENDFailed path (TABLE_NOT_FOUND, etc.)
SOURCECatalog / schema reference

Cross-turn corrections: if the last tool of a turn failed, the next user message can be recorded as CORRECTION — user semantics are treated as ground truth in synthesis.

Reconstruction: reconstructSession() runs a recursive CTE (max depth 3) for reflect + Rama validation.

Three-phase injection

Gated by MEMORY_INJECT_ENABLED=true and MEMORY_INJECT_CLASSES (e.g. inspector).

PhaseNameRule typesWhere injectedDefault budget
0INITHARD_RULE with confidence ≥ 0.9 and harmful_count ≥ 1System prompt~200 tokens, max 3
1aSCHEMA_GLOBALSCHEMA_MAP for agent class (+ FOER topic filter)System prompt~600 tokens, max 10
1bTASK_SCOPEDHEURISTIC, SOURCE_PREF, FAILURE_MODE via embedding searchSynthetic assistant turn before first user message~1200 tokens, max 20

Extras

  • Personal taught lane — author’s visibility='personal' rules even when helpful_count is 0
  • MMR — MEMORY_MMR_ENABLED diversifies similar bullets
  • Topic key — derived from user text + platform_memory_topics (FOER)

Advisory lock

lock.ts uses a dedicated pg.Client on DIRECT_URL and pg_try_advisory_lock(fnv1a64('mem-orch:{orgId}:{group}')) for the full DAG duration — prevents duplicate synthesis on the same org.

Job audit

Each job writes platform_job_runs (status, items processed, errors). Synthesis also writes platform_memory_synthesis_runs + per-session platform_memory_synthesis_details.

Manual trigger: POST /api/agent-lab/memory/synthesize runs runSynthesisSweep only (cap 20 sessions) — not the full locked DAG. Production nightly/weekly runs are expected to invoke runDag(orgId, 'nightly' | 'weekly') from your scheduler; monitor via Agent Lab FOER Ops UI.

Synthesis sweep — step by step

src/lib/memory/run-sweep.ts

1 Start run

Create platform_memory_synthesis_runs with reflectorVersion (e.g. marcus_reflect_v3).

2 Discover sessions

  • Watermark: max created_at on ACTIVE bullets for org
  • Already processed: union of all source_session_ids on ACTIVE bullets — each session synthesized at most once
  • Candidates: distinct session_id in platform_trace_nodes where created_at > watermark
  • Exclude: MEMORY_SYNTH_EXCLUDE_SESSION_IDS (comma-separated stopgap)

3 Per session — processSession

  1. Resolve agentClass from first trace node
  2. computeTaskSignature — SHA-256(agentClass :: tools :: entity keywords)[0:16]
  3. reconstructSession
  4. reflectSession → 0–7 candidate bullets
  5. curate → insert / dedup / supersede / quarantine

4 Finalize

Update synthesis run aggregates; one detail row per session.

Reflect — LLM extraction

src/lib/memory/synthesis/reflect.ts — persona Captain Track Sparrow, prompt version marcus_reflect_v3, model BEDROCK_SONNET_MODEL_ID.

Inputs (JSON to Bedrock)

  • TASK_SIGNATURE
  • ORDERED_TRACE — nodes, tool params, summaries, errors
  • EXISTING_BULLETS for dedup guidance
  • MARCUS_REFLECTIONS for the session

Sieve — discard

Typos, retry flaps, cosmetic fixes, dismissed reflections, negative existence inferred only from truncated describe_schema, invented join logic not seen in trace.

Sieve — keep

Structural errors, approach-changing corrections, successful SQL paths, schema discoveries, source preferences. User CORRECTION nodes are authoritative.

Output

0–7 JSON objects; Zod validated; no DB writes in reflect — only candidates to curate.

Curate — merge into store

src/lib/memory/synthesis/curate.ts — per candidate, in order:

StepModuleAction
0scrub.tsPII / credential redaction before embed or insert
0bvalidate.ts (Rama)Block phantoms — identifier must appear in trace
0ccaveat-guard.tsOptional QUARANTINE for caveat-heavy tables
1embedQueryTitan embedding → pgvector
2Nearest neighboursCosine distance within task scope (SCHEMA_MAP cross-signature dedup)
3DEDUPdistance < 0.07 → increment helpfulCount, append session id
4SUPERSEDEdistance < 0.20 + type/confidence change → old SUPERSEDED, new version+1
5INSERTNew ACTIVE bullet v1
Invariants: curate never hard-deletes rows; never rewrites bullets outside the candidate’s scope; supersede preserves history with valid_until.

Weekly refine — grow_refine

src/lib/memory/synthesis/refine.ts

  1. Dedup clustering — pairs with distance < 0.07 within (agentClass, taskSignature); merge counts
  2. TTL decay — e.g. FAILURE_MODE 14d, HEURISTIC 60d, SCHEMA_MAP 90d, HARD_RULE never (override via MEMORY_TTL_*)
  3. Harmful GC — harmful ≥ helpful and harmful ≥ 3 → SUPERSEDED
  4. Stats — health logging for Agent Lab

FOER — topic clustering

Framework for Organizing Episodic Recall — src/lib/foer/run-cluster.ts

Classifies each task_signature into a domain vocabulary (e.g. crew_personnel, vessel_voyage, estate_navigation) using Bedrock on sample rule texts → platform_memory_topics.

Coverage target: 90% of signatures assigned. Nightly DAG appends reclassify inline when coverage drops after synthesize; weekly always runs reclassify.

At chat time, Inspector derives topicKey from the user message to scope Phase 1a SCHEMA_MAP retrieval.

Reputation (optional)

When MEMORY_REPUTATION_ENABLED=true:

  • Curate records contributions (INSERT_AUTHOR, DEDUP_REINFORCE, …)
  • Attribution updates contributor reputation on helpful/harmful outcomes
  • Season-based leaderboard in Agent Lab; weekly rollover (Sunday 05:30 UTC target)

All reputation hooks are non-fatal — failures never break chat or synthesis.

Timeline example

Monday 10:00 — Analyst asks about crew certificate expiry
  • Phase 0/1a/1b bullets injected (if enabled)
  • Agent runs describe_schema → execute_tool; trace nodes append
  • recordInjection + successful run → injected bullets get helpful_count++
Tuesday 04:30 UTC — Nightly synthesize
  • Lock → sweep finds Monday’s session
  • Reflect extracts HEURISTIC about expiry_date as DATE
  • Curate validates against trace, embeds, INSERT or DEDUP
  • Optional reclassify if FOER coverage < 90%
Tuesday 10:00 — Similar question
  • New bullet appears in Phase 1b (semantic) or 1a (SCHEMA_MAP) without model retraining
