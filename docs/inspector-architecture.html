What Inspector is

Inspector is the product’s conversational data analyst for Synergy Maritime / Databricks data. It is not a separate microservice. It is a vertical slice of the monolith:

  • UI — InspectorShell on routes /inspector and /inspector/:sessionId
  • Client harness — useInspectorChat (SSE, messages, tool cards, charts)
  • API — POST /api/inspector/chat (prompt assembly + stream)
  • Engine — runAgentLoop / dispatchAgentLoop with executeInspectorTool
Product role: Help users understand data before they commission an agent in the workbench. The system prompt and AgentHandoffCard steer “build an agent” intent toward Agent Lab.

Harness layers (engineering model)

Inspector is a classic single-agent harness (ReAct-style tool loop), not a workflow engine or multi-agent orchestrator.

Layer Responsibility Primary code

Runtime: One HTTP POST per user turn, text/event-stream, maxDuration = 300 seconds. Closing the browser aborts the request; the agent does not continue in a background worker.

  1. User sends text from PromptCanvas.
  2. Client appends user + empty assistant messages and opens SSE to /api/inspector/chat.
  3. Server builds system prompt + optional synthetic recall turn, runs the tool loop.
  4. Client updates UI from SSE events; persists query results via /api/studio/results when applicable.
  5. After ~2s debounce, client PATCHes /api/agent-lab/workbench/sessions/:id with messages (server does not own transcript during stream).

Sessions & context mode

Creating and loading sessions

  • New: POST /api/inspector/sessions → workbench_sessions with surface: 'inspector'. Requires inspector:use or session:write.
  • Load: GET /api/agent-lab/workbench/sessions/:id + optional GET /api/studio/results?sessionId=... for past SQL result sets.

Server context stack (before the model runs)

Each turn, inspector/chat/route.ts assembles analysis context:

InputPurpose
Base system promptMandatory workflow: memory → catalog → SQL → export rules
buildInsightsContextHarvested insights when contextMode === 'harvested'
buildSessionKnowledgeContextTables, paths, heuristics confirmed in this Inspector session
buildSemanticContextGoverned entities, dimensions, measures from semantic model (per org + connection)
FOER operating memory (optional)If MEMORY_INJECT_ENABLED and class inspector: phases in system prompt + synthetic assistant recall turn
Message historyFrom request body (client is source of truth for transcript)

Model routing: Bedrock ConverseStream via runAgentLoop, or OpenAI-compatible path via dispatchAgentLoop → runFoundryAgentLoop (Azure Foundry, xAI, Bedrock Mantle, LLM Lite). Optional Grok fallback when Bedrock fails and xAI credentials exist.

Agent loop

  1. Stream assistant text (and optional “thinking” on supported Anthropic models).
  2. Collect tool-use blocks from the stream.
  3. Execute tools in parallel (Promise.all).
  4. Append assistant message + tool results to the conversation.
  5. Repeat until the model returns text only, hits getInspectorMaxLoops(), aborts, or errors.

Abort: client AbortController → request.signal → abortSignal on the loop. In-flight tool calls are not cancelled mid-execution.

Tools & how analysis happens

Tools are defined in INSPECTOR_TOOLS / buildToolConfig in prompts.ts. All execution goes through executeInspectorTool.

ToolRole
describe_schema Search, describe, profile harvested catalog metadata (preferred in harvested mode)
execute_tool Read-only Databricks SQL via executeDatabricksSQL (service principal on connection)
emit_chart Chart DSL on the last query result in the turn → ECharts option
emit_semantic_chart Governed SemanticQuery → compile → execute → chart (with staged SSE progress)
emit_disambiguation Surface candidate fields as chips; model should end turn and wait for user pick
export_query_result CSV export (reuses last successful SQL per prompt rules)
Analysis model: There is no separate “analysis engine” service. Analysis is LLM reasoning + tools + prompts, with deterministic safety on SQL and semantic compilation.

Sub-pipelines inside tools

Semantic chart (emit_semantic_chart)

runSemanticChartPipeline in chart-pipeline.ts:

  1. Validate SemanticQuery
  2. Compile to SQL (src/lib/semantic/compiler.ts)
  3. Execute on Databricks (executeSemanticQuery)
  4. Profile rows, recommend chart kind, build ECharts option
  5. Emit semantic_chart_result SSE with trust metadata for TrustPanel

Raw chart (emit_chart)

Uses last query_result from the turn; validates Chart DSL (often from tool input); compiles to ECharts without requiring a second full agent loop when inline DSL is valid.

UI composition

InspectorShell brings together:

  • PromptCanvas — chat thread (shared with workbench)
  • DataStudio — grids and charts from queryResults
  • SemanticChartCard, DisambiguationCard, QueryProgressCard, ExportReadyCard
  • DashboardPane — pin SQL/charts to dashboards
  • SemanticGovernancePanel — drafts, promotion, catalog (right pane)
  • DeveloperPane — Agent Ops metrics (role-gated)
  • AgentHandoffCard — detect build-agent intent → Agent Lab

SSE event types consumed by useInspectorChat include: text, thinking, loop_start, tool_call_*, query_result, semantic_chart_result, semantic_disambiguation, export events, and done.

After each turn (same HTTP request)

Inspector chat is the richest harness. Typical side effects:

  • TurnMetricsRecorder → agent_turn_log + agent_loop_log
  • withAgentOpsToolLog → sampled tool_invocation_log
  • logAgentCost on completed/truncated turns
  • openSession trace → platform_trace_nodes / edges (FOER, UUID session)
  • Bandit observation + optional judge score
  • persistSessionKnowledgeAfterTurn
  • Memory injection attribution when bullets were used
  • Marcus reflection (env-gated)

Limits & non-goals

  • Not multi-agent orchestration (pipeline tables exist; no runtime in src/).
  • Not durable runs — no worker resumes a turn after disconnect or API restart.
  • policy_entry is not consulted by the loop (CRUD API only).
  • SQL runs as the connection service principal, not per-user warehouse identity; read-only enforcement is in execute.ts.
  • Session ownership on chat is observe mode unless INSPECTOR_AUTH_ENFORCE=true (see platform audit for auth gaps on session GET).
