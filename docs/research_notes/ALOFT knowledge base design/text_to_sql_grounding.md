# Text-to-SQL Grounding: How Analytics Copilots Structure and Retrieve Catalog Knowledge (2024 – Oct 2026)

Scope: what knowledge artifacts leading analytics copilots and text-to-SQL systems use (schema metadata, semantic models, verified queries, glossary, sample values, query history, lineage, instructions), how they retrieve them, and measured accuracy impact. Written for designing the "catalog knowledge" layer of an analytics agent platform over Databricks Unity Catalog.

Labeling convention used throughout: **[VENDOR]** = vendor-published claim or internal eval (not independently reproducible unless noted); **[INDEP]** = academic paper / public leaderboard / open reproducible benchmark; **[PROD]** = engineering case study from a company using its own system internally.

---

## 1. Databricks AI/BI Genie (Genie Agents, formerly Genie Spaces): knowledge store, instructions, example SQL, trusted assets, UC metadata, metric views, benchmarks, query history

### Takeaway
Genie layers an agent-scoped, curated "knowledge store" (descriptions, synonyms, joins, SQL expressions for measures/filters/dimensions, entity-matched values) on top of Unity Catalog metadata, and retrieves example SQL and metadata selectively per question; Databricks' own guidance ranks SQL expressions and example SQL above free-text instructions, and its worked example shows accuracy climbing from 0% to 100% on a 13-question benchmark as metadata, joins, value matching, example SQL, and instructions were added in that order.

### Cited Findings
- **Naming/date:** Genie Spaces were renamed "Genie Agents"; the setup doc was last updated Oct 9, 2026. — [Databricks: Create and manage a Genie Agent](https://docs.databricks.com/aws/en/genie-agents/set-up)
- **Limits:** data must be registered in Unity Catalog; up to **50 tables, views, or metric views** per Genie Agent; requires pro/serverless SQL warehouse; data access evaluated with each end user's own UC permissions. — [Databricks: Create and manage a Genie Agent](https://docs.databricks.com/aws/en/genie-agents/set-up)
- **Response-generation context components** (official table): UC table metadata (names, descriptions, defined PK/FK relationships); column names and descriptions ("Genie intelligently filters for relevant column names and descriptions"); knowledge store context; example SQL queries ("intelligently selects relevant SQL examples"); SQL functions (all added functions); plain-text general instructions; prompt/response history of current chat (oldest parts dropped under token limits). Genie also uses "sample values from selected columns." — [Azure Databricks: Genie Agents concepts](https://learn.microsoft.com/en-us/azure/databricks/genie-agents/concepts)
- **Knowledge store contents:** agent-level descriptions for tables/columns, business terms and synonyms; agent-level data customization (focused datasets without altering UC tables); **prompt matching** (format assistance + entity matching, incl. spelling correction); join relationships; SQL expressions for measures, filters, and dimensions. All scoped to the agent, not written back to UC. — [Databricks: Tune Genie Agent quality](https://docs.databricks.com/aws/en/genie-agents/tune-quality)
- **Knowledge-store quota:** max **200 knowledge store snippets** per agent; table descriptions, join relationships, and SQL expressions count; text instructions, example SQL, SQL functions, column descriptions, and prompt-matching settings do not. — [Databricks: Tune Genie Agent quality](https://docs.databricks.com/aws/en/genie-agents/tune-quality)
- **Entity matching (value retrieval):** curated lists of distinct values for up to **120 columns**, up to **1,024 distinct values per column**, each ≤127 chars; string columns only; stored in workspace storage bucket; auto-enabled for eligible columns; blocked on tables with row filters/column masks (and must be disabled for views over such tables / dynamic views). Example: lets Genie map "Florida" to `FL`. Docs claim entity matching "significantly improves Genie's accuracy" (no number given). — [Databricks: Tune Genie Agent quality](https://docs.databricks.com/aws/en/genie-agents/tune-quality)
- **Column hiding:** hiding a column removes it from Genie's context (doesn't affect UC permissions) — used to exclude duplicate/confusing columns. — [Databricks: Tune Genie Agent quality](https://docs.databricks.com/aws/en/genie-agents/tune-quality)
- **Joins from UC constraints:** "Primary and foreign keys defined in your schema are automatically saved as join relationships in the Genie Agent." — [Databricks: Tune Genie Agent quality](https://docs.databricks.com/aws/en/genie-agents/tune-quality)
- **Instruction-type hierarchy (official best practice):** use **SQL expressions** for common business terms (revenue, active_customers, gross_margin); use **complete example SQL** for complex/multi-part questions; use **text instructions only as a last resort**. "Too many instructions can reduce effectiveness, especially in longer conversations." — [Azure Databricks: Genie best practices](https://learn.microsoft.com/en-us/azure/databricks/genie/best-practices)
- **Example SQL retrieval:** title each example with "the most typical phrasing of the user's question" to improve prompt-to-example matching; Genie either uses the example directly or learns from it for similar questions; examples can be static or parameterized. — [Databricks: Tune Genie Agent quality](https://docs.databricks.com/aws/en/genie-agents/tune-quality)
- **Trusted assets / trust badge:** parameterized example SQL queries and UC SQL functions (scalar or table-valued); when the exact text of a parameterized query or a SQL function is used, the response is labeled **"Trusted"**; users can edit parameter values and rerun. Genie cannot view/modify the SQL inside a function body (useful for logic that should not be surfaced). Users need `EXECUTE` on functions. — [Azure Databricks: Add SQL examples and instructions](https://learn.microsoft.com/en-us/azure/databricks/genie/add-instructions); [Databricks: Tune Genie Agent quality](https://docs.databricks.com/aws/en/genie-agents/tune-quality)
- **Query history as a knowledge source:** when data assets are added, Genie "automatically searches for relevant popular workspace queries associated with those assets," using the author's credentials (CAN VIEW on queries). Suggestions appear in a review dialog with a prepopulated question title; authors Accept/Reject; accepted ones become editable example SQL. Write-only queries are excluded; queries on tables not in the agent are not suggested (so purpose-built views won't get suggestions if history runs against base tables). — [Databricks: Create and manage a Genie Agent](https://docs.databricks.com/aws/en/genie-agents/set-up)
- **Metric views:** UC metric views separate measure definitions from dimensions so a metric is defined once and grouped by any field at runtime; queryable from Genie Agents, dashboards, SQL, external BI tools; defined via SQL DDL/YAML with "agent metadata." A Genie Agent's configured context can be **exported as a metric view**. — [Databricks: Unity Catalog metric views](https://docs.databricks.com/aws/en/uc-semantics/metric-views/); [Databricks: Create and manage a Genie Agent](https://docs.databricks.com/aws/en/genie-agents/set-up)
- **Benchmarks:** test questions with expected SQL for evaluation only; "Genie does not use benchmark questions or SQL to improve its context." — [Databricks: Genie Agents concepts](https://docs.databricks.com/aws/en/genie-agents/concepts)
- **Agent mode:** multi-step reasoning mode that decomposes questions, runs multiple SQL queries, returns structured report; "Flash (Beta)" variant for quick answers. — [Databricks: Genie Agents concepts](https://docs.databricks.com/aws/en/genie-agents/concepts)
- **[VENDOR] Worked accuracy progression** (13 marketing benchmark questions): baseline with only data objects = 0/13 correct; after cleaning UC names/descriptions, single-table questions worked; after join keys, multi-table questions worked; after enabling example values / entity matching ">50%"; iterations 1–3 combined = **54%**; adding example SQL for custom metrics (e.g., CTR) = **77%** ("largest single accuracy improvement"; "One well-crafted example query often solves an entire category of benchmark gaps"); adding text instructions (global filters, domain definitions, fiscal calendar) = **100%**. Replacing base tables with a custom view/metric view kept 100%. Databricks says benchmarks should typically be **>80% before UAT**; recommends 10–20 benchmark questions authored by SMEs before development. — [Databricks Blog: How to Build Production-Ready Genie Spaces](https://www.databricks.com/blog/how-build-production-ready-genie-spaces-and-build-trust-along-way)

### Inferences
- Genie's design implies a **typed knowledge model** rather than one blob of "docs": (a) UC-native metadata (comments, PK/FK, tags), (b) agent-scoped overrides, (c) structured semantics (SQL expressions / metric views), (d) value indexes, (e) example SQL (retrieved), (f) small global instruction set (always in context). An ALOFT catalog layer over UC should mirror this typing so each artifact can have its own retrieval policy and quota.
- The 0→54→77→100% sequence (single vendor example, small n) suggests a sensible build order: metadata + joins + value matching first, then metric definitions/example SQL, then instructions.
- Query-history mining with human Accept/Reject is the native Databricks bootstrap for example SQL; ALOFT can reproduce it from `system.query.history` plus UC lineage, filtered to SELECTs on in-scope tables.

### Gaps
- No public independent benchmark of Genie accuracy; the 13-question progression is a single vendor demo.
- Databricks does not document Genie's internal retrieval algorithm (embedding vs keyword, top-k) for example SQL or column filtering.
- Did not find a Databricks product literally called "knowledge store" outside Genie; found no doc describing Genie automatically learning from thumbs-up feedback into examples (feedback → curation appears to be manual).

## 2. Snowflake Cortex Analyst: semantic model YAML / semantic views, Verified Query Repository (VQR), accuracy vs plain text-to-SQL

### Takeaway
Cortex Analyst grounds generation in a semantic model (now native "semantic views") with logical tables/columns, metrics, sample values, and a Verified Query Repository retrieved by semantic similarity; Snowflake reports roughly +20 points over vanilla LLM SQL on BIRD subsets and ~2× GPT-4o on an internal BI set — all vendor-run.

### Cited Findings
- **VQR structure:** `verified_queries` section in the semantic model YAML; each entry has `name`, `question`, `sql`, optional `verified_at` (epoch), `verified_by`, `use_as_onboarding_question`. Verified SQL must use **logical** table/column names from the semantic model (logical tables prefixed `__`), not physical names. "Invalid or inaccurate queries can negatively impact Cortex Analyst's performance and accuracy." When a question is similar to a VQR entry, Cortex Analyst uses it to generate SQL and the response shows which verified query was used. — [Snowflake Docs: Cortex Analyst Verified Query Repository](https://docs.snowflake.com/en/user-guide/views-semantic/verified-query-repository)
- **Retrieval/cost:** "The model gets access to verified queries only when the user's question is semantically similar, so they generally don't meaningfully increase token usage"; "The more the better — there's no meaningful upper limit"; start with 10–20 and add from real user questions; "suggestion panels … driven by query history and usage data." — [Snowflake: Best Practices for Semantic Views for Cortex Analyst](https://www.snowflake.com/en/developers/guides/best-practices-semantic-views-cortex-analyst/)
- **Evaluations:** VQs double as ground truth; Snowsight creates a temporary semantic view with the evaluated VQs removed (a VQ can guide runtime OR be ground truth, not both, to avoid leakage); reports accuracy (execution-result comparison), **regressions** (previously correct now failing), latency, per-query diff. Snowflake now recommends transitioning to Cortex Agents, which "supports every Cortex Analyst capability with higher answer quality." — [Snowflake Docs: Cortex Analyst evaluations](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-analyst-evaluations)
- **Literal (value) retrieval:** sample values for low-cardinality columns; for high-cardinality columns, integration with **Cortex Search** performs semantic search over column values to retrieve correct literals (private preview at the time of the post). Evaluation counted SQL correct only if literals exactly matched. — [Snowflake Engineering: Evaluating Text-to-SQL Accuracy for Real-World BI](https://www.snowflake.com/en/blog/engineering/cortex-analyst-text-to-sql-accuracy-bi/)
- **[VENDOR] Accuracy claims (internal eval):** Cortex Analyst "90%+ SQL accuracy on real-world use cases"; "nearly 2x as accurate as single-prompt SQL generation from GPT-4o and about 14% more accurate than other solutions on the market"; GPT-4o alone dropped to **51%** on their internal set despite 90%+ Spider 1.0 scores. Focus on dimensional (star/snowflake) models. — [Snowflake Engineering: Evaluating Text-to-SQL Accuracy for Real-World BI](https://www.snowflake.com/en/blog/engineering/cortex-analyst-text-to-sql-accuracy-bi/)
- **[VENDOR, on public BIRD data] Agentic semantic-model improvement:** same LLM (Claude 3.5 Sonnet) vanilla vs Cortex Analyst with auto-improved semantic model, LLM judge = Mistral Large 2: debit_card_specializing 52→83%, california_schools 63→80%, thrombosis_prediction 45→70%, toxicology 69→79%; **average 57% → 78% (+21 pts)**. — [Snowflake Engineering: Agentic Semantic Model Improvement](https://www.snowflake.com/en/blog/engineering/agentic-semantic-model-text-to-sql/)

### Inferences
- The VQR pattern (question + gold SQL in logical names + verified_by/verified_at provenance + onboarding flag) is a ready-made schema for ALOFT's "verified query" artifact; the leakage-safe hold-out evaluation (remove eval VQs from runtime context) is worth copying directly.
- Writing verified SQL against logical semantic names rather than physical columns decouples curated examples from schema churn.

### Gaps
- No independent third-party evaluation of Cortex Analyst found; the 57→78 BIRD numbers use an LLM judge, not pure execution match.
- Snowflake doesn't publish VQR retrieval top-k or embedding model.

## 3. Semantic layers and LLMs: dbt Semantic Layer / MetricFlow, Cube, AtScale, LookML + Gemini — evidence they raise accuracy

### Takeaway
Every published comparison finds semantic layers raise accuracy substantially on business-metric questions (data.world 16→54%, AtScale 20→92.5%, dbt 2026: ~84–90% text-to-SQL vs 98–100% SL on modeled data, Looker "up to two-thirds fewer errors"), but all are small (11–40 questions), mostly vendor-authored, and the gap is shrinking as LLMs improve; the most durable advantage is failure mode — semantic layers refuse rather than return plausible wrong numbers.

### Cited Findings
- **[INDEP-ish, vendor researchers, public benchmark] data.world (Nov 2023):** enterprise insurance schema (ACME Insurance), GPT-4 zero-shot on SQL = **16%** accuracy; over a knowledge graph (ontology + mappings, SPARQL) = **54%**. — [Sequeda, Allemang, Jacob, arXiv 2311.07509](https://arxiv.org/pdf/2311.07509); [data.world PDF](https://data.world/mstatic/assets/pdf/kg_llm_accuracy_benchmark_11132023_public.pdf)
- **[VENDOR, open-source & reproducible] dbt Labs 2026 rerun (Apr 7, 2026)** on the same ACME Insurance benchmark, 11 questions × 20 runs: on original normalized schema, text-to-SQL improved from **32.7% (GPT-4, 2023) → 64.5%** (Sonnet 4.6 and GPT-5.3 Codex); Semantic Layer overall **60.5% → 72.7%**, and **100%** on questions within SL scope (questions needing "too many hops" = 0% for SL — it errors instead of answering). After LLM-generated **3 extra dbt models**: Text-to-SQL 90.0% (Sonnet 4.6) / 84.1% (GPT-5.3 Codex) vs Semantic Layer **98.2% / 100%**. Reasoning effort barely mattered for SL; xhigh effort raised GPT latency from ~8s to >20s with no accuracy gain; Sonnet 4.6 beat Opus 4.6. Caveat (dbt's): text-to-SQL got the **entire schema** in context, impractical for large warehouses. Recommendation: SL for KPI/board-grade answers, fall back to text-to-SQL for ad hoc. "With text-to-SQL, failure looks like a plausible but incorrect answer. With the Semantic Layer, failure looks like an error message." — [dbt Developer Blog: Semantic Layer vs. Text-to-SQL 2026](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026); [dbt-llm-sl-bench historical](https://dbt-labs.github.io/dbt-llm-sl-bench/historical/)
- **[VENDOR, public question set] AtScale (Aug 2024):** TPC-DS, 40 questions in 4 complexity quadrants, Gemini Pro 1.5; control with schema + PK/FK + few-shot = **20%**; with AtScale semantic layer + query engine (3 retries on syntax errors) = **92.5%**. Quadrants: low-Q/low-S 60→100%, low-Q/high-S 10→100%, high-Q/low-S 10→100%, high-Q/high-S 0→70%. Benchmark published as a public leaderboard repo. — [AtScale blog](https://www.atscale.com/blog/enable-natural-language-prompting-with-semantic-layer-genai/); [AtScale whitepaper PDF](https://www.atscale.com/wp-content/uploads/2024/08/Enabling-NLP-with-AtScale-Semantic-Layer-and-GenAI.pdf); [NLQBenchmarks/TPCDS_Benchmark](https://github.com/nlqbenchmarks/tpcds_benchmark)
- **[VENDOR] Looker:** "internal testing has shown that Looker's semantic layer reduces data errors in gen AI natural language queries by as much as two thirds" (no methodology published). — [Google Cloud Blog: Looker semantic layer and gen AI](https://cloud.google.com/blog/products/business-intelligence/how-lookers-semantic-layer-enhances-gen-ai-trustworthiness)
- **[VENDOR] Snowflake** semantic model +21 pts average on four BIRD DBs (see §2). — [Snowflake Engineering](https://www.snowflake.com/en/blog/engineering/agentic-semantic-model-text-to-sql/)
- **[VENDOR] Databricks:** encapsulating calculations in a view/metric view preserved 100% on the 13-question benchmark and is preferable when "you have dozens of custom metrics." — [Databricks Blog](https://www.databricks.com/blog/how-build-production-ready-genie-spaces-and-build-trust-along-way)

### Inferences
- The gap between raw text-to-SQL and semantic layers has narrowed (dbt: 32.7%→64.5% raw, and 84–90% on modeled data) — modern LLMs reduce but do not eliminate the advantage; data **modeling** (wide, denormalized, well-named views) helps both paths.
- For ALOFT on UC: UC metric views are the native deterministic layer; a hybrid router ("can a metric view answer? → else text-to-SQL with retrieved context") matches dbt's recommendation and Genie's design.

### Gaps
- Found no published Cube accuracy benchmark (not searched deeply; budget). No independent (non-vendor) replication of AtScale's or Looker's numbers. All benchmarks are ≤40 questions — high variance.

## 4. Google (BigQuery/Looker Conversational Analytics), AWS (Amazon Q in QuickSight / Quick Sight), Microsoft (Fabric data agents / Power BI Copilot)

### Takeaway
All three hyperscalers converged on the same artifact set — descriptions + synonyms on fields, a business-logic model (LookML / Q Topics / Power BI semantic model), always-on instructions, and verified question→query pairs retrieved by similarity — with small curated pools (Looker recommends 30–50 verified queries; Fabric retrieves top-3 examples; Power BI uses 5–7 trigger phrasings per verified answer).

### Cited Findings
**Google**
- BigQuery data agents: knowledge sources = tables, views, graphs, UDFs (and Lakehouse tables); custom table/field metadata; instructions. — [Google Cloud: BigQuery Conversational analytics overview](https://docs.cloud.google.com/bigquery/docs/conversational-analytics)
- Conversational Analytics API context: for BigQuery, structured context fields — table/column descriptions, **synonyms, tags, example queries** — plus system instructions; context "can enable agents to cite sources." Verified queries a.k.a. **"golden queries"** = NL question paired with correct SQL or Looker query. — [Google Cloud: Conversational Analytics API FAQ](https://docs.cloud.google.com/gemini/data-agents/conversational-analytics-api/frequently-asked-questions)
- Looker: agent can query up to **5 Explores**; verified queries only for Explore data agents; no custom fields/pivots; "no limit … but we recommend including no more than **30 to 50** question-and-query pairs per agent." Admins can review user queries and feedback (Preview "End User CA Query Review"). — [Looker: Explore data agents](https://docs.cloud.google.cn/looker/docs/conversational-analytics-looker-data-agents); [Looker: Conversational Analytics overview](https://docs.cloud.google.com/looker/docs/conversational-analytics-overview)

**AWS**
- Quick Sight (formerly QuickSight) Q **Topics** are an index of definitions used to map terms to columns/values and power autocomplete; authors add friendly names, descriptions, **field synonyms and value synonyms** (e.g., `NW`→Northwest), semantic types/subtypes (currency, location, identifier...), and **named entities** (field groups like "Address"). Docs: synonyms "improves accuracy." — [AWS: Making topics natural-language-friendly](https://docs.aws.amazon.com/quick/latest/userguide/topics-natural-language.html); [AWS: Named entities](https://docs.aws.amazon.com/quicksight/latest/user/quicksight-q-topics-data-entities.html)
- **Reviewed answers** (verified Q→visual pairs) managed via API (`BatchCreateTopicReviewedAnswer`, max 100 per call; `ListTopicReviewedAnswers`). — [AWS API: BatchCreateTopicReviewedAnswer](https://docs.aws.amazon.com/quicksight/latest/APIReference/API_BatchCreateTopicReviewedAnswer.html)
- [PROD/AWS blog] Routing across 50+ Q topics: topic metadata (name, description, metrics, dimensions, sample questions) embedded (Titan Text Embeddings V2) into a Bedrock Knowledge Base; vector search with **domain metadata filters**, then a lightweight LLM selects the best topic — "retrieval-then-selection." — [AWS ML Blog: Conversational data assistant Part 2](https://aws.amazon.com/blogs/machine-learning/build-a-conversational-data-assistant-part-2-embedding-generative-business-intelligence-with-amazon-q-in-quicksight/)

**Microsoft**
- Power BI "Prep data for AI": **AI data schema** (subset of tables/columns/measures), **verified answers** (approved visual + trigger phrases), **AI instructions** (terminology, metric preferences, fiscal definitions, which table "Customers" means). Stored at semantic-model level, reused by any Fabric data agent on the model. With data agents, verified answers don't return the visual; their columns/measures/filters steer DAX generation; system checks exact or semantically similar match first. — [Microsoft Learn: Semantic model best practices for data agent](https://learn.microsoft.com/en-us/fabric/data-science/semantic-model-best-practices); [Power BI tutorial: Prepare semantic model for AI](https://learn.microsoft.com/en-us/power-bi/create-reports/tutorial-copilot-power-bi-prepare-model)
- Microsoft checklist: "Select only relevant tables, columns, and measures (very important)"; **5–7 complete trigger questions per verified answer**, formal + conversational; ≤3 filters; keep agent-level instructions to cross-source routing/format/abbreviations and "DO NOT add semantic model specific instructions at Data Agent level"; evaluate with Fabric Data Agent Python SDK against ground truth. — [microsoft/fabric-toolbox checklist](https://github.com/microsoft/fabric-toolbox/blob/main/samples/data_agent_checklist_notebooks/Semantic%20Model%20Data%20Agent%20Checklist.md)
- Fabric example queries (few-shot) for Lakehouse/Warehouse/KQL sources: tool "automatically looks up the most relevant example queries for the user's question and passes the **top three**"; each example validated against source schema; not supported for semantic-model sources. Recommended instruction template: Objective / Data sources (priority) / Key terminology / Response guidelines / Handling common topics. — [Microsoft Learn: Data agent configurations](https://learn.microsoft.com/en-us/fabric/data-science/data-agent-configurations); [Microsoft Learn: Data agent example queries](https://learn.microsoft.com/en-us/fabric/data-science/data-agent-example-queries)

### Inferences
- Common pattern: **two-tier instructions** (global agent/router instructions vs. dataset-/model-scoped instructions) and **scope-limited schemas** (explicitly select the subset). ALOFT should store instructions at the scope they apply to (catalog/schema/table/metric) and only inject the ones in-scope for the retrieved objects.
- Value synonyms (QuickSight) and entity matching (Genie) solve the same problem as CHESS's LSH value index (see §5).

### Gaps
- None of Google/AWS/Microsoft publish quantitative accuracy deltas for these features (except Looker's "two-thirds" claim). No independent benchmarks found.

## 5. Academic: schema linking and retrieval on BIRD, Spider 2.0, CHESS, DIN-SQL, MAC-SQL, CHASE-SQL; value retrieval; few-shot retrieval; what context matters most

### Takeaway
On academic benchmarks, selective retrieval of values and schema (not "dump everything") and execution-based revision are the measured winners (CHESS ablations: −4.8 pts without entity/context retrieval, −6.1 without table selection, −6.8 without revision); enterprise-scale benchmarks (Spider 2.0) show schema linking over ~800-column DBs, dialects, and multi-step planning were the bottlenecks — 2024 classic pipelines scored <6% there, while 2026 agentic systems report up to ~97% on Spider 2.0-Snow.

### Cited Findings
- **CHESS (Stanford, 2024)** [INDEP]: Information Retriever (keyword extraction → **LSH index over unique DB values** for syntactic/edit-distance matching + vector DB over catalog descriptions), Schema Selector (filter_column, select_tables, select_columns), Candidate Generator, Unit Tester. BIRD test **71.10%**, ~83% fewer LLM calls than leading proprietary method; Spider test 87.2%. Ablation on BIRD dev subsample: full ~64.6; w/o entity & context retrieval **59.86 (−4.76)**; w/o filter_column −2.72; w/o select_tables **−6.12**; w/o select_columns −5.44; w/o revise **−6.80**. On a synthetic 4,337-column schema, schema selector gave +2% accuracy and **~5× fewer tokens**; "overloading the LLM context with redundant information can degrade its performance." Schema linking "unnecessary for small databases within BIRD" with long-context models. — [CHESS arXiv 2405.16755v3](https://arxiv.org/html/2405.16755v3); [CHESS GitHub](https://github.com/ShayanTalaei/CHESS)
- **Spider 2.0 (Nov 2024; ICLR 2025)** [INDEP]: 632 enterprise workflow tasks; DBs from real apps (Google Analytics, Salesforce), avg **812 columns**, BigQuery/Snowflake/etc., avg 144 tokens per gold SQL, 85.98% need dialect-specific functions. 2024 results: best o1-preview code agent **21.3%**; Spider 2.0-lite best parser 5.7% vs 91.2% Spider 1.0 and 73.0% BIRD. Baselines on lite: DIN-SQL+GPT-4o 1.46%, DAIL-SQL+GPT-4o 5.68%, CHESS+GPT-4o 3.84% (Snow: 0.00 / 2.20 / 1.28%). Error analysis: **wrong schema linking 27.6%** (column 16.6%, table 10.1%); Spider 2.0-lite has >755 columns/DB vs ~54 in BIRD; nested columns are hard. Oracle function docs gave only slight gain (DAIL-SQL+GPT-4o 5.68→5.85%); manually selected few-shot 0/1/3-shot = 5.68/6.40/6.76% — **few-shot from unrelated DBs helps little at enterprise scale**. — [Spider 2.0 arXiv 2411.07763](https://arxiv.org/html/2411.07763v2)
- **Leaderboards as of Oct 2026** [INDEP, self-reported submissions]: BIRD test EX (with oracle "evidence" knowledge) top = GrainSQL **82.95%** (Sep 26, 2026), DataGallery 82.39%, SiriusAI 82.28%, AskData+GPT-4o (AT&T) 81.95%, Agentar-Scale-SQL 81.67%; CHASE-SQL+Gemini **76.02%**; human 92.96%; plain Claude Opus 4.6 baseline 70.15%. AskData's earlier entry **without** oracle knowledge = 67.41% (Nov 2024) — not a clean ablation (different system versions). — [BIRD-bench leaderboard](https://bird-bench.github.io/)
- Spider 2.0-Snow leaderboard (547 Snowflake tasks): Genloop Sentinel Agent v2 Pro **96.70** (Mar 2026), Native mini 96.53, QUVI-3+Gemini-3-pro 94.15, TCDataAgent-SQL 93.97; ReFoRCE+o3 62.89; Spider-Agent+Claude-Sonnet-4.5 41.86. — [BenchmarkList: Spider 2.0](https://benchmarklist.com/benchmarks/spider_2_0/) (aggregator; corroborated by [nl2sql.ai](https://www.nl2sql.ai/news/bird-spider2-leaders-unchanged-new-submissions) and [classicdba.com](https://classicdba.com/generative-ai/text-to-sql-scores-on-spider-20-in-october-2026-why-967-is-not-solved-and-what-a-dba-should-test-instead)). Note: BIRD and Spider 2.0-Snow scores are not comparable. — [nl2sql.ai](https://www.nl2sql.ai/news/bird-spider2-leaders-unchanged-new-submissions)
- **Source-quality warning:** an aggregator ([awesomeagents.ai](https://awesomeagents.ai/leaderboards/text-to-sql-leaderboard/)) lists "CHESS Agent (GPT-5 backbone) 35.2% Spider 2.0" etc.; these numbers do not match the official BIRD board and look unreliable — do not cite.
- Snowflake on benchmark gap: GPT-4o hit 90%+ on Spider 1.0 but 51% on Snowflake's internal BI set; time-series and messy schemas underrepresented in academic benchmarks. — [Snowflake Engineering](https://www.snowflake.com/en/blog/engineering/cortex-analyst-text-to-sql-accuracy-bi/)

### Inferences
- What context matters most, ranked by evidence: (1) **correct schema subset** (table selection is the largest single CHESS component; schema linking is the #1 Spider 2.0 error class); (2) **value grounding** (LSH/entity matching; every vendor ships it); (3) **business definitions/evidence** (BIRD "oracle knowledge" setting and all semantic-layer studies); (4) **execution feedback/revision**; (5) **in-domain examples** — generic few-shot barely helps on Spider 2.0, whereas in-domain verified queries help a lot in vendor tools (§1, §2, §6).
- With today's long-context models, pruning matters less for small schemas but still matters for thousands of columns — for accuracy and ~5× token cost.

### Gaps
- Did not fetch primary DIN-SQL, MAC-SQL, CHASE-SQL papers for their own ablations (budget); CHASE-SQL figure here is only its BIRD leaderboard entry (76.02%). Top 2026 Spider 2.0-Snow systems are mostly closed/undocumented, so their knowledge techniques are unknown.

## 6. Open source: Vanna.ai, WrenAI (MDL), Dataherald, LangChain SQL agents

### Takeaway
Open-source tools split into RAG-over-artifacts (Vanna: DDL + docs + question-SQL pairs in a vector store) and semantic-layer-first (WrenAI: YAML MDL models/relationships/metrics + instructions + a memory of successful NL→SQL pairs); both treat stored successful question-SQL pairs as the main self-improving asset.

### Cited Findings
- **Vanna:** "train" on DDL (`vn.train(ddl=...)`), documentation, SQL examples / question-SQL pairs; stores in a vector DB, retrieves most relevant per question. Its Aug 2023 study compared schema-only vs static examples vs **contextually relevant examples** (10 most relevant of 30 stored examples) — "accuracy rates skyrocket"; "We can improve performance even more by maintaining a history of SQL statements that were executable and correctly answer actual questions." — [Vanna paper (GitHub)](https://github.com/vanna-ai/vanna/blob/main/papers/ai-sql-accuracy-2023-08-17.md) (headline ~3% schema-only vs ~80% with relevant examples is reported in a search-engine summary of this paper; full text didn't load in my fetch — verify before citing exact numbers).
- Vanna 2.0 (late 2025) added identity, row-level security, audit logging; main OSS repo reportedly **archived read-only Mar 29, 2026** as the project shifted commercial. — [Querio: Wren AI vs Vanna AI](https://querio.ai/articles/wren-ai-vs-vanna-ai-open-source-text-to-sql-compared) (third-party; unverified against GitHub).
- **WrenAI:** MDL = YAML under `models/`, `views/`, `relationships.yml`, plus `instructions.md`, compiled to `target/mdl.json`; agent queries model names, not raw tables. Agent loop: `wren memory fetch` (relevant tables/columns) → `wren memory recall` (similar past queries) → write SQL on semantic layer → execute via Wren engine → `wren memory store` (save successful NL-SQL pairs). Scaffolding introspects schema, detects relationships, and asks a human about ambiguous FKs/canonical tables. — [WrenAI quickstart](https://github.com/Canner/WrenAI/blob/5fd88706/docs/core/get_started/quickstart.md); [WrenAI model guide](https://github.com/Canner/WrenAI/blob/c36e56eb/docs/core/guides/model.md)

### Inferences
- WrenAI's "store successful pairs automatically" is an unreviewed feedback loop; contrast with Genie/Snowflake, which require human acceptance. ALOFT should distinguish *candidate* (auto-captured) from *verified* (human-approved) pairs and weight retrieval accordingly.

### Gaps
- Dataherald and LangChain SQL agents not researched within budget (LangChain's SQL agent is generally a tool loop: list tables → get schema → query → check; no accuracy data gathered). No independent accuracy benchmark for Vanna or WrenAI found.

## 7. Very large catalogs (thousands to 100K+ tables): table retrieval, hierarchical narrowing, popularity from query logs

### Takeaway
Production systems at scale don't rely on flat embedding search over table descriptions: they narrow by domain first (Uber workspaces + intent agent; AWS domain-filtered topic retrieval), retrieve tables and historical queries jointly, and re-rank with trust/popularity signals mined from query logs (Pinterest: tier, freshness, doc quality, co-occurrence, query success rate), often with a human confirming the table list.

### Cited Findings
- **[PROD] Uber QueryGPT:** "workspaces" = curated collections of SQL samples + tables per business domain (11 system workspaces, e.g., Mobility, Ads, Core Services; plus custom workspaces). **Intent agent** (LLM) maps the question to workspaces — "drastically narrow[s] the search radius for RAG." **Table agent** proposes tables, user ACKs or edits. **Column prune agent** removes irrelevant columns — fixed intermittent 128K-token overflows and "massively improved" cost/latency. — [Uber Engineering: QueryGPT](https://www.uber.com/us/en/blog/query-gpt/)
- **[PROD] Pinterest v1 (Querybook):** schema = table name/description + column name/type/description; unique values of **low-cardinality columns** injected (`'WEB'` not `'web'`); context-limit tactics: reduced schema (name+type only), tag-based column pruning; table discovery via offline embeddings of **table summaries and historical queries**, top-N similarity, LLM re-rank to top-K, user confirmation. — [Pinterest Engineering: How we built Text-to-SQL](https://medium.com/pinterest-engineering/how-we-built-text-to-sql-at-pinterest-30bad30dabff); [Dot summary](https://www.getdot.ai/blog/pinterest-text-to-sql-querybook)
- **[PROD] Pinterest Analytics Agent (2025–26):** >100,000 analytical tables, 2,500+ analysts; governance cut ~400K→~100K tables with **Tier 1/2/3** tiering. "Unified context-intent embeddings" index **historical queries by the analytical intent they answer**. Extracts from query history: join patterns/keys, filters, aggregation logic, **table co-occurrence frequency**, success rates (patterns with "98%+ success rate, high monthly usage" prioritized). **Governance-aware ranking** fuses similarity with tier, freshness, ownership, documentation completeness. "Asset-first": surface existing trusted tables/queries/dashboards/metrics before generating new SQL. Hybrid vector + metadata-filter search ("similar to user_actions AND Tier 1 AND contains impression data"); millions of embeddings, daily incremental updates. Generation validates against catalog, uses column profiling for literal values, runs EXPLAIN before EXECUTE with bounded retries, LIMIT ≤100, returns SQL, tables, sources, confidence warnings. Adoption: 40% of analysts in two months; #1 internal agent (10× next). Benchmark: table discovery "meets expectations," SQL generation "has room for improvement"; stale patterns from deprecated tables are a failure mode. — [Pinterest Engineering: Unified Context-Intent Embeddings](https://medium.com/pinterest-engineering/unified-context-intent-embeddings-for-scalable-text-to-sql-793635e60aac)
- **[PROD] Pinterest documentation bootstrap:** LLM-drafted table descriptions using lineage + query context reduced manual doc effort ~40%, >75% rated "usable" or better; **glossary term propagation** via a column join graph from query logs auto-tagged >40% of in-scope columns; total manual documentation work down ~70%; humans in loop for Tier-1, "LLMs draft, humans review" for Tier-2; AI docs marked as such. — [Pinterest Engineering](https://medium.com/pinterest-engineering/unified-context-intent-embeddings-for-scalable-text-to-sql-793635e60aac)
- **[PROD/AWS]** retrieval-then-selection over 50+ Q topics with domain filters (see §4). — [AWS ML Blog](https://aws.amazon.com/blogs/machine-learning/build-a-conversational-data-assistant-part-2-embedding-generative-business-intelligence-with-amazon-q-in-quicksight/)
- Vendor scoping caps: Genie ≤50 tables/agent; Looker ≤5 Explores/agent — vendors handle scale by forcing curated scopes rather than catalog-wide retrieval. — [Databricks](https://docs.databricks.com/aws/en/genie-agents/set-up); [Looker](https://docs.cloud.google.com/looker/docs/conversational-analytics-overview)
- [INDEP] CHESS schema selector on 4,337 columns: +2% accuracy, ~5× fewer tokens. — [CHESS](https://arxiv.org/html/2405.16755v3)

### Inferences
- A UC-native design maps naturally to hierarchical narrowing: domain/workspace (or UC catalog/schema + tags) → table retrieval (hybrid: embedding over table summaries + historical-query intents, filtered by tags/tier) → re-rank with popularity from `system.query.history`, lineage co-occurrence, freshness, certification tags → column pruning → value lookup.
- Query history is the single richest signal at scale (joins, filters, popularity, gold SQL), but needs staleness handling (deprecated tables).

### Gaps
- No public recall@k numbers for table retrieval from Uber or Pinterest. Found no published hierarchical catalog→schema→table retrieval ablation specifically; the hierarchy evidence is architectural, not measured.

## 8. Feedback loops: thumbs-up → verified queries, human curation workflows, trust badges

### Takeaway
Vendors make human-in-the-loop curation the gate: usage/query history and feedback produce *suggestions*; an author accepts them into verified/trusted sets; answers built from verified assets get a visible badge or source citation; and verified sets double as regression test suites (with hold-out to avoid leakage).

### Cited Findings
- **Genie:** popular workspace queries suggested → author Accept/Reject → editable example SQL; "Trusted" label when a parameterized example or UC function is used; authors can view generated SQL. Benchmarks are eval-only. — [Databricks: Set up](https://docs.databricks.com/aws/en/genie-agents/set-up); [Azure Databricks: Add instructions](https://learn.microsoft.com/en-us/azure/databricks/genie/add-instructions)
- **Snowflake:** VQR entries carry `verified_by`/`verified_at`; responses show which verified query was used; "suggestion panels … driven by query history and usage data" and "feedback loops to add verified queries from real usage data"; evaluations track **regressions**. — [Snowflake VQR docs](https://docs.snowflake.com/en/user-guide/views-semantic/verified-query-repository); [Snowflake best practices](https://www.snowflake.com/en/developers/guides/best-practices-semantic-views-cortex-analyst/); [Snowflake evaluations](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-analyst-evaluations)
- **Looker:** admin review of user queries and feedback (Preview, consent-gated) in System Activity. — [Looker overview](https://docs.cloud.google.com/looker/docs/conversational-analytics-overview)
- **Power BI:** Copilot proposes trigger-phrase suggestions for a verified answer from the visual; author edits/applies. — [Power BI tutorial](https://learn.microsoft.com/en-us/power-bi/create-reports/tutorial-copilot-power-bi-prepare-model)
- **AWS:** reviewed answers as curated Q→visual pairs via API. — [AWS API](https://docs.aws.amazon.com/quicksight/latest/APIReference/API_BatchCreateTopicReviewedAnswer.html)
- **WrenAI:** auto-stores successful NL-SQL pairs into memory (no review gate in quickstart). — [WrenAI quickstart](https://github.com/Canner/WrenAI/blob/5fd88706/docs/core/get_started/quickstart.md)
- **Pinterest:** responses return SQL, tables, date ranges, source references, confidence warnings; AI-generated docs labeled and routed to owners for review. — [Pinterest Engineering](https://medium.com/pinterest-engineering/unified-context-intent-embeddings-for-scalable-text-to-sql-793635e60aac)
- **dbt:** a semantic-layer miss is an explicit error rather than a wrong answer — a built-in trust signal. — [dbt blog](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)

### Inferences
- Suggested ALOFT lifecycle: captured (auto, from thumbs-up or successful runs) → candidate (dedupe, re-execute, check tables still live) → verified (human approval, provenance) → benchmark (held out). Show a "Verified" badge only when the answer came from a verified asset or a metric view.

### Gaps
- No vendor publishes measured accuracy gains from feedback loops specifically. No evidence found of fully automatic thumbs-up → trusted promotion in Genie, Cortex, Looker, or Fabric; all documented paths need a human step.
