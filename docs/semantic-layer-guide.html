Semantic Layer — End-to-End Guide

A complete, plain-English guide: build the layer, govern it, use it in production, and improve it over time. The same content is inlined on architecture-guide.html → Semantic Layer (run node scripts/embed-semantic-guide.mjs after editing this file).

Complete playbook — proper order

How to read this guide:
  1. Work through phases 1–12 below (each box = one step, who does it, what changes in the DB).
  2. Then Status & governance for draft → governed rules.
  3. Then Inspector & dashboards for how users consume metrics.
  4. Use Glossary when a term is unclear.

Think of the semantic layer as a loop, not a one-time project: harvest context → author metrics → review → promote → use in chat and dashboards → improve from feedback. Each phase below says who acts, what to do, and what appears in Aurora.

1

Prerequisites — connections and organization

Who: Platform admin / cloud team

  • Purpose: Nothing semantic can run without a warehouse connection and an org row in Aurora.
  • Do: Configure Databricks OAuth M2M (DATABRICKS_*), Aurora (DATABASE_URL), and user login (Entra).
  • Result: Inspector can resolve a connection; APIs use getDefaultOrg() for your tenant.
  • Not this step: No metrics exist yet — that is phase 3–5.
2

Harvest the Data Estate (context, not governance)

Who: Data engineer or steward — Agent Lab → Estate → Jobs / Sources

  • Purpose: Inventory tables, profile columns, and generate AI descriptions so humans (and Inspector) understand the warehouse.
  • Pipeline order (typical): change_detect (optional) → T0 t0_structural → T1 t1_profile → T2 t2_semantic (LLM cards) → embed (vectors for catalog search). T3 usage (t3_usage) is separate and source-wide. See Context pipeline T0–T4.
  • Yes, T2 exists: job kind t2_semantic stamps last_t2_at and writes object/column semantic JSON — this is enrichment, not governed metrics.
  • T3 naming: Inspector docs sometimes call embeddings “T3”; in code, T3 = usage/lineage (t3_usage, live). t3_connected is listed in the UI but not implemented in orchestrator.ts yet.
  • Storage: platform_context_* — not platform_sem_*.
  • Advantage: Mapper, estate briefing, and describe_schema in Inspector get accurate metadata without stewards typing every column.
  • Example: After T2, object marine.gold.inspections has a semantic summary card stewards can confirm via confirm-semantic (trust on descriptions only).
3

Obtain a semantic model (container in Aurora)

Who: Admin or automated bootstrap (when T4 works)

  • Purpose: All entities/measures hang off platform_semantic_models.id.
  • Intended path: T4 t4_scan → t4_entity_propose → t4_dim_propose writes candidate rows (source_type=auto_bootstrap). Diagrams + detail: T4 visual guide.
  • Today in this repo: T4 orchestrator jobs fail (handlers not shipped). Existing DBs may still contain data from an earlier T4 deployment.
  • Check: GET /api/inspector/semantic/models returns at least one model; Inspector Semantic tab uses /candidates.
4

Map and align (optional but valuable)

Who: Data steward — /agent-lab/estate/mapper

  • Purpose: Link columns across sources so joins and lineage make business sense.
  • Do: Review proposed mappings; accept or correct.
  • Feeds semantic layer: Informs stewards when defining entities/joins; does not auto-promote measures.
  • Detail: Manual schema-pair launch + steward confirm; not on EventBridge. Full guide: context-harvesting → Mapper. Table-level silos: Silo Scan.
5

Author definitions (build the layer)

Who: Analyst or steward — Inspector “Define metric”, Metrics catalog, or graduate from a chart

  • Purpose: Create business metrics and dimensions tied to real columns.
  • API: POST …/drafts → rows in platform_sem_measures or platform_sem_dimensions with draft, created_by = you.
  • Fields that matter: label, column, aggregate, synonyms, nl_intent (“what question does this answer?”).
  • Side effect: upsertIntentEmbedding stores NL text for search/disambiguation.
  • Example: Draft measure “Open defects” = COUNT(defect_id) on entity Inspections, intent “How many open defects per vessel?”
6

Preview before sharing (authoring mode)

Who: Same author as the draft

  • Purpose: Run the metric on real Databricks data while still private.
  • API: POST …/authoring-preview with SemanticQuery; server sets authoringMode + your user id only.
  • Rules: You may reference your drafts; never another user’s drafts (SemanticDraftAccessError).
  • UI: Define Metric panel chart preview; results may show “Draft — not governed”.
7

Submit for governance (draft → candidate)

Who: Owner of the draft only

  • Purpose: Make work visible to the org for review — not yet “official.”
  • API: POST …/submit with definition IDs you own.
  • Gate: No reputation required to submit. T4/system rows (created_by null) cannot be submitted until a human owns them.
  • Visibility: Appears in GET …/review and Metrics catalog (Govern lens).
8

Review and promote (candidate → governed)

Who: Admin, or author with enough semantic_authoring reputation

  • Purpose: Mark definitions as governed — the production contract.
  • API: POST …/promote — runs evaluatePromotionEligibility.
  • Promotion gate: Admin always OK; else streetCred ≥ 80 self-approve, or quorum sum ≥ 120 / admin approver. Day one: empty reputation → effectively admin-only.
  • Entity rule: Promoting a measure requires its parent entity to already be governed.
  • Audit: platform_sem_audit row; creditAuthoringPromotion if MEMORY_REPUTATION_ENABLED=true.
  • Model status: recalculateModelStatus may set model to governed when any entity is governed.
9

Use in production (consume governed definitions)

Who: All analysts with Inspector / dashboard access

  • Inspector chat: buildSemanticContext injects governed catalog into prompt → agent calls emit_semantic_chart with IDs → chart-pipeline + executeSemanticQuery (model must be governed).
  • Dashboards: Widget picker GET …/definitions (no drafts) → widget stores SemanticQuery → viewers hit POST …/dashboards/[id]/data (no authoring bypass).
  • Guided builder: NL dashboard outline (Intent → Blueprint → Drill-in). LLM proposes chart specs; blueprint-ground.ts enforces catalog IDs — see Guided blueprint tab.
  • Advantage: Same measure id → same SQL → same number in chat and on the dashboard.
10

Operate and change safely (after govern)

Who: Steward with edit rights; admins for others’ rows

  • Edit governed defs: PATCH …/definitions/[id] — decideEditGate (admin or self-approve).
  • Computation changes: Editing formula-like fields can demote to candidate (forceDemotion) so numbers are re-reviewed.
  • Archive: Retire bad metrics; excluded from queries.
  • Lineage: GET /api/inspector/semantic/lineage shows dashboards consuming a measure before you change it.
11

Continuous improvement — how the layer gets better over time

Who: Users, stewards, and background jobs together

  • Disambiguation in Inspector: When the agent is unsure (“revenue” matches several measures), it calls a disambiguation tool; user picks a chip → follow-up query uses the right governed id. Teaches the session; reduces wrong charts.
  • NL intents + embeddings: Every nl_intent on drafts/governed defs is embedded; resolve-intent and disambiguation-rank get better at matching questions to metrics. Backfill: scripts/backfill-nl-intent-embeddings.ts.
  • Reputation loop: Successful promotions credit authors in semantic_authoring (CONTRIBUTED). Higher streetCred → self-approve future promotions → faster iteration without losing control.
  • Teach mode (related): Personal rules in FOER can be promoted to org with the same promotion gate; credits same reputation domain — aligns “what the org knows” with semantic governance.
  • Estate refresh: Re-harvest (T0/T1/T2) when schemas change; change_detect jobs keep context fresh so stewards do not govern against stale column lists.
  • confirm-semantic on estate cards: Stewards certify AI descriptions → better mapper/authoring decisions (trust signal, not metric promotion).
  • Audit + contributions UI: my-contributions, per-model contributions — transparency for who improved the catalog.
  • Future: T4 bootstrap when ported; optional applyMetricViews to publish governed SQL to Databricks spinor_semantic for external BI.
12

Close the loop (repeat)

Who: Whole team

  • New business questions → new drafts or synonyms on existing measures.
  • Wrong answers → fix definition or add disambiguation; check lineage for downstream dashboards.
  • Schema changes → harvest → review entities → update joins/measures → re-promote if demoted.

Continuous improvement loop (diagram)

Harvest (T0–T2) ──► Steward authors drafts ──► Preview ──► Submit ──► Promote (governed) │ │ │ ▼ └──────────── Schema / estate refresh ◄──── Use (Inspector + dashboards) ▲ │ │ ▼ Lineage + audit ◄──── Improve (intents, disambiguation, rep, teach, PATCH)
Summary: You build in phases 5–6 (drafts), govern in 7–8 (submit/promote), use in phase 9, and improve continuously in 10–12 via feedback, embeddings, reputation, re-harvest, and controlled edits.

Overview

What is the semantic layer? (one sentence)

It is the official dictionary of your business numbers — stored in Aurora — so when someone asks for “revenue” or “deficiencies per vessel,” the app uses one approved definition and turns it into safe SQL on Databricks.

What problem does it solve?

Without a semantic layer, every analyst and every AI answer writes its own SQL. Two dashboards both labeled “Revenue” can use different filters, joins, or columns. The semantic layer fixes that by storing named metrics and dimensions with owners, review, and audit — then Inspector and dashboards must use those IDs instead of inventing SQL.

Advantages (why we built it this way)

  • One version of the truth — promoted (governed) metrics are what production chat and dashboards use.
  • Safer than raw SQL from the AI — the agent sends a structured SemanticQuery; the app compiles SQL with join rules and blocks dangerous expressions.
  • Human workflow — draft → submit → promote fits data stewards; reputation and admin override match FOER governance.
  • Natural language alignment — synonyms and nl_intent plus embeddings help match questions to the right metric.
  • Traceability — platform_sem_audit records who changed status; lineage shows which dashboards use a measure.

Plain analogy

Harvester = walking the warehouse with a clipboard (what tables exist, column types, AI descriptions).
Semantic layer = the signed metric catalog on the wall (“Revenue = SUM(net_amount) on orders, exclude refunds”).
Databricks = the factory floor where the actual data lives; we only send compiled SQL there to read it.
Important distinction: ALOFT’s semantic definitions live in Aurora (platform_sem_*). They are not the same as Databricks Unity Catalog “metric views,” and they are not created by the harvester alone.

System of record

Aurora PostgreSQL: models, entities, dimensions, measures, joins, audit, NL intent embeddings.

Execution plane

Databricks runs the SQL the app compiles. Data never moves into Aurora for analytics.

Who uses it

Inspector (chat + charts), dashboard widgets, metrics catalog, guided dashboard blueprint.

Reading queries: production users never send raw SQL for governed analytics; they (or the agent) send IDs. Building metrics: stewards use the UI ladder below before numbers appear in chat.

Worked example — Inspector question

User: “Total open defects by flag this year.”
Agent builds SemanticQuery: entity = Inspections, measure = Open Defect Count (id meas_abc), dimension = Flag (dim_flag), filter = status = open, time grain = year.
App checks model is governed, compiles SQL like SELECT flag, SUM(...) AS open_defect_count FROM catalog.schema.inspections WHERE ... GROUP BY flag, runs on Databricks.
Chart reads column open_defect_count (from toAlias of the measure label) — not the display name “Open Defect Count”.

platform_semantic_models

Definition
The top-level container for one org’s semantic world (often one per business domain).
Purpose
Dashboards and Inspector bind to a model; status summarizes whether anything is officially governed yet.

Model “Marine operations” with source_type=auto_bootstrap after T4 (when enabled).

platform_sem_entities

Definition
One business table or view, identified by full_path (catalog.schema.table).
Purpose
Anchor for dimensions and measures; compiler uses this path in the FROM clause.
Example
full_path = marine.gold.inspections, label “Inspections.”

platform_sem_measures & platform_sem_dimensions

Definition
Measures = numbers you aggregate (sum, count, …). Dimensions = attributes you group or filter by.
Purpose
These are the IDs the agent puts in SemanticQuery.
Example
Measure “Revenue” = SUM(net_amount). Dimension “Vessel” = column vessel_id.
Advantage
Synonyms let “sales” and “revenue” map to the same governed measure in NL search.

Guided dashboard blueprint

The guided builder is an NL-first path to designing a dashboard on top of the semantic layer. It lives in the dashboard builder (components/inspector/dashboard-builder/guided/*), not in Inspector chat. Blueprint is stage 2: a reviewable outline of 4–6 proposed charts before any widgets are pinned or queries run at scale.

One sentence: You state the business decision the dashboard should answer; the platform resolves terms against the catalog, proposes a storyboard of charts, grounds every field id server-side, then you curate and drill in to live widgets.

Why it exists (value)

  • Speed — First layout from one question instead of adding widgets one by one.
  • Governance — Charts reference catalog measure/dimension ids; invented ids cannot survive grounding.
  • Transparency — Each card has a rationale; missing metrics surface as “define it” rows, not silent wrong SQL.
  • Separation from chat — Inspector chat explores (SQL, tools, many agent loops). Blueprint authors a governed dashboard spec.

Context pipeline T0–T4 — architecture & depth

The context harvester (Data Estate) builds a searchable catalog in Aurora from Databricks. It feeds Inspector, Mapper, and (when enabled) semantic bootstrap — but it is not the governed semantic layer (platform_sem_*). Full estate UI detail: context-harvesting-guide.html. Example rows per tier + T4 output: Sample data atlas.

Which tables get harvested / bootstrapped? Start with source scope_include / scope_exclude (permanent fence), then optional per-job includePatterns / excludeSchemas on Estate Jobs. Plain-English guide + curated_db.addressable_market example: context-harvesting-guide → Source scope.
Quick answers:
  • Do we have T2? Yes — job t2_semantic in src/lib/context/enrich.ts (Bedrock Sonnet describes tables/columns).
  • Do we have T3? t3_usage is implemented (weekly cron + Jobs); see context-harvesting → T3. t3_connected is UI-only — use t3_usage.
  • Embeddings? Separate job embed — often documented as “search tier”; writes platform_context_embeddings. Implemented in orchestrator; uses Azure text-embedding-3-large (not warehouse SQL).

What it does

Purpose

How

T4 — how the semantic layer gets built (visual guide)

Start here: One-minute story → click layers & diagram boxes for details → sample data atlas → steps below.
In one minute: Harvesting (T0–T2) writes a catalog in Aurora (“what tables exist and what columns mean”). T4 is an automated job that reads that catalog, asks an LLM (Bedrock) to propose official metric definitions, and saves them as candidate rows in the semantic layer. Stewards then promote the good ones to governed so Inspector and dashboards can use them safely. T4 does not run SQL for end users — it only creates metadata in PostgreSQL.

3. Three job kinds — coordinator tree

┌─ t4_scan ─────────────────────────────────────────────────────────────┐ │ Coordinator: one run per org/source launch (--kind t4_scan) │ │ • Advisory lock: ctx-orch:{orgId}:t4_scan (no overlapping scans) │ │ • Select eligible context objects (T2 done; incremental: last_t4_at) │ │ • Group tables by catalog.schema → enqueue t4_entity_propose children │ │ • Stats on parent job: clusters_enqueued, tables_total, … │ └───────────────────────────────┬───────────────────────────────────────┘ │ parent_job_id = scan.id ┌───────────────────────┴───────────────────────┐ ▼ t4_entity_propose (per schema cluster) │ │ scope.cluster_catalog, scope.cluster_schema │ │ • Bedrock: cluster tables → business entities │ │ • INSERT platform_sem_entities (candidate, created_by NULL) │ │ • INSERT platform_sem_joins (join_on_sql between entities) │ │ • Enqueue t4_dim_propose per table in cluster │ │ • Stats: entities_proposed, joins_proposed │ └───────────────────────┬───────────────────────┘ │ parent_job_id = entity_propose.id ▼ t4_dim_propose (per table) │ scope.context_object_id → platform_context_objects.id │ │ • Resolve full_path → entity row in platform_sem_entities │ │ • Bedrock: propose dimensions + measures from T2 card + profiles │ │ • INSERT platform_sem_dimensions / platform_sem_measures (candidate) │ │ • Stats: dimensions_written, measures_written │ │ • SET platform_context_objects.last_t4_at = now() │

4. Step A — t4_scan (getting / selecting tables)

Scan phase (plain English)

Trigger
EventBridge aloft-t4-semantic-bootstrap-weekly (Sunday 08:00 UTC), Agent Lab → Jobs → Run T4 Entity Scan, or POST …/context/jobs/launch with kind: t4_scan. reharvest-all enqueues a source-wide scan after T2 (not per-object scope).
What it reads
platform_context_objects (+ columns, profiles, T2 semantic JSON) for the org’s active source(s). Does not re-introspect Databricks for structure if T0 already ran.
Eligibility
Objects with last_t2_at set; incremental runs prefer objects where T4 is stale or missing (last_t4_at null or older than T2 refresh — exact filter lives in scanEstate in the ported handler).
What it writes
Child job rows (t4_entity_propose) with parent_job_id pointing at the scan job. Coordinator may ensure a platform_semantic_models row exists (name e.g. “Auto-Bootstrap Model”, source_type=auto_bootstrap, often status=candidate until promoted).
Concurrency
MAX_CONCURRENT_BY_KIND.t4_scan = 1 — only one scan coordinator at a time per org (plus advisory lock).
Failure modes
Second overlapping scan exits early (“locked by another process”). No T2 → zero tables → scan succeeds with little or no children.

5. Step B — t4_entity_propose (creating entities & joins)

Entity + join proposal

Unit of work
One catalog.schema cluster (all tables in that schema that the scan assigned to this child).
LLM input
Table names, T2 summaries/grain/key columns, FK hints from object cards, optional usage signals if T3 ran.
Creates
  • platform_sem_entities — full_path matches context object path; entity_label, description, synonyms, status=candidate, created_by=NULL.
  • platform_sem_joins — from_entity_id, to_entity_id, join_on_sql, join_type (default inner).
Uniqueness
One entity per (model_id, full_path) — constraint ux_pse_model_path. Re-runs upsert or skip per handler logic.
Fan-out
Enqueues one t4_dim_propose per table, carrying context_object_id in job scope.
Throughput
~10 clusters/min budgeted in RATE_PER_MINUTE; MAX_CONCURRENT_BY_KIND.t4_entity_propose = 2 (each may spawn up to 5 dim tasks).

11. End-to-end example (one table)

  1. T0–T2 run on prod.drifter.process_flow_log_user — context object has profile + semantic card.
  2. t4_scan includes schema drifter → enqueues t4_entity_propose for that schema.
  3. Entity propose creates platform_sem_entities with label “Process Flow Log User”, full_path as above, candidate.
  4. t4_dim_propose for that object creates dims (“Is Active”, “User ID”, …) and measures (“Total Process Flow Log Users” COUNT, “Distinct Users” HLLP).
  5. Entities UI shows the card with Candidate badges until you promote selected defs.
  6. Compiler can build SQL from governed subset only when Inspector/dashboard requests governed IDs.
