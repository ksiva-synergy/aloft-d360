# ALOFT agent builder and runtime: current state vs harness gaps (code audit, branch feature/ui-redesign, 2026-11-02)

Method: read-only audit of `C:\ALOFT\aloft-ui-redesign`. Every finding cites `path:line` instead of a URL. "Unreferenced" means no hit in `src/` or `scripts/` outside tests (git grep / ripgrep). Status keys: **PRESENT**, **PARTIAL**, **MISSING**, **BUG**.

## Inventory: status of each harness area

### Takeaway
The workbench gives an agent a name, instructions, a single smoke-test question and a draft catalog row. After that there is no immutable version, no eval gate, no rollback, and no per-agent runtime policy. Several declared settings (model, tools, policies, datasources, temperature/max_tokens) are stored but ignored at runtime. Automate (Flows) already has the governance agents lack: immutable versions, a publish gate, budgets and pinned capability versions.

## What does an "agent version" mean in this code today, and can you tell which version produced a given answer?

### Takeaway
An "agent version" is either a free-text label on a mutable row (`agent_catalog.version`, almost always `'1.0.0'`) or a separate forked row with a new slug. It is not an immutable snapshot. You cannot reliably tell which configuration produced a given answer: turn logs and saved chat messages record neither agent id/version nor a prompt hash.

### Cited Findings
- Row shape: `version String?`, `config Json?`, `tools Json?`, `status String? @default("draft")`, `parent_id`, `is_head`, `draft_of_id`, `policy_ids String[]` — `prisma/schema.prisma:90-121`.
- API accepts any `version` string ≤40 and any `status` string ≤40; ownership/lineage fields cannot be set by clients — `src/app/api/catalog/agents/schema.ts:4-27`.
- Commission always sets `version: '1.0.0'`; workbench edits never bump it — `src/app/api/agent-lab/workbench/commission/route.ts:69`; `src/lib/construction/persist-commissioned.ts:22-32` (no `version` field written).
- PATCH updates in place (`prisma.agent_catalog.update`) and audits only `fields: Object.keys(body)`, not before/after values — `src/app/api/catalog/agents/[id]/route.ts:34-35`.
- Fork = new row, new slug `${original.slug}-fork-${ts}`, `parent_id` = original, status `draft`, owner = caller — `src/app/api/catalog/agents/[id]/fork/route.ts:22-45`.
- "Versions" = lineage tree (root + 2 levels), sorted by `created_at` — `src/app/api/catalog/agents/[id]/versions/route.ts:14-55`.
- Prompt snapshot to `prompt_catalog` (has `version`, `parent_version_id`, `linked_agent_ids`, status `published`) is keyed on `config.prompt`, while all writers and readers use `config.systemPrompt`, so it effectively never fires — `src/app/api/catalog/agents/[id]/route.ts:37-48`; `src/lib/prompt-snapshot.ts:29-47`; `src/lib/construction/catalog-sync.ts:63,84`; `src/lib/agent-lab/artifactDraftSchemas.ts:19`.
- The runtime returns `agent: {id, name, slug, status}` and `model`, but no version — `src/lib/agents/run-catalog-agent.ts:331-332`. The chat SSE `done` event carries `model` only — `src/app/api/agent-lab/agents/chat/route.ts:189-195`.
- `agent_turn_log` / `agent_loop_log` have `session_id`, `surface`, `model`, and no agent id or version columns — `prisma/schema.prisma:3156-3207`; `src/lib/agent-ops/record-turn-metrics.ts:48-72`.
- A saved chat message has no turnId/model/version — `src/lib/agents/agent-chats.ts:237-239`.
- `agent_cost_log` and legacy `agent_run_log` have an `agent_version` column, but agent runs never write them (Inspector writes `'1.0.0'` hardcoded) — `prisma/schema.prisma:394-426`; `src/app/api/inspector/chat/route.ts:584,649`.
- Flows-side "Try it" audit records `slug, model, outcome, loops, toolCalls, costUsd, turnId`, but no version — `src/app/api/agent-lab/flows/agent-try/route.ts:45-52`.
- The construction draft is the real source of truth for workbench-built agents (`workbench_sessions.construction_state`, `saved_agent_id`) — `prisma/schema.prisma:170-192`. It is overwritten on every edit, so it is not versioned either.

### Inferences
- The best you can do today to attribute an answer is: chat id → `agent_turn_log.session_id` (agent chat) → timestamp → current `agent_catalog` row. Because rows mutate in place, that row may no longer match what ran.
- `agent_catalog.updated_at` plus the `audit_log` field-name entries give an edit timeline but not content. The before/after config is not kept anywhere.

### Gaps
- Whether `writeAudit` stores a full `before` snapshot anywhere for workbench edits: `persistCommissionedAgent` does not call `writeAudit` at all (`src/lib/construction/persist-commissioned.ts:1-59`), so workbench edits to commissioned agents are unaudited.

## What testing exists before an agent reaches users, and what gates promotion?

### Takeaway
Before an agent reaches users there is only an optional one-question smoke test, run with a different model default and toolset than production. Commission requires only completeness (name, class, ≥40-char instructions). The only promotion gate is a human admin "approve" that sets `published`, and nothing enforces it: chat runs drafts, and Flows expect statuses no code ever sets.

### Cited Findings
- Readiness: `validate` when name + instructions ≥40 + class id; `canCommissionAgent` = validate|commission — `src/lib/construction/readiness.ts:4-24`. The commission route rejects otherwise with "need name, class, and instructions (≥40 chars)" — `src/app/api/agent-lab/workbench/commission/route.ts:48-53`.
- Test run: a single question, read-only tools, 8 loops, result stored as `validation.lastTestRun` (single slot, overwritten), outcome = loop outcome (`completed|truncated|errored`), not correctness — `src/app/api/agent-lab/workbench/test-run/route.ts:23-24,36-41,147-169`; `src/lib/construction/constructionState.ts:59-70`.
- Test vs prod drift: test `resolveWorkbenchModel(body.model, role)` (feature default `workbench_chat`, `src/lib/construction/workbench-model.ts:27`) vs runtime `'commissioned_agents'` — `test-run/route.ts:47`; `src/lib/agents/run-catalog-agent.ts:187`. The test has no knowledge tool — `test-run/route.ts:103` vs `run-catalog-agent.ts:253`. Test system prompt `mode: 'test'` vs `'live'` — `src/lib/construction/prompts.ts:87-89,110-118`.
- Prompt lint and `coachScore` fields exist in construction state but are not used by readiness — `constructionState.ts:18-23`; `readiness.ts:4-19`.
- Approve: admin-only, self-approval blocked unless platform_admin, comment recorded in `catalog_review_comments`, sets `status:'published', is_head:true`, audited — `src/app/api/catalog/agents/[id]/review/route.ts:44-64`.
- Flow publish requires agent status `live|staging|preview` — `src/lib/flows/policy.ts:139-160`; `src/lib/agents/catalog.ts:7-11,25,41`. Catalog status vocabulary is `draft|in_review|published|deprecated` — `src/types/catalog.ts:1`; `src/lib/agent-lab/artifactDraftSchemas.ts:5`. No code sets `live/staging/preview` on `agent_catalog` (only `PlatformAgent` `UpdateAgentInput` mentions them, `src/lib/platform/agents.ts:47-48`, and `updateAgent` has no callers).
- Agent chat runs any agent with ≥20-char instructions regardless of status — `src/app/api/agent-lab/agents/chat/route.ts:92-94`; `src/lib/construction/catalog-sync.ts:85`.
- Eval queue exists but there is no runner — `src/app/api/agent-lab/ops/evals/route.ts:36-46`. The planned Phase E items (eval tables, headless runner, CI, Boost scorers) are all unchecked — `docs/agent-ops-build-plan.md:346-351`. The data-access doc wants a leakage eval set "run on every model or prompt change" — `docs/data-access-control-design.md:236` (§8.7) — and change control for prompts/models on Restricted data (§8.6, `:235`).
- Contrast, Flows: publish only the latest saved immutable version, re-run policy, require a successful simulation, audit — `src/lib/flows-store/service.ts:106-135`.

### Inferences
- Because approve sets `published` and Flows want `live`, approved agents are unusable in published automations. Teams wanting automation would have to PATCH `status:'live'` by hand, which bypasses review entirely (PATCH accepts any status string, `src/app/api/catalog/agents/schema.ts:23`).
- `validation.lastTestRun` copied into `config.validation` (`commission/route.ts:78`; `catalog-sync.ts:68`) looks like evidence of testing but can be stale or failed (`outcome: 'errored'` is accepted).

### Gaps
- No evidence found of CI or offline tests that exercise agent quality. Unit tests cover catalog-sync and authz (`src/lib/construction/__tests__/catalog-sync.test.ts`, `src/app/api/__tests__/authz-hardening.test.ts`), not answer quality.

## What runtime controls exist, and which declared settings are ignored at runtime?

### Takeaway
The real controls are a hardcoded read-only tool allowlist, a read-only SQL guard with row and time caps, a loop cap, message size limits, KB permission filtering and log redaction. Missing: per-agent tool and data scoping, status/ACL checks, rate limits, cost caps, sensitivity-based provider routing, input/output PII checks, and real injection delimiting. Most per-agent declared settings are ignored.

### Cited Findings
- Tool allowlist hardcoded in code, not per agent: `AGENT_TOOLS = {describe_schema, execute_tool}` — `src/lib/agents/run-catalog-agent.ts:34,250-256,274`. Commission stores `tools: state.tools.actions.map(a => a.toolId)` — `src/app/api/agent-lab/workbench/commission/route.ts:85` — and the runtime never reads it.
- Loop/token limits: `AGENT_MAX_LOOPS = 10` — `run-catalog-agent.ts:35,289`; `maxTokens: 4096`, `temperature: 0.3` fixed — `src/lib/inspector/agent-loop.ts:174-175`; `truncated` outcome at loop cap — `agent-loop.ts:332`.
- Model selection ignores `config.model`: `resolveWorkbenchModel(input.model, input.role, 'commissioned_agents')` — `run-catalog-agent.ts:187`; resolution uses only requested key, role access and feature default — `src/lib/construction/workbench-model.ts:29-50`.

## What do the unused tables and doc plans reveal about the intended design?

### Takeaway
The schema already holds most of a harness design: immutable manifests with rollback refs, eval suites with held-out/perturbation cases and gate verdicts, acceptance records with thresholds, config versions with model/temperature/iteration limits, golden sets and validation rules. Almost none of it is wired. Recommendations can reuse these tables rather than invent new ones.

### Cited Findings
- `PlatformAgentManifest` (`platform_agent_manifests`): `agent_id, session_id, config_ref, class_id, skill_ref, tool_ids[], schema_ref, eval_suite_id, rollback_ref, lineage_note, status('active')` — `prisma/schema.prisma:1887-1906`. ### Inferences
- Natural reuse map: (1) **immutable version** = a new `agent_catalog`-adjacent snapshot or `PlatformAgentManifest` row per commission/publish (`config_ref` → snapshot id, `tool_ids`, `eval_suite_id`, `rollback_ref` → previous manifest), with "live" = latest `status='active'` manifest (`getManifest` already implements that query). (2) **evals** = `PlatformEvalSuite/Case/Run/Result` (already supports held-out vs seen scores, generalisation gap, gate verdict, red-team count). (3) **release gate** = `PlatformAcceptanceRecord` thresholds compared against `PlatformEvalRun.gateVerdict` for `manifestId`. (4) **per-agent runtime config** = `agent_lab_config_versions`-style fields (model, temperature, max_iterations) or simply honouring `config.model/temperature/max_tokens`. (5) **budgets** = `budget_config` scoped per agent. (6) **attribution** = add `agent_id` + manifest/version id to `agent_turn_log` (Phase D "pin version on turn metadata").
- Two parallel eval schemas exist (`agent_eval_*` snake_case and `Platform*` camelCase). Consolidating on `Platform*`, which is richer and already read by the Ops UI, avoids a third.

### Gaps
- No design doc was found (in `docs/**/*.md`) that specifies how `PlatformEvalRun.gateVerdict` / `PlatformAcceptanceRecord` were meant to be computed or enforced. Their semantics are inferred from column names only. The "Business Agent Studio" HTML (`docs/agent-studio/*.html`) mentions an "Evaluation Lab" with held-out historical cases, but at concept level only.
- Whether the Boost / Performance Lab code (referenced by the eval POST note) has a scorer that could execute `PlatformEvalCase`s was not traced.
