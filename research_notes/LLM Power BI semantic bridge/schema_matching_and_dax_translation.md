# LLM techniques for schema matching, column mapping, and DAX/expression translation (Power BI semantic models → Databricks Unity Catalog)

Scope note: research conducted Nov 10, 2026. Sources are 2023–2026 unless flagged. "Vendor-reported" marks results published by the tool's own authors/sellers without independent benchmark. Peer-reviewed academic results are labelled with venue.

## 1. What does recent research (2023–2026) show for LLM schema matching / column matching / entity resolution? Accuracy and prompting patterns?

### Takeaway
The strongest, best-evidenced pattern is two-stage **retrieve-then-rerank**: cheap embedding/small-LM retrieval narrows candidates, then an LLM scores or ranks a short list (Magneto, VLDB 2025; ReMatch, Microsoft 2024). LLM-only matching over whole schemas underperforms on large targets, accuracy on realistic (non-curated) benchmarks is still modest (top-1 ≈ 0.42 on MIMIC→OMOP; F1 0.36–0.80 across real datasets), and results on popular benchmarks are inflated by saturation and training-data leakage.

### Cited Findings

**Magneto (Liu, Pena, Santos, Wu, Freire — NYU; PVLDB 18(8), 2025; peer-reviewed, open source)**
- Architecture: two phases — candidate retrieval with a small LM (SLM) using column embeddings, then LLM reranking; designed because SLMs need hard-to-get training data and LLMs hit cost and context-window limits — [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
- SLM fine-tuning is self-supervised: an LLM generates syntactically diverse synthetic training data (different column-name and value representations), with triplet loss + hard-negative mining — [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
- Column representation includes name, ~10 sampled values, and an inferred coarse type (numerical, categorical, date, binary; >90% distinct values → "key"); 10 values sometimes beat 30, "likely because of reduced noise" — [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
- Reranker prompt is **scoring-oriented**: one source column + top target candidates, LLM assigns each pair a 0.00–1.00 score (example output `WorkerID(0.95); EmpCode(0.30); StaffName(0.05)`), which enables cross-column comparison and global ranking, unlike prior table-wise rank-only prompts — [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
- Reranker used GPT-4o-mini; retriever MPNet (also supports RoBERTa, E5, Arctic, MiniLM) — [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf); [Magneto project page](https://edenwuyifan.github.io/20250728/project-magneto)
- Results: on the new human-curated biomedical **GDC benchmark** (10 source tables, 16–736 columns; target 93–4.5k columns), all Magneto variants beat traditional, model-based and supervised baselines on MRR and Recall@GT; fine-tuned-SLM + LLM reranker was best; even zero-shot variants beat recent SOTA — [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
- On **Valentine** datasets Magneto matched or beat baselines except **Unicorn**, whose advantage the authors attribute to data leakage (Unicorn was trained on Valentine data); ISResMat and Unicorn failed to complete GDC beyond 100 columns — [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
- Ablation: LLM-only approaches (GPT-4o-mini over the whole schema; Llama-3.3-70B) underperform the SLM+LLM combination for large target schemas; number of candidates sent to the reranker (3–20) is a tunable cost/accuracy knob — [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
- Stated limitation: "if the correct match is missing from the top-k, reranking cannot recover it" — retrieval recall caps end accuracy — [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
- Benchmark saturation: public real-data benchmarks (Magellan, WikiData in Valentine) are "quickly becoming saturated" with near-perfect scores — [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
- Code: [VIDA-NYU/magneto-matcher](https://github.com/VIDA-NYU/magneto-matcher)

**ReMatch (Sheetrit, Brief, Mishaeli, Elisha — Microsoft Israel; arXiv 2403.01567, 2024; preprint)**
- No training, no predefined mappings, **no access to source data** (metadata only). Target tables and source attributes are turned into structured documents (table purpose, PKs, FKs, attributes with type and description); embedding retrieval picks top-J candidate target tables per source attribute; GPT-4 (gpt-4-1106) ranks top-K target attributes; Ada-002 embeddings — [ReMatch arXiv](https://arxiv.org/html/2403.01567v2)
- MIMIC-III → OMOP (268 source columns / 25 tables → 425 target columns / 38 tables; expert-curated; released as the largest public single-schema mapping dataset): with J=1 accuracy@1 = 0.424, @3 = 0.644, @5 = 0.709; with J=2 acc@5 = 0.729, acc@7 = 0.758. Retrieving more tables (J≥3) *lowered* accuracy (e.g., J=7 acc@1 = 0.317) — extra tables add noise — [ReMatch arXiv](https://arxiv.org/html/2403.01567v2)
- Adding guidance improved results most at J=1; on the small Synthea→OMOP set (8 target tables), skipping retrieval was best for acc@5 — [ReMatch arXiv](https://arxiv.org/html/2403.01567v2)
- Prior SOTA SMAT (supervised) needed 80% labelled mappings to reach acc@5 = 100%; with a realistic 20% training split it was "significantly lower" than ReMatch — [ReMatch arXiv](https://arxiv.org/html/2403.01567v2)
- Explicit design goal: low K to "assist human schema matching, and minimize cognitive overload" — [ReMatch arXiv](https://arxiv.org/html/2403.01567v2)

**Parciak et al., "Schema Matching with LLMs: an Experimental Study" (UHasselt; VLDB 2024 TaDA workshop)**
- Compared task scopes: 1-to-1 (one attribute pair per prompt), 1-to-N, N-to-1, N-to-M (whole schemas). Each prompt sent 3 times with **majority voting**; split or missing votes = "unknown"; reported F1 and a "decisiveness" score — [Parciak et al. arXiv](https://arxiv.org/html/2407.11852)
- Best F1 per dataset ranged 0.364–0.800 on real (health-domain) datasets; GPT-4 beat GPT-3.5 across scopes; all scopes except 1-to-1 beat an N-gram name-similarity baseline (max gain 0.245 F1); N-to-1 (one target attribute vs. all source attributes) had highest mean F1 with GPT-4; N-to-M lowest — attributed to complex output format — [Parciak et al. arXiv](https://arxiv.org/html/2407.11852)
- Takeaway from authors: adding context (more candidate attributes in the prompt) improves precision; no single task scope dominates all datasets — [Parciak et al. arXiv](https://arxiv.org/html/2407.11852); artefacts at [GitHub](https://github.com/UHasselt-DSI-Data-Systems-Lab/code-schema-matching-LLMs-artefacs)

**Entity matching (record-level, relevant to matching dimension members / table identity)**
- Peeters, Steiner, Bizer (EDBT 2025): zero-shot GPT-4 (0613) mean F1 = 86.80 across prompt/dataset settings vs. GPT-4o 69.90 and GPT-4o-mini 65.10; GPT-4 without task-specific training beat fine-tuned PLMs (RoBERTa, Ditto) on 3 of 4 e-commerce datasets and was comparable on bibliographic data; LLMs more robust to unseen entities — [Peeters et al. arXiv/EDBT](https://arxiv.org/html/2310.11244)
- Same paper: "there is no single best prompt"; prompts must be tuned per model/dataset; GPT-4 can generate structured explanations and cluster its own error classes — [Peeters et al. arXiv/EDBT](https://arxiv.org/html/2310.11244)
- Note the counter-intuitive result that newer GPT-4o scored lower than GPT-4-0613 in that study — model upgrades are not guaranteed improvements for matching — [Peeters et al. arXiv/EDBT](https://arxiv.org/html/2310.11244)
- "Match, Compare, or Select?" (COLING 2025): across 10 LLMs, a **selecting** strategy (choose the match among several candidates) that incorporates record interactions outperforms independent pairwise "match" prompts; proposes COMEM compound framework for cost-effectiveness — [COLING 2025 paper](https://aclanthology.org/2025.coling-main.8.pdf)
- Jellyfish (instruction-tuned LLaMA-2-13B family for data preprocessing incl. entity matching) is designed for out-of-domain data-prep tasks; one model classifies with reasoning, a second refines — as described in [EDBT 2025 cross-dataset EM study](https://openproceedings.org/2025/conf/edbt/paper-224.pdf)

### Inferences
- For ALOFT, the evidence supports: (1) embedding retrieval over UC `information_schema` / table comments (per Power BI column) → (2) LLM *selection with per-candidate scores* among 3–10 candidates → (3) steward review. ReMatch's finding that fewer retrieved tables beats more suggests narrowing first to a table (via M lineage) and then matching columns within it.
- ALOFT's case is easier than the benchmarks in one way: for Databricks-sourced models, Power Query navigation usually names the physical table directly (see Q5), so the LLM matching problem reduces mostly to (a) renamed columns inside Power Query, (b) aliases in native SQL, and (c) non-Databricks sources (Snowflake, Excel) that must be matched to UC equivalents by name/values.
- Published accuracy numbers (0.4–0.8) are on cross-standard healthcare schemas; mapping a PBI column back to the column it was loaded from will likely score higher, but there is no published benchmark for that exact task, so ALOFT should build its own labelled set from steward approvals.

### Gaps
- No independent numbers retrieved for Unicorn (SIGMOD 2023) or Jellyfish on schema-matching (only descriptions and Magneto's leakage note).
- No published benchmark specifically for BI-semantic-model → warehouse column mapping was found.
- Results mostly use GPT-4-era models; no 2026 frontier-model results on GDC/MIMIC were found.

## 2. How are column mappings validated: value overlap, data type checks, statistical profiling, execution checks?

### Takeaway
Validation combines (a) instance-based similarity (value-set Jaccard, distribution distance), (b) type and key-ness checks, and (c) execution/reconciliation against the target (schema, row-hash, and per-column comparisons). Instance-based signals help most when names are uninformative; metadata-only methods (ReMatch) exist when data access is restricted.

### Cited Findings
- Valentine (Koutras et al., ICDE 2021 / PVLDB 14 demo — pre-2023 but the standard benchmark used by Magneto) evaluates matchers including instance-based **Distribution-Based** matching (Earth Mover's Distance over column value distributions) and a **Jaccard-Levenshtein** baseline (Jaccard of value sets, treating values as equal if Levenshtein distance < threshold) — [Valentine arXiv](https://arxiv.org/html/2010.07386v2)
- Valentine library docs: DistributionBased compares quantile histograms, "great for numeric or categorical data where names give you nothing"; Jaccard/Tversky matcher supports exact, string-distance, or sentence-embedding equality and is recommended "as a sanity check alongside a heavier matcher" — [Valentine matchers docs](https://delftdata.github.io/valentine/matchers/)
- Valentine metric: Recall@GroundTruth on a ranked list of all column pairs — [Valentine in Action, PVLDB 14](https://vldb.org/pvldb/vol14/p2871-koutras.pdf)
- Magneto feeds inferred column type and key-ness (>90% distinct) plus sampled values into the matcher; header-only serialization is a weaker baseline than name+values — [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
- Databricks Lakebridge **Reconcile** validates migrated data with report types: `schema` (column names + data types), `row` (hash per row, no key needed), `data` (row + column values via `join_columns`, per-column mismatch detail, `threshold_mismatch`), `all`; supports `column_mapping` when names differ and `drop_columns` for audit columns — [Lakebridge Reconcile guide](https://databrickslabs.github.io/lakebridge/docs/reconcile/); [Lakebridge config reference](https://databrickslabs.github.io/lakebridge/docs/reconcile/configuration/); [Lakebridge FAQ](https://databrickslabs.github.io/lakebridge/docs/faq/)
- Caveat from Lakebridge docs: type checks can give false matches/mismatches — e.g., narrower Databricks integer targets compare "equal" to BigQuery INT64 though they can't hold the full range; DATETIME matches timestamp though semantics differ — [Lakebridge Reconcile guide](https://databrickslabs.github.io/lakebridge/docs/reconcile/)
- WorldLink Labs' Databricks accelerator (vendor marketing) lists "KPI parity validation" — comparing KPI results against the Power BI baseline — as a final step — [WorldLink Semantic Model Migration Accelerator](https://worldlink-us.ai/partners/databricks/semantic-model-migration)

### Inferences
- For PBI→UC column mapping, a practical validator stack: (1) type compatibility (PBI type vs. UC type), (2) value overlap / distinct-count and null-rate similarity on samples from both sides, (3) row-count and aggregate parity (e.g., `SUM`, `COUNT DISTINCT` for the mapped column vs. the PBI model via XMLA/DAX query), (4) for measures, KPI parity at several group-by grains.
- For Import-mode models the PBI model holds a cached copy; querying it via DAX (`EVALUATE SUMMARIZECOLUMNS(...)`) and comparing to UC SQL is the closest analogue to Lakebridge's data reconcile. This is an inference; not described in a source found here.

### Gaps
- No source quantified how much value-overlap checks reduce false-positive mappings in an LLM pipeline.
- No source found on reconciling Power BI semantic model outputs (DAX query results) against Databricks automatically, other than vendor claims.

## 3. What exists for DAX-to-SQL translation, and which DAX constructs are hard?

### Takeaway
No peer-reviewed DAX→SQL paper was found; the field is tooling-led. Databricks Labs (Kasal), Databricks Forge, and WorldLink Labs ship hybrid pipelines: deterministic templates for simple aggregates, LLM fallback for complex measures, explicit "unsupported/decline" lists, and guards that reject translations that silently drop DAX components. The hard parts are DAX's evaluation-context semantics (context transition, filter overrides, implicit CALCULATE around measure references) and time intelligence, which UC metric views now partly cover via window measures.

### Cited Findings

**Tools / accelerators (all vendor- or author-reported)**
- **Kasal (databrickslabs/kasal)** frames the problem as two parallel translations: DAX → Spark SQL (measures) and Power Query M → source SQL (`Databricks.Catalogs(...)` navigation or native `SELECT`), feeding a metric-view YAML emitter; pipeline: extraction (PBI REST/scan) → config generation → M parser (+LLM fallback) and DAX translator (+LLM fallback) → join detection from DAX refs + PBI relationships → YAML → validation → `CREATE METRIC VIEW` deploy — [Kasal UCMV pipeline architecture](https://github.com/databrickslabs/kasal/blob/main/src/docs/powerbi/ucmv-pipeline-architecture.md)
- Kasal DAX path runs "llm_first": a regex fast-path only for trivially safe patterns (single-column SUM, ANSI-safe DIVIDE, simple filtered aggregates); everything else goes to an LLM with a "skill corpus" system prefix: `SKILL.md` (rules + output contract), `PATTERNS.md` (var-chain ratios, join-alias FILTER, share-of-total, ALLEXCEPT, SUMMARIZE-LOD), `EDGE_CASES.md`, and `UNSUPPORTED.md` — an "honest-skip list (TREATAS, LOOKUPVALUE, TOPN…) — what to decline, not fake" — [Kasal UCMV pipeline architecture](https://github.com/databrickslabs/kasal/blob/main/src/docs/powerbi/ucmv-pipeline-architecture.md)
- Kasal correctness guards: `sql_measure_sanitizer.py` and `detect_lost_dax_component` catch dropped prior-year windows, dropped DIVIDE denominators, exclusions, additive terms, and share-of-total collapse; a translation that drops a component is rejected rather than emitted; `dependency_graph.py` topologically orders measures so base measures translate before ratios — [Kasal UCMV pipeline architecture](https://github.com/databrickslabs/kasal/blob/main/src/docs/powerbi/ucmv-pipeline-architecture.md)
- Kasal tool-86 doc (author-reported): 14+ DAX patterns deterministic; Kahn's algorithm for dependencies; 470-measure model in <30 s; 823 tests; on one project (26 fact tables, 470 measures) 20/23 reference views exact measure-level match, 3/23 strict supersets, "93% business coverage"; LLM fallback "can push translation rate from 70% to 85%+ on complex models, at the cost of non-determinism" — [Kasal tool-86 doc](https://github.com/databrickslabs/kasal/blob/main/src/docs/powerbi/tool-86-uc-metric-view-generator.md). Note: translation *rate* ≠ verified correctness.
- **Databricks Forge** (databricks-solutions, release notes 2026-03-05): scans Fabric/PBI via Admin Scanner API; 4-step migration wizard — gold schema proposal with LLM-enhanced DDL, DAX-to-SQL "with confidence scoring", Lakeview dashboard generation, Genie space generation; hybrid deterministic templates + LLM; PBI→Spark type mapping; snake_case name normalization with a "full name-mapping ledger" — [Databricks Forge release notes](https://databricks-solutions.github.io/databricks-forge/release-notes/RELEASE_NOTES_2026_03_05.html)
- **WorldLink Labs** (Databricks partner, marketing page): TMDL parse → "deterministic DAX-to-SQL translation" with configurable rules → metric view YAML + "review bundles for flagged measures" → deploy via SQL Statement Execution API → KPI comparison against Power BI baseline — [WorldLink accelerator](https://worldlink-us.ai/partners/databricks/semantic-model-migration)
- **Lakebridge Switch** (Databricks Labs, experimental): LLM transpiler (Mosaic AI Model Serving) converting SQL/other formats to notebooks/SDP; custom YAML prompts for unsupported dialects; `max_fix_attempts` loop for syntax errors — general SQL, not DAX-specific — [Lakebridge Switch docs](https://databrickslabs.github.io/lakebridge/docs/transpile/pluggable_transpilers/switch/); [Lakebridge FAQ](https://databrickslabs.github.io/lakebridge/docs/faq/)

**Target capabilities: UC metric views**
- Window measures support `order`, `range` (`current`, `cumulative`, `trailing N unit`, `leading`, `all`), `semiadditive` (`first`/`last`), and `offset` (e.g., `-12 month`) for YoY, MoM, running totals, moving averages; YTD = cumulative window + a `current` year window — [Databricks metric views advanced techniques](https://docs.databricks.com/aws/en/uc-semantics/metric-views/advanced-techniques)
- Version constraints: `offset` requires YAML spec 1.1+; dated offset requires DBR 18.1+; numeric offset and unitless ranges require DBR 19+; `semiadditive` optional on DBR 19+; non-deterministic order fields (e.g., `current_timestamp()`) give incorrect results — [Metric view YAML reference (Microsoft Learn)](https://learn.microsoft.com/en-us/azure/databricks/uc-semantics/metric-views/yaml-reference)
- Semantic gap example: the documented period-to-date measure returns the latest year *with data*, not the calendar year containing today; "current year" must be pushed into the query because `CURRENT_DATE()` in the YAML breaks materialized metric views — [Databricks Community thread](https://community.databricks.com/t5/warehousing-analytics/metric-views-window-period-to-date-not-working/td-p/153551). DAX `TOTALYTD` etc. depend on a marked date table and filter context, so equivalence must be checked explicitly.

**Why DAX is hard (SQLBI, authoritative practitioner source)**
- Context transition: CALCULATE/CALCULATETABLE turn all row contexts into an equivalent filter context, which propagates through relationships; e.g., `Product[CalcSumOfSalesQuantity] = CALCULATE(SUM(Sales[Quantity]))` returns per-product sales while `SUM(Sales[Quantity])` returns the grand total — [SQLBI: Understanding Context Transition](https://www.sqlbi.com/articles/understanding-context-transition/)
- Context transition filters on *all columns* of the iterated table (actually the expanded table), so with duplicate rows it includes all duplicates — [SQLBI: Understanding Context Transition](https://www.sqlbi.com/articles/understanding-context-transition/); [SQLBI: Context transition in DAX](https://www.sqlbi.com/articles/understanding-context-transition-in-dax/)
- **Every measure reference is implicitly wrapped in CALCULATE**, so calling `[Measure]` inside an iterator (e.g., SUMX) triggers context transition with no visible CALCULATE — [SQLBI: Context transition in DAX](https://www.sqlbi.com/articles/understanding-context-transition-in-dax/)
- Evaluation order: CALCULATE evaluates filter arguments first in the outer context, then performs context transition, then applies the filters (which can override transition filters, e.g., `ALL(Product[ProductKey])`); the first argument is evaluated last — [SQLBI: Context Transition and Filters in CALCULATE](https://www.sqlbi.com/articles/context-transition-and-filters-in-calculate/); [SQLBI: Order of evaluation](https://www.sqlbi.com/articles/order-of-evaluation-in-calculate-parameters/)
- Time intelligence functions implicitly wrap their date column in `CALCULATETABLE(VALUES(...))`, so `SAMEPERIODLASTYEAR('Date'[Date])` performs context transition inside a row context — [SQLBI: Context Transition and Filters in CALCULATE](https://www.sqlbi.com/articles/context-transition-and-filters-in-calculate/)
- KEEPFILTERS changes whether a CALCULATE filter intersects or replaces the existing filter — [SQLBI: Order of evaluation](https://www.sqlbi.com/articles/order-of-evaluation-in-calculate-parameters/)

### Inferences
- A DAX measure has no single SQL equivalent; it is a function of the query's filter context. A metric view measure is likewise evaluated at query grain, which makes metric views a closer target than flat SQL views, but `ALL`/`ALLEXCEPT`/`REMOVEFILTERS` (filter removal), `USERELATIONSHIP` (inactive relationship activation), `TREATAS`, virtual-relationship patterns, iterator measures calling other measures, and calculation groups have no direct metric-view counterpart and should default to "needs steward".
- Suggested difficulty tiers for ALOFT routing: Tier A (auto-candidate) — `SUM/AVERAGE/MIN/MAX/COUNT/DISTINCTCOUNT` of a column, `DIVIDE` of two such, CALCULATE with simple equality filters on dimension columns; Tier B (LLM + strict verification) — VAR chains, SUMX over a single table with row-level arithmetic, YTD/PY via window measures; Tier C (decline/manual) — context-transition-inside-iterator, ALL/ALLSELECTED share-of-total, USERELATIONSHIP, TREATAS, LOOKUPVALUE, TOPN, calculation groups, RLS-dependent logic.
- Row-level security in PBI (DAX role filters) is a governance artifact, not a measure; it maps conceptually to UC row filters/column masks rather than to metric view measures. This is an inference — no source on automated RLS translation was found.

### Gaps
- No academic paper or public benchmark on DAX→SQL translation accuracy was found.
- No source specifically documented `USERELATIONSHIP`, calculation groups, or RLS translation to UC; these are listed as hard by inference from DAX semantics and from Kasal's decline list (which cites TREATAS, LOOKUPVALUE, TOPN).
- Kasal and Forge accuracy claims are self-reported on internal projects; Forge's confidence-scoring method is not documented in the release notes.

## 4. What does LLM code translation research (SQL dialects, legacy migration) say about verification?

### Takeaway
Across academic and industrial sources the consistent recipe is **rules first, LLM for failures, then an ordered validation ladder** (parse → compile/execute → result comparison → tests → human review). Execution feedback loops produce the largest accuracy jumps, but execution-equivalence on sample data is empirical evidence, not proof. Pure LLM translation of dialect-specific SQL is weak (PARROT: <38.53% average).

### Cited Findings
- **CrackSQL** (SIGMOD/PACMMOD 2025): rule tools (SQLGlot, jOOQ, SQLines) fail on some operations, produce wrong translations from rule gaps, and are version-sensitive; CrackSQL segments queries by functionality, uses a cross-dialect syntax embedding model to retrieve relevant dialect specs, and a local-to-global strategy that restricts LLM translation/validation to snippets with execution errors; reported up to 77.42% improvement over existing methods — [CrackSQL ACM](https://dl.acm.org/doi/10.1145/3725278)
- CrackSQL reported metrics distinguish Acc_EX (executes on target) from Acc_RES (identical results including order). PG→MySQL: SQLGlot 74.19/70.97, GPT-4o 61.29/61.29, CrackSQL 87.1/74.19; MySQL→PG: SQLGlot 60.32/60.32, GPT-4o 50.79/44.44, CrackSQL 85.71/79.37. Gap between EX and RES shows "runs" ≠ "correct" — [CrackSQL GitHub](https://github.com/OpenDataBox/CrackSQL)
- **DialectEvo** (PVLDB 19): deterministic translation first (SQLGlot), LLM with bounded self-reflection on failure, verification by actual execution; uses **multiset equivalence** (preserving duplicates) for unordered queries and list equivalence when ORDER BY is present, because set-based EX is "too permissive" — [DialectEvo PVLDB](https://www.vldb.org/pvldb/vol19/p4850-ma.pdf)
- DialectEvo explicitly cautions EX is "empirical evidence… not a complete guarantee of semantic equivalence": logically different queries may coincide on current data; NULL handling, type coercion, function semantics differ by DBMS — [DialectEvo PVLDB](https://www.vldb.org/pvldb/vol19/p4850-ma.pdf)
- DialectEvo ablation on ~1,400–1,500 BIRD-derived pairs per dialect: SQLGlot alone MySQL→Oracle 72.50%; adding LLM fallback Oracle→PG 78.71% → 98.59%; adding execution feedback PG→Oracle 86.10% → 98.19%; rule summarization from failures Oracle→Hive 92.74% → 98.99%; ~99% across 12 scenarios; direct GPT-5-mini 78–98% — [DialectEvo PVLDB](https://www.vldb.org/pvldb/vol19/p4850-ma.pdf). Note: the benchmark was filtered to queries whose cross-dialect semantics could be validated, which favours high scores.
- **PARROT** (NeurIPS 2025 Datasets & Benchmarks): 598 translation pairs from 38 benchmarks and real business services; LLMs average <38.53% accuracy; SOTA ranges ~17–60% across dialects; examples of failures include missing `NULLIF` divide-by-zero safeguards and mishandled nested ROLLUP. Also notes >89% of BIRD queries are system-agnostic, so text-to-SQL benchmarks overstate dialect skill — [PARROT NeurIPS paper](https://proceedings.neurips.cc/paper_files/paper/2025/file/269f1e26da3fd01d0d463765a934553f-Paper-Datasets_and_Benchmarks_Track.pdf)
- **Google, "Migrating Code at Scale with LLMs" (FSE 2025, industry)**: validation ladder applied in order — LLM completion success → reject whitespace-only changes → AST parse (and reject unchanged AST) → "punt" check (ask LLM if change was necessary) → build → regression tests → developer review → code-owner approval. 39 migrations, 595 changes, 93,574 edits; 74.45% of changes and 69.46% of edits LLM-generated; ~50% time reduction (developer-estimated) — [Google FSE 2025 arXiv](https://arxiv.org/html/2504.09691)
- **Google experience report (2025)**: 80% of code modifications in landed changes fully AI-authored; 5,359 files / 149k+ lines migrated in 3 months in one effort; ~87% of AI code committed unchanged; **reviewer throughput was the bottleneck**, so they deliberately throttled weekly change volume; file-needs-edit prediction 91% accurate for Java — [Google arXiv 2501.06972](https://arxiv.org/html/2501.06972); [Google Research blog](https://research.google/blog/accelerating-code-migrations-with-ai/)
- Self-consistency / voting in matching: Parciak et al. use 3-sample majority voting and treat split votes as "unknown" — [Parciak et al. arXiv](https://arxiv.org/html/2407.11852)

### Inferences
- For DAX→SQL, ALOFT can mirror the Google/DialectEvo ladder: (1) DAX AST parse succeeds and every referenced column/measure is accounted for in the output (component-loss check, as Kasal does), (2) generated SQL parses (SQLGlot, Databricks dialect), (3) `EXPLAIN`/dry-run against the warehouse (read-only), (4) result parity: run the DAX measure on the PBI model and the candidate SQL on UC at several grains (total, by month, by a key dimension, with a filter), compare with multiset semantics and numeric tolerance, (5) steward review.
- Differential testing at multiple grains is important specifically for DAX because errors in filter-context handling often show up only at sub-total levels, not at grand total.
- Throttling review volume (Google) suggests ALOFT should queue candidates by business impact (report usage) rather than dumping all ~500 models at once.

### Gaps
- No source on test-data generation specifically for semantic-equivalence of BI measures; LLM-generated test inputs for SQL equivalence were not investigated in this session.
- COBOL/PL-SQL migration verification sources (e.g., AWS, IBM) were not retrieved due to tool budget.

## 5. How to parse Power Query M deterministically vs. with LLMs to extract source tables and native SQL?

### Takeaway
Deterministic parsing is mature: Microsoft's open-source `powerquery-parser` (TypeScript, MIT) and Python `pbi_parsers` produce M ASTs; commercial catalogs (DataHub, Atlan, Matia) extract lineage from `Databricks.Catalogs`/`Snowflake.Databases` navigation steps and `Value.NativeQuery` SQL. Main failure modes are parameters, shared named expressions, and name-changing transforms; LLMs are best used as a fallback for those residual cases.

### Cited Findings
- **microsoft/powerquery-parser**: parser for Power Query/M in TypeScript, MIT, "designed to be consumed by other projects"; `TaskUtils.tryLexParse` returns an AST; recursive-descent + combinatorial parser following the 2016 M spec with documented deviations; npm `@microsoft/powerquery-parser` v4.0.0 (updated Oct 2026, ~8k weekly downloads); sibling `powerquery-language-services`, formatter, VS Code extension, and Power Query SDK — [powerquery-parser GitHub](https://github.com/microsoft/powerquery-parser); [npm package](https://www.npmjs.com/package/@microsoft/powerquery-parser); [specification notes](https://github.com/microsoft/powerquery-parser/blob/master/specification.md)
- **pbi_parsers** (Python, pip): lexers, parsers, formatters for DAX and M, "designed to support code introspection and analysis, not execution", explicitly for extracting PQ source types (Excel, SQL, etc.) and DAX lineage dependencies; `to_ast()` for DAX; used in `pbi_ruff` linter — [pbi_parsers GitHub](https://github.com/douglassimonsen/pbi_parsers); [pbi_parsers docs](https://douglassimonsen.github.io/pbi_parsers/)
- **PyDAXLexer**: extracts table/column/measure references from DAX; lexer grammar adapted from Tabular Editor (MIT) via ANTLR — [PyDAXLexer GitHub](https://github.com/jurgenfolz/PyDAXLexer)
- **Scanner API** (Admin REST): with "Enhance admin APIs responses with detailed metadata" and "…with DAX and mashup expressions" tenant settings, scans return tables, columns, measures, DAX expressions, and mashup (M) queries per table; full scan then incremental scans — [Microsoft Power BI blog](https://powerbi.microsoft.com/en-gb/blog/announcing-scanner-api-admin-rest-apis-enhancements-to-include-dataset-tables-columns-measures-dax-expressions-and-mashup-queries/)
- **DataHub** PowerBI source parses M expressions; table lineage supported for Databricks, Snowflake, BigQuery, SQL Server, PostgreSQL, Oracle, MySQL; native-SQL parsing (`Value.NativeQuery`) supported for Snowflake and Redshift; flags `native_query_parsing`, `enable_advance_lineage_sql_construct` (joins, subqueries), `extract_column_level_lineage` — [DataHub PowerBI docs](https://docs.datahub.com/docs/generated/ingestion/sources/powerbi/)
- **Atlan** retrieves M as a string and uses a custom parser; notes parameter substitution and variable naming in the Power Query Editor "may lead to inconsistent behavior"; resolves named-expression references (`db_source`, `#"db@source"`, `""&db_source&""`) by inlining before parsing — [Atlan PBI lineage docs](https://docs.atlan.com/apps/connectors/business-intelligence/microsoft-power-bi/references/what-lineage-does-atlan-extract-from-microsoft-power-bi)
- **Matia** column-level lineage: preserved through name-preserving steps (`Table.RemoveColumns`, `SelectColumns`, `ReorderColumns`, `SelectRows`, `Distinct`, `Sort`, `Buffer`); dropped (table-level only) after name-changing steps (`RenameColumns`, `Combine`, `Unpivot`, `Pivot`, `AddColumn`, `Group`) "rather than guessing"; parses `Value.NativeQuery` SQL to map columns — [Matia Power BI docs](https://docs.matia.io/docs/connectors/bi-tools/power-bi)
- Kasal uses `mquery_parser.py` with an `mquery_llm_fallback` for M it cannot parse deterministically — [Kasal UCMV pipeline architecture](https://github.com/databrickslabs/kasal/blob/main/src/docs/powerbi/ucmv-pipeline-architecture.md)

### Inferences
- Recommended order for ALOFT: (1) parse M to AST, (2) inline shared expressions and resolve parameters from the scan's dataset expressions, (3) detect connector function (`Databricks.Catalogs`/`DatabricksMultiCloud.Catalogs`, `Snowflake.Databases`, `Excel.Workbook`, `Sql.Database`) and follow `{[Name=...,Kind=...]}[Data]` navigation to get catalog.schema.table, (4) extract `Value.NativeQuery` SQL and parse it with SQLGlot (Databricks/Snowflake dialect) for table and column lineage, (5) replay `Table.RenameColumns`/`SelectColumns` steps to map PBI column names back to physical names, (6) only send unresolved steps (custom functions, dynamic SQL string concatenation, `Table.AddColumn` expressions) to an LLM. Steps 5–6 turn many "LLM matching" cases into deterministic ones.
- SQLGlot includes a column-lineage module usable for step 4; this was not verified with a source in this session.

### Gaps
- No public accuracy numbers comparing deterministic M lineage extraction vs. LLM extraction were found.
- The exact Databricks connector function names in M (and how Unity Catalog three-level navigation appears) were not confirmed from Microsoft docs in this session; check against ALOFT's own scanned M in `powerbi-estate/`.

## 6. How to compute confidence and decide auto-accept vs. human-review thresholds?

### Takeaway
Raw verbalized LLM confidence is overconfident and clusters into a few values, so it should not be the threshold signal alone. Better signals: per-candidate scores from a reranker (Magneto), agreement across samples (majority vote/self-consistency), score margin between top-1 and top-2, plus independent deterministic validators (lineage match, type, value overlap, execution parity). Thresholds must be calibrated on a locally labelled set and can differ by field/risk.

### Cited Findings
- Magneto's reranker emits 0–1 scores per candidate pair, enabling a global ranked list and Recall@GT evaluation; scores of non-reranked candidates are normalized below the lowest reranked score — [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
- Parciak et al. use 3-vote majority with "unknown" on split decisions and report a decisiveness score — usable as an abstain signal — [Parciak et al. arXiv](https://arxiv.org/html/2407.11852)
- LLM judges are "known to be overconfident, systematically expressing higher confidence than their empirical accuracy supports"; linear probes on hidden states give more cautious, better-calibrated confidence with higher accuracy among top-confidence predictions — [Calibrating LLM Judges (arXiv 2512.22245)](https://arxiv.org/html/2512.22245v1)
- Verbalized confidence suffers "saturation" (scores fall into few bins), so "no confidence threshold that accepts at least one claim can avoid accepting a substantial proportion of false claims"; DiNCo normalizes confidence across self-generated distractor alternatives and combines with self-consistency; DiNCo at 10 calls beat self-consistency at 100 — [DiNCo arXiv 2509.25532](https://arxiv.org/html/2509.25532)
- Kasal rejects translations failing component-loss guards instead of emitting them (hard gate, not a score) — [Kasal UCMV pipeline architecture](https://github.com/databrickslabs/kasal/blob/main/src/docs/powerbi/ucmv-pipeline-architecture.md); Forge reports "confidence scoring" for DAX translation without describing the method — [Databricks Forge release notes](https://databricks-solutions.github.io/databricks-forge/release-notes/RELEASE_NOTES_2026_03_05.html)
- Document-AI practice (not schema matching, vendor guidance): AWS bands confidence as high 90–100%, medium 70–89%, low <70% needing review, and recommends testing thresholds on your own data — [AWS ML blog](https://aws.amazon.com/blogs/machine-learning/process-multi-page-documents-with-human-review-using-amazon-bedrock-data-automation-and-amazon-sagemaker-ai/); per-field thresholds (e.g., 0.90 totals, 0.98 IDs) and auto-flow only if both confidence and validation rules pass — [EDC IDP article](https://resources.edc.ae/insights/closing-the-loop-confidence-scoring-and-human-review-in-idp); combine confidence with validation logic, business rules, and external-system checks — [Instabase blog](https://www.instabase.com/blog/overcoming-the-limitations-of-llms-data-validation-and-human-review)
- ReMatch and Magneto both frame output as a ranked short list for human selection (top-K with low K to limit cognitive load) rather than auto-accept — [ReMatch arXiv](https://arxiv.org/html/2403.01567v2); [Magneto PVLDB paper](https://www.vldb.org/pvldb/vol18/p2681-freire.pdf)
- Google throttled change volume because reviewers were the bottleneck — [Google arXiv 2501.06972](https://arxiv.org/html/2501.06972)

### Inferences
- Proposed composite for column mapping: `evidence = {deterministic lineage hit (M navigation / NativeQuery parse / rename replay), reranker score, top1–top2 margin, k-sample agreement, type compatible, value-overlap/distribution similarity, row-count parity}`. Auto-accept only when deterministic lineage resolves the column *and* type + value checks pass; LLM-only matches go to steward review regardless of score until local calibration shows precision ≥ target (e.g., 99%) at a chosen threshold.
- Proposed for DAX measures: auto-candidate (still steward-approved, but pre-checked) only when the measure is Tier A *and* multi-grain result parity passes within tolerance; Tier B requires parity + review; Tier C is declined with an explanation. "Confidence" for measures should be dominated by execution parity, not LLM self-report.
- Calibrate with steward decisions: log every accept/reject, then fit isotonic/Platt calibration on the composite score and pick thresholds from the precision–coverage curve; re-check when the LLM model version changes (Peeters showed newer models can score lower).

### Gaps
- No source reported calibrated thresholds specifically for LLM schema matching or DAX translation.
- No published evaluation of conformal prediction for schema matching was found in this session.
