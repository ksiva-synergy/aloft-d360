# Streaming, Prompting, and Polishing Rich Visual LLM Chat Responses (as of Nov 2026)

Target context: Claude via AWS Bedrock `ConverseStreamCommand` plus other providers; React/Next.js frontend. Research date 2026-11-01. Items from before 2026 are dated inline.

## (a) Streaming: how do you render partial markdown, fences, Mermaid, JSON chart specs, SVG, and streamed tool-call input?

### Takeaway
Use the same idea everywhere: accumulate the raw stream for each block, repair or parse it best-effort on each render, and only run the expensive renderers (Mermaid, chart libraries, syntax highlighting) once the block is closed or settled. While a block is still open, show a fixed-size placeholder. In Bedrock Converse, tool input arrives as `contentBlockDelta.delta.toolUse.input` string fragments, so a chart tool's input can be partially parsed and previewed as it streams. Anthropic's `eager_input_streaming` removes server-side buffering, but in exchange you may receive invalid JSON. Whether you can switch it on through Converse (rather than InvokeModel) is not confirmed.

### Cited Findings

**Markdown and fenced blocks while streaming**
- Vercel's Streamdown (a drop-in streaming markdown renderer) repairs unterminated code fences, tables, and lists before each render "so output never flashes broken formatting." Its `remend` preprocessor replaces incomplete images and links with sentinel URLs, e.g. `![alt](https://exampl` becomes `![alt](streamdown:incomplete-image)`. — [Streamdown release notes (releasebot)](https://releasebot.io/updates/vercel/streamdown); [developersdigest summary](https://www.developersdigest.tech/library/skills/streamdown-chat-rendering)
- Streamdown added a `useIsCodeFenceIncomplete` hook. It returns true while streaming is active, the block is the last one, and its fence is unclosed. Its stated purpose is to defer expensive renders such as syntax highlighting and Mermaid until the block is complete. — [Streamdown release notes](https://releasebot.io/updates/vercel/streamdown)
- Streamdown v2.7.0 changed Mermaid handling. Diagrams render one at a time while their fence streams, with a pause after each render, so a growing diagram no longer holds up the stream. "Once the fence closes or the stream stops, the final diagram renders without a pause." — [GitHub release streamdown@2.7.0](https://github.com/vercel/streamdown/releases/tag/streamdown%402.7.0)
- Other libraries use the same close-the-unclosed-fence approach, for example the Rust crates `mdstitch` and `mdstream`. — [docs.rs mdstitch](https://docs.rs/mdstitch); [docs.rs mdstream](https://docs.rs/crate/mdstream/latest/source/tests/code_fence_metadata.rs)
- Sources disagree on Streamdown's current version (v2.5.0 in one listing, v2.7.0 in another). Check npm. — [openapps.pro](https://openapps.pro/packages/streamdown); [GitHub release](https://github.com/vercel/streamdown/releases/tag/streamdown%402.7.0)

**Partial JSON (chart specs, tool input)**
- Partial-JSON repair closes an open string value and any open array or object, and drops a dangling key, colon, or comma. A truncated stream can end "normally with whatever partial value had accumulated, and no error is raised," so a truncated answer can look finished. This is from the Dart `stream_struct` package's `parsePartialJson`, but the caveat applies to every partial-JSON parser. — [pub.dev stream_struct](https://pub.dev/packages/stream_struct)
- In the Vercel AI SDK, the old `streamObject` + `partialObjectStream` pattern (v4/v5) has moved to `streamText` with `Output.object`, which exposes a `partialOutputStream` for rendering a UI while the object is still being generated. — [AI SDK recipe (current)](https://ai-sdk.dev/resources/recipes/node/stream-object.md); [AI SDK v5 cookbook](https://ai-sdk.dev/v5/cookbook/node/stream-object)

**Bedrock Converse streaming of tool input**
- `ContentBlockDelta` is a union, so each event sets exactly one member (text, toolUse, reasoningContent, citation, ...). — [AWS API ref: ContentBlockDelta](https://docs.aws.amazon.com/ja_jp/bedrock/latest/APIReference/API_runtime_ContentBlockDelta.html); [wener.me notes](https://wener.me/notes/ai/maas/bedrock)
- `ToolUseBlockDelta.input` is described as "The input for a requested tool", Type: String, Required. — [AWS API ref: ToolUseBlockDelta](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ToolUseBlockDelta.html)
- Event order: `contentBlockStart` carries `toolUseId` and `name`, then several `contentBlockDelta` events with `delta.toolUse.input` string fragments, then `contentBlockStop`, then `messageStop`. You concatenate the fragments per `contentBlockIndex` and parse at `contentBlockStop`. Parsing an individual fragment fails. — [Rust Converse tutorial (levelup)](https://levelup.gitconnected.com/aws-bedrock-converse-api-with-rust-tool-use-streaming-e20b7f42a5bd); [issoh.co.jp (JA)](https://www.issoh.co.jp/tech/details/2391/); [NTT DATA deck](https://speakerdeck.com/player/4df89fe8991641a0b3625a84856a4e06)

**Anthropic fine-grained tool streaming**
- To enable it, set `"eager_input_streaming": true` on each user-defined tool and turn on streaming. The legacy beta header `fine-grained-tool-streaming-2025-05-14` still turns it on for tools that leave the field unset, and an explicit `false` overrides the header. The header cannot be combined with computer-use or browser-use toolsets. — [Anthropic docs: Fine-grained tool streaming](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)
- The docs list the feature as stable on the Claude API, Amazon Bedrock, Amazon Bedrock (InvokeModel), Google Cloud, and Microsoft Foundry. Supported models include claude-opus-5-5, sonnet-5-5, haiku-5-5, opus-4-x, and sonnet-4-5/4-6. — [Anthropic docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)
- Without the flag, "the API buffers and validates each parameter value before streaming it back, so nothing prints for a large parameter until Claude has finished generating it." With it, fragments arrive "from the moment Claude starts the parameter, and they are typically longer, with fewer mid-word breaks." — [Anthropic docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)
- Warning from the docs: "you might receive partial or invalid JSON", and a `max_tokens` stop can cut a parameter off midway. The documented recovery is to return a `tool_result` with `is_error: true` and content `{"INVALID_JSON": "<raw input>"}`, built with a JSON library so it is escaped correctly. — [Anthropic docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)
- In Anthropic-native streaming, `content_block_start` for a tool_use block carries `input: {}` as a placeholder, and the real input arrives as `input_json_delta` events with `partial_json` strings. The contract is: initialize an empty string on start, append on each delta, parse on stop. — [Anthropic docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)
- AWS's own Bedrock page (older) says you enable it by adding the beta header `fine-grained-tool-streaming-2025-05-14`. Its example puts `anthropic_beta` in the Messages-format body (InvokeModel) and lists only Claude Sonnet 4 / Opus 4. One third-party guide says that for Claude, fine-grained tool streaming uses the Messages request format rather than the Converse schema. — [AWS Bedrock: Claude tool use](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-anthropic-claude-messages-tool-use.html); [hidekazu-konishi Converse deep dive](https://hidekazu-konishi.com/entry/amazon_bedrock_converse_api_deep_dive.html)
- Converse's `additionalModelRequestFields` is for "additional inference parameters that the model supports" beyond `inferenceConfig`. — [AWS API ref: ConverseStream](https://docs.aws.amazon.com/zh_tw/bedrock/latest/APIReference/API_runtime_ConverseStream.html)

**Streaming generative-UI protocols**
- A2UI (Google, Apache-2.0, CopilotKit contributes) streams declarative JSON as JSONL, so clients render partial UI as it arrives. The agent picks from a client-approved component catalog and sends no executable code. The current release is v0.9.1, and v0.9 moved from the nested typed format of v0.8 to flat JSON. The repo includes "A2UI Theater" for stepping through streaming scenarios. The GitHub README calls it an "early stage public preview." — [github.com/google/A2UI](https://github.com/google/A2UI); [a2ui.org](https://a2ui.org/); [azukiazusa.dev](https://azukiazusa.dev/en/blog/a2ui-protocol); [CopilotKit blog](https://copilotkit.ai/blog/a2ui-whats-new-in-google-generative-ui-spec)
- Vercel Labs `json-render`: the model can only use components in a Zod-defined catalog, and the output streams as JSONL patches (RFC 6902-style) applied by a `useUIStream` hook for progressive rendering. A claimed "sub-300ms perceived latency" comes from a third-party skill page and is unverified. — [jimmysong.io](https://jimmysong.io/ai/json-render); [sourcepulse](https://www.sourcepulse.org/projects/25901769); [LiveRender (hex)](https://preview.hex.pm/preview/live_render/0.2.1)

### Inferences
- **Recommended Converse pipeline:** keep a `Map<contentBlockIndex, {kind, name, raw}>`. On each `toolUse.input` delta, append to `raw`, then call a best-effort partial-JSON parser (e.g. `partial-json` or `best-effort-json-parser` on npm, or the AI SDK's partial parser), throttled to about one parse per animation frame or every 50–100 ms. Render a chart preview once the minimum renderable fields exist, e.g. `type` plus at least one complete series or row. Parse strictly with schema validation at `contentBlockStop`.
- **Design the spec schema so partial prefixes are useful.** Put small, layout-determining fields first (`chartType`, `title`, `x`/`y` field names, `height`, `series` names), then data rows. A partial parse can then size the container (no layout shift) and add points progressively. The model usually emits keys in schema order, which makes this practical.
- **Never render the final chart from a partial prefix without a "done" signal.** Truncated JSON repairs silently ([stream_struct note](https://pub.dev/packages/stream_struct)). Check `messageStop.stopReason` (`max_tokens` vs `tool_use` / `end_turn`) before treating a spec as final.
- **Fenced text blocks (```chart, ```mermaid, ```svg):** while a fence is open, show a fixed-height skeleton labelled with the language, e.g. "Drawing diagram…". Optionally show the raw source in a collapsed `<pre>`. Render once on fence close. For JSON chart fences, partial parsing works just as it does for tool input.
- **SVG:** progressively inserting a partially streamed SVG string is possible, because the browser parser drops unclosed elements via `DOMParser`. But it flickers and is a sanitization risk. A safer default is a placeholder until `</svg>`, then a sanitized render (DOMPurify with the SVG profile), cached by content hash.
- **Block-level memoization:** split the message into top-level blocks (e.g. with `marked.lexer` or the remark AST) and `React.memo` each block keyed by index plus a content hash. Only the last, still-growing block re-renders. This is Streamdown's model and the standard fix for O(n²) re-render cost in long answers.
- **Without verified Converse support for `eager_input_streaming`,** the default Converse buffering likely means large string parameters (e.g. SVG markup in a tool argument) arrive late in big chunks. That favors array-of-small-objects schemas (rows as separate array items) over one large string parameter. Inference from the buffering description in the Anthropic docs.

## (b) Emission design: fenced DSL vs tool calls vs JSON UI specs vs XML tags; which chart formats LLMs produce reliably; prompt rules and self-repair

### Takeaway
For a multi-provider app, the most robust split is: Mermaid and short SVG as fenced blocks in text (cheap, portable, streams naturally), and data charts as a dedicated tool call (`render_chart`) with a small, validated, Vega-Lite-like or custom minimal schema whose data comes from prior tool results. Validation errors go back to the model as `is_error` tool results. The research is consistent that LLMs fail most on data transformation and readability, not on syntax. A simpler intermediate spec beats raw grammars, especially for weaker models. No rigorous Vega-Lite vs ECharts head-to-head study exists.

### Cited Findings

**Benchmarks on LLM chart generation**
- **VisEval** (Microsoft Research and ShanghaiTech, IEEE VIS 2024 Best Paper, TVCG): 2,524 NL–VIS pairs, 1,150 visualizations, 146 databases. It scores validity (code runs), legality (meets the query) and readability (judged by a multimodal model). — [arXiv 2407.00981](https://arxiv.org/html/2407.00981v2); [IEEE VIS 2024 page](https://aa.ieeevis.org/year/2024/program/paper_v-full-1332.html); [GitHub microsoft/viseval](https://github.com/microsoft/viseval)
- VisEval Matplotlib pass rates (2024 models): GPT-4 75.27% (3.29% invalid, 21.44% illegal), GPT-3.5 61.79%, Gemini-Pro 51.59%, CodeLlama-7B 28.17%. On Seaborn, GPT-4's invalid rate rose from 3.29% to 25.41% and its pass rate fell to 58.70%. The library and grammar the model targets therefore matter a lot. — [arXiv 2407.00981](https://arxiv.org/html/2407.00981v2)
- In VisEval, illegal output (wrong transformation, mapping, or sort) is the dominant failure for strong models: 21.44% illegal vs 3.29% invalid for GPT-4. Its error categories are invalid code, illegal data transformation, illegal visualization transformation, illegal order, and low readability. Charts with three visual channels (stacked bar, grouped line, grouped scatter) score lower than two-channel charts, and quality falls as query hardness rises. — [arXiv 2407.00981](https://arxiv.org/html/2407.00981v2)
- Noisy tables ("table disruption") cut pass rates by 7–20 points, e.g. GPT-4 75.27 to 65.86 and Gemini-Pro 51.59 to 31.80. — [arXiv 2407.00981](https://arxiv.org/html/2407.00981v2)
- VisEval's examples: GPT-3.5 fails to sort as specified and places the legend off-canvas, GPT-4 has overflow issues, and Gemini-Pro maps the wrong aggregate to the y-axis. — [IEEE VIS 2024 page](https://aa.ieeevis.org/year/2024/program/paper_v-full-1332.html)
- Comparing pipelines on GPT-3.5 single-table queries (Matplotlib pass rate): CoML4VIS 67.55%, LIDA 67.77%, Chat2vis 69.93%. LIDA had the lowest readability (2.79). — [arXiv 2407.00981](https://arxiv.org/html/2407.00981v2)
- **LIDA** (Microsoft, ACL 2023 demo) reports "an error rate of < 3.5% on over 2200 visualizations generated (compared to a baseline of over 10% error rate)". Its repair is two-step: evaluate to get repair instructions (human-written or generated), then repair, driven by self-evaluation or compile feedback. No separate before/after figure for repair alone is reported. — [arXiv 2303.02927](https://arxiv.org/pdf/2303.02927); [LIDA project](https://lida-api.business.superwise.ai/)
- **DracoGPT** (2024): GPT-3.5-Turbo produced valid Vega-Lite completions only 19.10% of the time, and kept emitting Vega-Lite even when asked for Vega-Altair. — [arXiv 2408.06845](https://arxiv.org/pdf/2408.06845)
- **Flint** (2026): a semantics-driven intermediate language that compiles to Vega-Lite gives more reliable generation than raw Vega-Lite, "and the advantage grows as model capability decreases." It is shipped as the `flint-chart` npm package aimed at agent developers. — [arXiv 2607.20775](https://arxiv.org/pdf/2607.20775); [flint-chart README](https://cdn.jsdelivr.net/npm/flint-chart@0.4.1/src/README.md)
- A practitioner write-up (opinion, not a controlled study) argues that the common failures, axis-type and time-type errors in particular, look nearly the same whether the target is Vega-Lite, ECharts, or Matplotlib. — [braindetox.kr](https://braindetox.kr/en/posts/flint_visualization_language_2026.html)
- **VegaChat** (2026): Vega-Lite's declarative form lets some errors be fixed algorithmically, e.g. normalizing datetime fields. — [arXiv 2601.15385](https://arxiv.org/pdf/2601.15385)
- Text2Vis (2025) criticizes VisEval for lacking diverse chart types, real-world data-science tasks, and multi-step reasoning. — [arXiv 2507.19969](https://arxiv.org/html/2507.19969v1)

**Product precedent: Claude inline visuals (March 2026)**
- Anthropic launched inline custom visuals in beta on 2026-03-12. Claude "can create custom charts, diagrams and other visualizations in-line", on by default, either on its own judgment or on request ("draw this as a diagram"). As of 2026-04-22 the feature is in Cowork on paid plans. — [Claude blog](https://claude.com/blog/claude-builds-visuals); [Claude support](https://support.claude.com/en/articles/13979539); [alternativeto](https://alternativeto.net/news/2026/3/anthropic-s-claude-can-now-respond-with-interactive-visuals-such-as-charts-and-diagrams)

The Anthropic blog itself does not name the technology. — [The New Stack](https://thenewstack.io/anthropics-claude-interactive-visualizations/); [implicator.ai](https://www.implicator.ai/anthropic-gave-claude-a-whiteboard-not-a-canvas/)
- Competitors: OpenAI launched "dynamic visual explanations" for math and science around the same week, and Google added interactive charts and simulations for Gemini Ultra in Dec 2025. — [The New Stack](https://thenewstack.io/anthropics-claude-interactive-visualizations/)

**Guardrailed JSON UI specs**
- A2UI and json-render both restrict the model to a client-defined component catalog and send declarative JSON with no executable code, framed as the security model. Any model that can produce JSON can generate A2UI. — [github.com/google/A2UI](https://github.com/google/A2UI); [jimmysong.io json-render](https://jimmysong.io/ai/json-render)

**Error feedback loop**
- Anthropic's documented pattern for unparseable tool input is a `tool_result` with `is_error: true` that wraps the raw input, `{"INVALID_JSON": ...}`, so the model can retry. — [Anthropic docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)

### Inferences
- **Tradeoff matrix (synthesis):**
  - *Fenced DSL in text* (```mermaid, ```chart JSON, ```svg): works with every provider and streams naturally with text. There is no schema enforcement, and models sometimes nest or forget fences. Tokens are about the same as a tool call. Validation is client-side, and repair needs a follow-up turn because there is no tool_result channel.
  - *Dedicated tool* (`render_chart`, `show_diagram`): you get a JSON Schema in the tool definition, a clear stream boundary (contentBlockStart and Stop), and a `tool_result` channel for validation errors and self-repair. Tool calling works across Bedrock Converse (all tool-capable models), OpenAI, and Gemini. Costs are tool-definition tokens on every request (cacheable) plus an extra turn when the tool result is fed back. This is the best fit for data charts, where provenance and validation matter.
  - *JSON UI specs (A2UI / json-render / Thesys C1):* good for whole widgets and forms. They are heavier, and some lock you to a vendor (Thesys C1 is a hosted API). A2UI is still pre-1.0.
  - *XML tags (`<antArtifact>` style):* Claude-specific habits. They stream well and the attributes carry metadata, but portability is poor and other providers under-follow them.
- **Recommended chart format:** a minimal custom schema, roughly `{type: bar|line|area|scatter|pie|table, title, x:{field,type}, y:[{field,label,format}], series?, data:[{...}], source:{toolCallId}}`, rendered by your own React chart component. Optionally compile it to Vega-Lite or ECharts. This follows VisEval's finding that output validity swings with grammar complexity (Matplotlib vs Seaborn) and Flint's finding that a semantic intermediate layer improves reliability. Raw ECharts `option` objects are very large and permissive, so validating them is hard.
- **Data provenance rule** (prompt plus enforcement): require `source.toolCallId` (or row references) on every chart. Server-side, check that the data values, or a sample of them, appear in that tool result. Otherwise reject with `is_error: "data not found in referenced tool result; use only values returned by tools"`. VisEval's main failure mode is illegal *data transformation*, which supports aggregating server-side (SQL or code) and having the model chart already-aggregated rows instead of computing sums or averages itself.
- **"Show, don't tell" prompt rules** to adapt:
  - Use a visual only when its structure carries the meaning: comparisons of 3 or more values, trends over time, distributions, part-to-whole, processes or flows with 4 or more steps, architecture or relationships.
  - Use prose or a table for a single number, fewer than 3 data points, yes/no answers, or anything the user asked to keep short.
  - Make at most one visual per answer unless asked for more.
  - Always add 1–2 sentences of takeaway text next to the visual; never let a visual stand alone.
  - Never invent or estimate data for a chart; if data is missing, say so.
- **Self-repair loop:** the client renderer (Mermaid parse error, schema validation, chart lib exception) posts the error back. For tool calls, send it as `tool_result is_error`. For fenced blocks, auto-send a hidden follow-up user turn ("The ```mermaid block failed to parse: <error line N>. Re-emit only the corrected block."). Cap it at 1–2 retries, then fall back to showing the source code. Mermaid has `mermaid.parse()` for validating without rendering, which makes a server-side or pre-render check cheap.

- I did not fetch nvBench, ChartGPT, Data Formulator, or the full Flint paper, so their numbers are not included.
- I could not get the actual system prompt and tool definitions behind Claude's inline visuals feature. A tool name like "show_widget" could not be confirmed. The often-cited 2024 leaked artifacts prompt (`<antArtifact>`, the "good artifacts are…" rules) was not retrieved from a primary source in this session.

## (c) Polish: accessibility, theming, performance

### Takeaway
Treat each visual as a complex image: give it a short accessible name plus a long description and a data-table fallback, use Mermaid's `accTitle`/`accDescr` and ECharts' `aria` and decal options, and keep streamed tokens out of live regions (announce status only). For theming, feed design tokens into each library's theme API and re-render on theme change: Mermaid `base` theme plus `themeVariables`, ECharts `registerTheme` and `setTheme`, Shiki dual themes via CSS variables. For performance, dynamic-import the heavy libraries (Mermaid alone is about 480 KB of chunk), render only on fence close, cache output by content hash, and virtualize long threads.

### Cited Findings

**Accessibility**
- The W3C WAI Complex Images tutorial classes graphs, charts, flow charts, and org charts as complex images. It calls for a two-part text alternative: short alt text plus a long description, linked via `aria-describedby` (the value is the id of the description element). Long descriptions should be available to everyone, e.g. shown in the main content, and the image should be summarized in the surrounding text. — [W3C WAI: Complex Images](https://www.w3.org/WAI/tutorials/images/complex); [W3C draft](https://w3c.github.io/wai-tutorial-images/tutorials/images/complex/)
- `longdesc` (WCAG 2.0 technique H45) is legacy. One third-party source says it is deprecated and unsupported in modern browsers. — [W3C H45](https://www.w3.org/WAI/WCAG20/Techniques/html/H45)
- University guidance adds that charts must also provide the data they contain, which favors a data table as the long-description format. — [Niagara College accessibility hub](https://accessibilityhub.niagaracollege.ca/articles/websites/charts-and-graphs/)
- Mermaid automatically sets `aria-roledescription` on the SVG to the diagram type. Authors can add `accTitle: ...` (single line) and `accDescr: ...` (single line) or `accDescr { ... }` (multi-line). These become `<title>`/`<desc>` and are wired with `aria-labelledby`/`aria-describedby`. — [Mermaid docs: Accessibility](https://mermaid.js.org/config/accessibility.html); [Mintlify mirror](https://www.mintlify.com/mermaid-js/mermaid/configuration/accessibility)
- Adrian Roselli (2022) argues that using a chart generated from mermaid-js "almost guarantees" several WCAG violations, so Mermaid's built-in accessibility is only a starting point. — [adrianroselli.com](https://adrianroselli.com/2022/03/maybe-dont-use-flow-charts-on-github.html)
- An unverified task page reports that state diagrams can't take an accessible description in the diagram text. — [harborframework mirror](https://hub.harborframework.com/tasks/abundant/mermaid-js__mermaid-2917)
- ECharts' ARIA support is off by default. It generates a chart description automatically, needs `AriaComponent` imported when using modular builds (v5+), and supports `aria.decal.show` (patterns as a non-color cue for color-blind users) with custom `aria.decal.decals`. The handbook says `aria.show`, while the API reference says `aria.enabled`; check against the installed version. — [ECharts handbook: Web Accessibility](https://echarts.apache.org/handbook/en/best-practices/aria); [ECharts accessibility guide (mirror)](https://www.mintlify.com/apache/echarts/guides/accessibility)
- **Streaming and screen readers:** don't make the streaming body a live region. Announce short status messages instead ("Generating a response", "Response complete", "Response failed") from a separate polite region. A naive live region that mirrors token updates "will often produce constant interruptions". Avoid `aria-atomic="true"` on the streaming container, because the whole response re-announces on every token. Use `aria-busy="true"` during streaming and flip it to false on completion. Create live regions empty and early. Keep Stop reachable and preserve input focus. Automated checkers can't verify any of this, so test manually. — [azukiazusa.dev: accessible streaming chat UI](https://azukiazusa.dev/en/blog/accessible-streaming-chat-ui); [tianpan.co (2026-04)](https://tianpan.co/blog/2026-04-17-ai-accessibility-streaming-screen-readers); [Educative course](https://www.educative.io/courses/engineering-reliable-state-logic-for-ai-features/accessible-streaming-output-live-regions)
- An alternative pattern seen in practice: `role="log"`, `aria-live="polite"`, `aria-relevant="additions text"`, `aria-busy={isTyping}` on the transcript. This conflicts with the status-only advice above. — [TrixtyAI IDE PR #172](https://github.com/TrixtyAI/ide/pull/172)

**Theming**
- Mermaid's built-in themes are `default`, `base`, `dark`, `forest`, and `neutral`. Only `base` is fully customizable through `themeVariables` (`primaryColor`, `primaryTextColor`, `primaryBorderColor`, ...). Set `darkMode: true` so derived colors are computed correctly and meet WCAG contrast. Switching on `prefers-color-scheme` requires re-initializing and calling `mermaid.run()` again. — [Mermaid theming docs](https://mermaid.js.org/config/theming.html); [Mintlify mirror](https://www.mintlify.com/mermaid-js/mermaid/concepts/theming)
- ECharts: register themes with `echarts.registerTheme(name, obj)` and apply them at `echarts.init(dom, 'dark')`. `setOption` alone does not change the theme. The ECharts test suite shows `chart.setTheme()` for switching at runtime. — [ECharts theme test](https://apache.googlesource.com/echarts/+/refs/heads/master/test/theme.html); [ECharts customization guide (mirror)](https://www.mintlify.com/apache/echarts/guides/customization)
- Shiki dual themes store both themes' colors as CSS variables on each token instead of rendering the code twice. With `defaultColor: false` the HTML has no inline color at all, and your CSS chooses `--shiki-light` or `--shiki-dark`, which gives clean switching via a `[data-theme]` selector and no `!important`. — [Shiki: Dual Themes](https://shiki.style/guide/dual-themes)

**Performance**
- Real-world case (coder/mux): switching Mermaid to a dynamic `import()` on first diagram render moved a roughly 482 KB Mermaid chunk out of the startup path. Startup JS dropped from about 2,833 KB to about 2,292 KB across chunks. — [coder/mux commit](https://github.com/coder/mux/commit/bd18b4afa124e70db598d7deb20cc643b7ef0b47)
- Streamdown defers Mermaid and highlighting until the fence completes (`useIsCodeFenceIncomplete`) and throttles Mermaid renders mid-stream. — [Streamdown releases](https://releasebot.io/updates/vercel/streamdown)

### Inferences
- **Chart component contract:**
  - Wrap the chart as `<figure role="figure" aria-labelledby=title aria-describedby=summary>`.
  - Show a visible 1–2 sentence summary written by the model, e.g. a required `summary` or `altText` field in the `render_chart` schema.
  - Add a "View data" toggle that renders a real `<table>` from the same `data` array.
  - If the SVG chart lib can't be made keyboard-navigable, mark it `aria-hidden` and put focusable points in the table instead.
  - For Mermaid, put `accTitle`/`accDescr` in the prompt rules ("every mermaid block must begin with accTitle and accDescr"). If they are missing, inject them on the client from the surrounding text.
- **Reduced motion:** gate chart entry animations on `matchMedia('(prefers-reduced-motion: reduce)')` (ECharts `animation: false`; CSS transitions behind `@media (prefers-reduced-motion: no-preference)`). Streaming placeholders should not pulse under reduced motion. This is standard practice; no specific source was fetched here.
- **Tokens into charts:** read CSS custom properties with `getComputedStyle(document.documentElement).getPropertyValue('--chart-1')`, build the Mermaid `themeVariables` / ECharts theme object from them, and re-render on theme change via a `MutationObserver` on `<html data-theme>` or a `matchMedia` listener. Cache rendered SVG per (content hash, theme) pair. For sandboxed iframes (HTML or SVG widgets), `postMessage` the token map into the iframe on load and on theme change. Iframes don't inherit the parent's CSS variables.
- **Palette:** use one categorical palette of 6–8 hues, validated for contrast against both light and dark surfaces (WCAG 3:1 for graphical objects, SC 1.4.11). Pair it with ECharts decals or Mermaid line styles so information isn't encoded by color alone (SC 1.4.1).
- **Mermaid in a Web Worker** isn't straightforward, because Mermaid measures text in the DOM. Practical options are an `OffscreenCanvas`-free main-thread render scheduled in `requestIdleCallback` once the fence closes, or server-side rendering (headless browser or mermaid-cli) with cached SVG. Shiki can run in a worker or on the server (it is string in, HTML out), and Next.js server components can highlight code blocks after a message completes.
- **Long threads:** virtualize the message list (`react-virtuoso` and `@tanstack/react-virtual` handle variable heights). Keep a height cache per message so rendered charts don't cause jumps when they scroll back into view. Store rendered SVG and HTML with the message so re-mounting doesn't re-run Mermaid or Shiki. Reserve chart height from the spec (`height` field) during the skeleton phase to avoid CLS.
- **Sanitize every SVG or HTML the model emits** (DOMPurify, or a sandboxed iframe with `sandbox="allow-scripts"` and no same-origin) before injecting it. Mermaid's `securityLevel: 'strict'` is the default and should stay that way.
