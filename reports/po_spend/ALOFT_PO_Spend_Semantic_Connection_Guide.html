1. Why this feels confusing

Power BI PO Spend Analytics is not “just a report on a table.” The important business logic lives in three places at once:

  • SQL inside Power Query — joins and CASE rules (compliance vs leakage, status flags, DOC from FDL).
  • DAX measures — 119 KPIs on top of that flattened table.
  • Fabric storage — warehouse / lakehouse objects the PBIX pointed at when it was built.

Databricks has (or will have) the same underlying data, often under different names (catalog.schema.table), not po_spend_analysis as in Fabric.

ALOFT does not “import Power BI.” It stores a governed semantic model in its database and, at query time, runs SQL against Databricks only, using paths you configure.

Common mistake Thinking harvest / embeddings alone gives you PO Spend KPIs. Embeddings help find tables. You still must define entities, dimensions, measures tied to real UC paths and promote them to governed.

2. The idea in one sentence

Connect = tell ALOFT the exact Unity Catalog path of your fact table (or view), then register columns as dimensions and amounts as measures until Inspector can compile SQL to that path.

The technical name for “the path” in ALOFT is full_path on an entity — always three parts: catalog.schema.table.

3. Three layers (what each system owns)

Power BI / Fabric

Specification & UX

Shows charts, slicers, RLS. Today: reads Fabric SQL + embedded logic in the PBIX. Good source for what to name KPIs and what SQL to reproduce.

Databricks UC

Data & transforms

Tables and views holding rows. This is where joins and CASE logic should live long-term (especially one “enriched” view matching Purchase_History).

ALOFT

Governed semantics

Entities, dimensions, measures, joins stored in Aurora (platform_sem_*). Compiler turns a semantic query into SELECT … FROM catalog.schema.table.

User question (Inspector / dashboard) │ ▼ ┌─────────────────────┐ │ ALOFT semantic model │ ← entity.full_path = catalog.schema.table │ dimensions, measures │ └──────────┬──────────┘ │ compile SQL ▼ ┌─────────────────────┐ │ Databricks │ ← rows live here │ Unity Catalog │ └─────────────────────┘ Power BI today (parallel path, not ALOFT runtime): PBIX ──► Fabric warehouse / SQL DB ──► same business rows (different door)

4. What actually gets “connected”

Think in four registry rows in ALOFT — not in Power BI terminology:

Power BI concept ALOFT table (concept) You set
Table e.g. Purchase_History Entity entity_label + full_path (UC table or view)
Column in model Dimension column_name = real column name in Databricks
DAX measure Measure aggregate (e.g. sum) + column, or safe expression
Relationship Join join_on_sql e.g. fact.doc = doc_target.doc
Status: candidate → governed Until an entity and its measures are governed, production Inspector paths treat them as draft. Promote the entity first, then headline measures.

5. Pick a design: one view or many tables

You said equivalent tables already exist in Databricks. You still choose how ALOFT sees the fact:

✓ Recommended: one enriched UC view

Recreate Fabric Purchase_History SQL as a Spark view (joins + flags in the view).

  • One entity, one full_path
  • Matches how PBIX already flattens data
  • Easiest joins to doc_target only

Alternative: several UC tables

One entity per table; define joins manually.

  • More entities and join SQL to maintain
  • Auto T4 joins may default to = id — you must fix to PONO / DOC
  • Cross-table CASE logic harder in measures

Example placeholder for a gold view (your team fills real catalog names): reporting_layer.gold.po_spend_enriched

6. Step-by-step build checklist

1

List Unity Catalog paths

Write down every table/view PO Spend needs: fact, doc targets, optional RLS map. Three-part paths only.

2

Align columns with Power BI

Use schema.csv from the PBIX extract. Every dimension in ALOFT must point at a column that exists on the UC object (or view).

3

Harvest in ALOFT (Agent Lab → Jobs)

Run estate harvest (T0–T2 at minimum) on the catalog/schema that contains those tables so columns and descriptions appear in Estate.

4

T4 bootstrap (optional but helpful)

Jobs t4_entity_propose and t4_dim_propose create candidate entities and draft dimensions from column roles. Review — don’t trust blindly.

5

Edit the entity model on each table’s Estate page

Fix labels, add PBIX dimensions (DOC, compliance_flag, dates), add joins to doc_target, copy measure names from DAX as synonyms.

6

Promote entity → promote measures

Use Promote on the entity card. Then promote 5–15 headline KPIs.

7

Smoke test

Run the example SQL from the entity card or ask Inspector a question that maps to a governed measure. Compare one PONO to Power BI.

Diagnostic if dimensions never appear

From repo root (with app database URL):

npx tsx scripts/context/trace-t4-dim-for-table.ts --full-path YOUR.CATALOG.SCHEMA.TABLE

9. FAQ

We have tables in both Fabric and Databricks — which does ALOFT use?

Databricks only for queries ALOFT runs. Fabric/PBIX remains a reference until you repoint BI to UC.

Does ALOFT auto-sync from Power BI?

No. You extract semantics (PBIXray + this doc), implement logic in UC if needed, then author and promote in Estate.

Harvester found 55 purchase tables but none are governed — what now?

Those are ERP module candidates, not the PO Spend Analytics mart. Find or build the analytics fact path, harvest that schema, and create a dedicated entity for the mart — don’t mark all 55 governed at once.

What is “connected” in one line for my stakeholder?

“We registered the PO spend mart in ALOFT against Unity Catalog path X; governed dimensions and KPIs compile to SQL on X so agents and apps match our definitions.”
