# Freeze, test and gate every ALOFT agent

ALOFT should adopt agent versioning now. Today an "agent" is one mutable `agent_catalog` row that the workbench overwrites on every edit, including edits to an already published agent. That means no answer can be traced to the configuration that produced it, and no bad change can be rolled back. The industry pattern fits ALOFT's schema well: one mutable draft per agent, immutable auto-numbered versions created only on commit, and movable pointers (`staging`, `production`) that chat follows and automations pin. Rollback becomes a pointer move. The wider harness gap is larger than versioning. The runtime enforces a hardcoded tool list, a read-only SQL guard, a loop cap and message limits, but it ignores most settings a builder declares (model, temperature, tools, policies, data sources, output schema). It also never checks agent status, so drafts and deprecated agents run for anyone who knows the slug. There is no eval runner, so the only pre-release test is a single unscored question, run with a different model default and toolset from production. Two of the gaps are outright bugs that block or bypass the release process: approval sets `published` while Automate requires `live|staging|preview`, and the prompt-snapshot hook listens for a config key no writer uses. Most of the fix is wiring, not new design. The schema already contains manifests with rollback references, eval suites with held-out cases and gate verdicts, acceptance thresholds, and budget rows, none of them connected. The plan below fixes the release-path bugs first (about two weeks). It then adds immutable versions with run attribution, then a deterministic eval harness that gates approval, then per-agent runtime enforcement, then online evaluation, shadow runs and feedback.

## ALOFT "versions" are labels on a row that keeps changing

Every agent platform reviewed treats a version as a frozen snapshot of the whole agent definition. Microsoft Foundry says "an agent version captures a specific immutable snapshot of an agent. Every time you make changes to your agent, such as updating the prompt or adding tools, a new agent version is created" ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/agent-applications)). Bedrock Agents keeps a mutable `DRAFT` and makes numbered versions that "are immutable … To make updates to an agent in production, you must create a new version" ([AWS](https://docs.aws.amazon.com/bedrock/latest/userguide/deploy-agent.html)). AgentCore Runtime states that each version "contains all the configuration needed for execution" ([AWS AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agent-runtime-versioning.html)). Salesforce Agentforce's "Commit Version" locks a metadata snapshot before activation ([Trailhead](https://trailhead.salesforce.com/content/learn/modules/new-agentforce-builder-quick-look/explore-the-new-agentforce-builder)).

ALOFT has none of this. `agent_catalog.version` is a free nullable string of up to 40 characters (`prisma/schema.prisma:96`, `src/app/api/catalog/agents/schema.ts:15`). Commission always writes `'1.0.0'` (`src/app/api/agent-lab/workbench/commission/route.ts:69`), and nothing ever increments it. The admin PATCH updates the row in place and audits only the *names* of the changed fields, not their values (`src/app/api/catalog/agents/[id]/route.ts:34-35`). The bigger problem is the workbench. `persistCommissionedAgent` writes name, tools and config straight onto the catalog row (`src/lib/construction/persist-commissioned.ts:22-32`), and it runs on every Config-panel edit and every builder chat turn (`src/app/api/agent-lab/construction/route.ts:56-67`, `src/app/api/agent-lab/workbench/chat/route.ts:273-279`). It does not call `writeAudit`. **A builder chatting with the workbench about a published agent changes that agent's live prompt for every user and automation immediately, with no review, version bump or audit record.**

The features that look like versioning do not deliver it. "Fork" creates a separate agent with a new slug, `<slug>-fork-<ts>` (`src/app/api/catalog/agents/[id]/fork/route.ts:22-45`). The versions endpoint walks `parent_id` lineage only two levels deep and has no auth check in the handler (`versions/route.ts:14-55`). Approval sets `is_head: true` without clearing it on siblings, and nothing reads it (`review/route.ts:58-62`). The prompt auto-snapshot into `prompt_catalog` fires only when the PATCH body contains `config.prompt` (`[id]/route.ts:37-48`), but the runtime, the workbench and the canonical draft schema all use `config.systemPrompt` (`src/lib/construction/catalog-sync.ts:63,84`; `src/lib/agent-lab/artifactDraftSchemas.ts:19`), so in practice it never fires. On the observability side, `agent_turn_log` has no agent id or version column (`prisma/schema.prisma:3156-3207`), and saved chat messages store only `{id, role, content, timestamp, inspection}` (`src/lib/agents/agent-chats.ts:237-239`). **The only way to attribute an answer today is to join chat id to turn log to timestamp to the current catalog row, and that row may no longer match what ran.**

### Recommended model: draft, numbered snapshot, protected pointer

The model that transfers best is Bedrock's and AgentCore's. A mutable draft holds work in progress. Immutable versions get monotonically increasing integers. Named pointers are what callers bind to: a `DEFAULT`-style pointer follows the latest version, and named endpoints such as `production` move only when someone promotes explicitly ([AWS AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agent-runtime-versioning.html)). No surveyed platform uses semantic versioning for agents. Integers plus a content hash avoid arguments over what counts as "breaking" for a prompt change. A separate `breaking` flag is still useful for output-schema or tool-contract changes, because pinned automations depend on those. Versions should be created only on an explicit commit or submit-for-review, not on autosave. That is how Agentforce's Commit Version and Bedrock's alias-driven versioning avoid the version explosion that every-save registries produce ([Trailhead](https://trailhead.salesforce.com/content/learn/modules/new-agentforce-builder-quick-look/explore-the-new-agentforce-builder); [Braintrust](https://www.braintrust.dev/docs/evaluate/prompts/versions)).

The status of a version ("in production") should be *derived* from which pointers reference it, not stored as a second field that can drift. ALOFT already has that drift between `status`, `is_head` and the Flows vocabulary. Rollback is repointing `production` to an earlier version, which every reviewed platform supports and which is instant ([AWS](https://docs.aws.amazon.com/bedrock/latest/userguide/deploy-agent.html); [LangSmith](https://docs.langchain.com/langsmith/manage-prompts); [MLflow](https://mlflow.org/docs/latest/genai/prompt-registry/)). A separate kill switch modeled on Bedrock's `aliasInvocationState = REJECT_INVOCATIONS` pauses an agent without rolling it back ([AWS](https://docs.aws.amazon.com/bedrock/latest/userguide/deploy-agent.html)). Interactive chat should follow `production`. Automations should pin an exact version number, the way Braintrust recommends pinning in production code so "later saves don't affect your application until you update the pin" ([Braintrust](https://www.braintrust.dev/docs/evaluate/prompts/versions)). Today the Flow `agent` step stores only `agentSlug`, while capability `tool` steps already pin an exact semver (`src/lib/flows/schema.ts:98-112` vs `:167-169`). ALOFT should own this registry in Postgres rather than lean on a vendor prompt object: OpenAI's `v1/prompts` endpoint shuts down on 30 November 2026, and OpenAI now advises keeping prompts in versioned code with evals in the deploy path ([OpenAI](https://developers.openai.com/api/docs/guides/prompting)).

| Snapshot field (frozen in the version) | Why it must be frozen | Where it lives today |
|---|---|---|
| System prompt, persona, prompt template variables | Primary behavior driver | `config.systemPrompt`, `config.persona` (mutable) |
| **Resolved** model id (dated or ARN, never an alias) plus temperature, max tokens, reasoning budget | Floating aliases change behavior silently ([vincentschmalbach.com](https://www.vincentschmalbach.com/model-alias-vs-versioned-model-id/), secondary) | `config.model` stored but ignored (`run-catalog-agent.ts:187`) |
| Tool ids with risk tier and JSON schema copied by value | A tool edit must not change a pinned version | `agent_catalog.tools` stored but ignored |
| Data scope: catalogs, schemas, tables | Basis for the runtime table allowlist | `config.datasources`, prompt text only (`prompts.ts:84-100`) |
| KB bindings (id; index or sync id recorded per run) | KBs re-sync, so record the resolved state on each run | linked KBs resolved at run time |
| Answer fields and output schema | Automations consume them | `input_schema`/`output_schema`/`config.output` ignored |
| Guardrail profile and version, limits (loops, tokens, USD, wall clock), policy ids | Release-relevant behavior | hardcoded constants; `policy_ids` ignored |
| Memory scope configuration | Changes what context the model sees | PlatformAgent `thread_policy`/`retrieval_scope` ignored |
| Parent version, content hash, commit message, creator, eval run id, approver | Audit, dedup and gating | none |

Settings that legitimately differ by environment, such as credentials, the data identity and connection references, belong outside the snapshot. Copilot Studio keeps them in connection references and environment variables, and Foundry binds identity to the published application rather than the version ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/agent-applications)). MLflow is the counter-example to avoid: its model config attached to a prompt version can change without creating a new version ([MLflow](https://mlflow.org/docs/latest/genai/prompt-registry/)).

**Reuse.** `PlatformAgentManifest` already holds `config_ref`, `tool_ids[]`, `schema_ref`, `eval_suite_id`, `rollback_ref`, `lineage_note` and `status`, and `getManifest` already implements "latest active manifest" (`prisma/schema.prisma:1887-1906`, `src/lib/platform/agents.ts:287-317`, currently with no callers). It is the natural version record. Extending it with `catalog_agent_id`, `version_no`, `snapshot Json`, `config_hash`, `created_by` and `commit_message`, and adding one small `agent_alias` table (`name`, `manifest_id`, `invocation_state`, `protected`), costs less than a new design. `prompt_catalog`, which has `parent_version_id` and `linked_agent_ids`, can remain the prompt-text history once its trigger is fixed.

## Builders declare thirteen things; the runtime enforces about four

The point of a harness is that "safety and reliability come from the harness, not from the prompt". Anthropic calls the Claude Agent SDK "a general-purpose agent harness" that owns the loop, context management and permissions ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Its permission order is hooks, then deny rules, then ask rules, then mode, then allow rules, then callback, and deny rules apply even in bypass mode ([Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/permissions)). The OpenAI Agents SDK adds per-tool input and output guardrails with tripwires ([OpenAI Agents SDK](https://openai.github.io/openai-agents-python/guardrails/)). The principle in both: the agent *declares* its scope, and the platform *enforces* it in code. The table below is the checklist a builder should work through for every agent. Each row shows what ALOFT does today, with code evidence.

| Dimension | What the builder must decide | What the harness must enforce | ALOFT today | Evidence |
|---|---|---|---|---|

Lint and `coachScore` exist but readiness ignores them; readiness only requires ≥40 characters | `src/lib/construction/readiness.ts:4-24`; `constructionState.ts:18-23` |
| Model | Pinned model id, parameters, allowed fallbacks within one sensitivity class | Use the declared model; route by data sensitivity | **Ignored.** The model is resolved from caller key, role and feature default *before* the agent row is loaded. `maxTokens: 4096` and `temperature: 0.3` are hardcoded | `run-catalog-agent.ts:187-191`; `agent-loop.ts:174-175`; `providers/factory.ts:6-14` |

Because tools and limits are global constants, **every ALOFT agent has identical power**: read-only SQL over everything the shared Databricks principal can see. Agents differ only in prompt text and linked KBs. This is OWASP LLM06 Excessive Agency in its "excessive permissions" form. Its mitigations are to run extensions in the user's context and to enforce authorization downstream rather than in the model ([OWASP LLM06](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)). The fix with the most leverage is a per-agent table allowlist checked against parsed SQL identifiers, with `describe_schema` filtered to the same list so the model never learns about out-of-scope tables. Moving toward caller identity or narrowly granted per-agent principals would let Unity Catalog row and column policies apply. Databricks on-behalf-of mechanics were not verified in this research and need a separate spike.

Prompt-injection containment needs the same architectural treatment. Detection is probabilistic, and Simon Willison's point that "in web application security 95% is very much a failing grade" applies directly ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Meta's Rule of Two says an agent should combine no more than two of: untrusted input, sensitive data access, and the ability to change state or communicate externally ([Meta AI](https://ai.meta.com/blog/practical-ai-agent-security/)). ALOFT agents always have sensitive data. Free-text warehouse columns and multi-author KB documents are untrusted input. Markdown images or links in the chat renderer, and any automation that emails, posts or writes back, are external channels. The practical rules that follow are four: sanitize the chat renderer deterministically (no remote images, allowlisted link domains); wrap every SQL result and KB chunk in randomized delimiters with provenance, the "spotlighting" defense Microsoft uses ([MSRC](https://www.microsoft.com/en-us/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks)); require a human approval step for automations that pair SQL or KB access with an outbound action; and use blocking rather than parallel input guardrails for unattended runs. The OpenAI SDK warns that in parallel mode "the agent may have already consumed tokens and executed tools before being cancelled" ([OpenAI Agents SDK](https://openai.github.io/openai-agents-python/guardrails/)). Bedrock's `ApplyGuardrail` works without invoking a model, so it can serve as one provider-neutral layer for prompt-attack, PII masking and contextual-grounding checks. Its `action: NONE` detect-only mode allows thresholds to be calibrated on live traffic before enforcement ([AWS Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html); [AWS grounding](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-contextual-grounding-check.html)). Grounding checks cap the source at 100,000 characters and the response at 5,000, so large result sets must be summarized before checking.

Observability should follow the OpenTelemetry GenAI conventions: one `invoke_agent` span carrying `gen_ai.agent.id`, `gen_ai.agent.version`, `gen_ai.conversation.id` and usage tokens, with message content opt-in and stored by reference ([OTel GenAI](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)). Those attributes are still at "Development" stability, so ALOFT should pin a semconv version. Each run should also record the pointer it resolved through. Without it, an incident cannot distinguish "the pointer moved" from "the version changed".

## Testing an agent means a golden set, k repeats and paired comparison

The current pre-release test cannot catch a regression. The workbench Test run answers one question of at most 2,000 characters, stores only the latest result in a single slot that the next run overwrites, and records the loop outcome (`completed|truncated|errored`) instead of correctness (`test-run/route.ts:23-24,40,147-169`). It also runs a different harness from production: feature default `workbench_chat` instead of `commissioned_agents`, no `search_knowledge` tool, no turn-metrics recorder, and 8 loops instead of 10 (`test-run/route.ts:47,103,108,24` vs `run-catalog-agent.ts:187,253,236,35`). The result is not tied to a config hash, and an `errored` run is still copied into `config.validation` as if it were evidence (`commission/route.ts:78`). Anthropic is explicit that the eval should run "the same agent configuration used in production", with each trial isolated from shared state ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). **The first rule of the ALOFT eval harness is therefore that it calls `runCatalogAgent` against a specific version snapshot, never a parallel test path.**

### Creating test cases

Start with **20-50 cases per agent drawn from real failures and existing manual checks**, not hundreds. Early changes have large effects, so small sets detect them ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). The set grows past 100 as production failures are fed back in ([Hamel Husain](https://hamel.dev/blog/posts/evals-faq/)). Each case needs an unambiguous pass/fail definition that two domain experts would agree on, and a reference solution that proves it can be solved. A 0% pass rate across many trials usually means the task or grader is broken ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). For a data agent, a case should carry the user turns, the reference SQL, the expected result captured on a pinned data snapshot, the expected tables and columns, the expected typed answer fields with tolerances, the KB documents it must cite, a `should_refuse` flag, forbidden tables or PII columns, caps on tool calls, cost and latency, and rubric notes for any judge. This mirrors Agentforce Testing Center's utterance → expected topic/actions/response format ([Trailhead](https://trailhead.salesforce.com/content/learn/modules/agentforce-agent-testing/set-up-testing-criteria)). `PlatformEvalCase` already has nearly every field needed: `input`, `expectedOutput`, `heldOut`, `perturbation`, `parentCaseId`, `fixtureNs`, `caseKind`, `scorerType`, `scorerConfig`, `weight`, `tags` (`prisma/schema.prisma:1711-1731`).

Cases come from three sources. Domain owners write the "must work" seed set. An LLM proposes expansions from table comments, sample rows and KB titles using dimension tuples (question type × table × difficulty × persona); a human executes, fixes or rejects each one, and nothing is admitted automatically. Synthetic data cannot tell you how often a failure occurs in production ([Hamel Husain](https://hamel.dev/blog/posts/evals-faq/)). Harvested production failures (thumbs-down answers, approver rejections, automation failures) become regression cases once a human writes the expected outcome. Balance the set with should-not cases (unanswerable, ambiguous, empty-result, permission-restricted questions) so the agent is not optimized one-sidedly ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Add two or three paraphrases per seed case, linked through `parentCaseId`, to measure robustness. Hold out roughly 20-30% that prompt authors never see while iterating; that fraction is a judgment, not a published standard. A separate security set should be owned by people other than the agent's author, following NIST AI 600-1's independence recommendation ([NIST AI 600-1](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf); action IDs come from secondary summaries). Multi-turn behavior can be tested by replaying the first N-1 real turns and scoring turn N, which "often works better" than a simulated user ([Hamel Husain](https://hamel.dev/blog/posts/evals-faq/)).

### Scoring: deterministic first, judges only where needed

Anthropic's order of preference is code graders where possible, LLM graders where necessary, and humans for validation ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). For ALOFT the deterministic stack is: execution match of the agent's final SQL against the reference SQL on the same snapshot, compared as order-insensitive multisets with numeric tolerance (the BIRD/Spider execution-accuracy practice, since string match "significantly underestimates" correctness ([BIRD](https://arxiv.org/pdf/2305.03111))); precision and recall of referenced tables and columns; per-field answer accuracy; SQL safety (single read-only statement, no forbidden objects); citation ids that are a superset of `must_cite_docs` and were actually retrieved in the trace; and trajectory constraints such as tool-call count, repeated identical SQL and error loops. LLM judges are used only for groundedness, refusal-when-unknown and "answers the question". Each judge is binary, covers one failure mode, may return "Unknown", and must be calibrated against 100-200 human labels with reported TPR/TNR before it can block a release ([Hamel Husain](https://hamel.dev/blog/posts/evals-faq/)). Databricks MLflow 3 ships `RetrievalGroundedness`, `Correctness`, `ToolCallCorrectness` and `Guidelines` judges and accepts custom code scorers ([Databricks](https://docs.databricks.com/aws/en/mlflow3/genai/eval-monitor/concepts/judges/)). It could host this backend, but only inside ALOFT's own workspace and keys, given the standing rule that ALOFT and DATA360 never share settings or infrastructure.

### Running a benchmark and comparing versions or models

A benchmark run fixes the agent version, the resolved model id and parameters, the dataset version, the warehouse snapshot (Delta time travel or a snapshot schema), the KB index version and the judge model. Each case runs **k = 3 times** (k = 5 for automation agents) in isolated sessions. Consistency matters more than best-case success. pass^k, the probability that all k trials pass, falls quickly: **75% per-trial success gives pass^3 ≈ 42%** ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). On τ-bench, GPT-4o fell to about 25% at pass^8 in retail ([τ-bench](https://arxiv.org/pdf/2406.12045)). Cases that pass in some trials but not all should be listed separately as flaky; they are the best targets for prompt or tool fixes.

The scorecard per version, or per model, reports pass^1 with a 95% confidence interval, pass^3, execution accuracy, table/column precision and recall, field accuracy, groundedness, citation coverage, refusal accuracy split into correct refusals and over-refusals, security attack-success rate by category, mean and p95 cost, p50 and p95 latency, tool calls per answer, tool-error rate, loop-cap hits and flaky-case count, with per-tag breakdowns. Comparison between a candidate and production, or between model A and model B, must be **paired on identical cases and snapshot**. The output is a per-case diff (newly failing, newly passing, unchanged) plus the paired mean difference with its standard error. Paired SE shrinks as per-question correlation rises, and questions that share a source table need clustered errors, which can be "over three times as large as naive standard errors" ([Anthropic statistics](https://www.anthropic.com/research/statistical-approach-to-model-evals)). With fewer than about 100 cases the intervals will be wide, so a McNemar test on discordant pairs or a bootstrap over cases (standard statistics, not drawn from a cited agent-eval source) plus manual review of every changed verdict is more honest than a headline delta. For open-ended prose, a pairwise judge with randomized order counters the position bias documented for LLM judges ([LangSmith](https://docs.smith.langchain.com/evaluation/how_to_guides/evaluate_pairwise); [Zheng et al.](https://arxiv.org/html/2306.05685v4)). Public benchmarks only shortlist models. The same o1-preview agent scores 91.2% on Spider 1.0, 73.0% on BIRD and **21.3% on the enterprise-style Spider 2.0** ([Spider 2.0](https://arxiv.org/abs/2411.07763)), so release decisions must rest on ALOFT's own schemas and KBs.

The data model for this already exists. `PlatformEvalRun` carries `agentRevisionId`, `manifestId`, `seenScore`, `heldOutScore`, `generalisationGap`, `gateVerdict`, `redTeamFindings`, `casesTotal/Passed`, `costUsd` and `durationMs`. `PlatformEvalResult` stores per-case output, score, pass flag, scorer detail, latency, cost and a `trajectoryId` that links to `platform_trajectories` (`prisma/schema.prisma:1733-1779`). Only a runner is missing. Today `POST /api/agent-lab/ops/evals` inserts a `queued` row that nothing ever picks up, and the UI sends `suiteId` without `agentId` (`evals/route.ts:27-47`; `src/views/agent-lab/ops/evals.tsx:21-29,39`).

| Chaos / failure injection | Warehouse down, SQL timeout, KB unavailable, model 429/5xx: degrade honestly, no loop or fabrication (inferred from SRE practice; no cited agent-specific source) | Pre-release, periodic | Advisory |
| Dependency upgrade | Re-run all published agents when model, tool code, schema or KB index changes | On change | Yes for switching defaults |
| Judge validation | TPR/TNR of each judge against human labels | Before a judge may gate | Yes |
| Human review / UAT | Approver reviews every changed verdict and every "Unknown" | At approve | Yes |
| Shadow | Candidate runs on replayed production inputs, output hidden, side effects blocked ([FeatBit](https://www.featbit.co/blogs/offline-eval-shadow-test-canary-rollout)) | Post-approval, automation agents | Gate to promote |
| Canary / A-B | Small sticky cohort with rollback triggers | Post-promotion | Rollback trigger |
| Online evals | Async judges on sampled traces, drift alerts on quality, cost and latency; failures fed back into datasets ([Braintrust](https://docs.braintrust.dev/guides/evals)) | Continuous | Alerting |

No platform reviewed documents a built-in shadow mode, and Foundry routes 100% of traffic to a single deployment ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/agent-applications)). ALOFT should therefore treat shadow as offline replay of logged production questions, and canary as pointer routing with sticky hashing per conversation, built only once a single pointer works. Slow LLM judges belong in asynchronous evaluation, not inline guardrails ([Hamel Husain](https://hamel.dev/blog/posts/evals-faq/)).

## Promotion should require a passing run on the exact version

Today approval is a human click that sets `published` (`review/route.ts:58-63`). Nothing requires an eval, nothing stops a later PATCH from changing a published agent, and the runtime never checks status anyway. A defensible gate runs automatically when a version is submitted for review, stores its run id on the version, and shows the approver the result. Thresholds are organization-specific: the FeatBit playbook explicitly warns against universal numbers ([FeatBit](https://www.featbit.co/blogs/offline-eval-shadow-test-canary-rollout)). The values below are starting points, stored per agent in `PlatformAcceptanceRecord` (`targetMetric`, `threshold`, `generalisationGapThreshold`, `manifestId`; `prisma/schema.prisma:1781-1800`).

| Gate | Rule |
|---|---|
| RG1 Regression | 100% of protected cases pass (pass^3 for automation agents). No case that passes on the current `production` version may fail on the candidate without a recorded waiver |
| RG2 Quality vs production | Paired comparison on the full set. Block if the lower 95% CI bound of the difference is below −X points (X set per agent, e.g. 3-5); show per-case diffs for small sets |
| RG3 Security | Zero successes on permission, exfiltration and write-attempt cases. Injection success rate no worse than production |
| RG4 Budget | p95 latency, mean cost and tool calls within +Y% of production or under absolute caps. Zero loop-cap hits |
| RG5 Judge validity | Only judges with recorded TPR/TNR above the bar (e.g. ≥0.8) may block; the rest are advisory |
| RG6 Human sign-off | Approver acknowledges every changed verdict and every "Unknown". Approval records dataset version, run id and model id; self-approval stays blocked |

Promotion then means moving the protected `production` pointer to the approved version. Langfuse's protected labels, which only admins and owners can move, are the precedent ([Langfuse](https://langfuse.com/docs/prompt-management/features/prompt-version-control)). Model upgrades follow the same path: re-run every published agent's regression suite on old and new model against the same snapshot before the platform default changes.

## A five-phase plan that wires tables already in the schema

The sequence follows dependency order. Release-path bugs come first because every later gate sits on them. Versions come before evals because a gate needs a fixed thing to test. Runtime enforcement comes before online monitoring because there is little point measuring drift on settings the runtime ignores. The phases mirror plans already written in the repo: Phase D of `docs/agent-ops-build-plan.md:340-351` ("pin version on turn metadata", eval tables, headless runner), ADR-004's ModelGateway with limits enforced in code (`docs/business-ai-studio/adr/ADR-004-agent-runtime-and-model-routing.md:9-15`), and `docs/data-access-control-design.md` §8. Automate's Flows already implements the target pattern, with immutable `PlatformFlowVersion` rows, a `current_version_id` and a publish gate that re-runs policy and requires a passing simulation (`prisma/schema.prisma:3227-3240`; `src/lib/flows-store/service.ts:106-135`). Agents should copy it rather than invent a new one.

## Conclusion

The core finding is that ALOFT's gap is integrity, not sophistication. The schema already anticipated manifests, acceptance thresholds, held-out generalization gaps and red-team counts, but the live path lets a chat turn rewrite a published agent and lets anyone run a draft. Approval cannot even reach Automate. Until those are fixed, an eval harness would test something different from what runs, and any score it produced would be decorative. Sequencing therefore matters more than feature breadth: unify status, freeze versions, attribute every run, and only then gate on evals.

The second implication is that every ALOFT agent currently has the same blast radius: the shared principal's entire warehouse view. That makes the security test set and per-agent table scoping more urgent than prompt tuning, and the release gate is where those properties get proved. The part of the industry pattern that matters most here is not semantic versioning or canaries, which most platforms lack anyway. It is a frozen snapshot, a protected pointer, and a passing run tied to that exact snapshot. Everything else can be added incrementally on those three primitives.
